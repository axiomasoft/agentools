# Code definitions and instance data

Install `Definitions.Registry` from actual `Definition` objects in trusted host
code. Explicit platform/tenant OwnerScope plus id/version/content hash identify
immutable installed versions. A tenant cannot inherit another tenant's definition.
The hash covers defaults, hard restrictions, declared editable fields, pinned
plugin references and provenance/evaluation references. Those references are
provenance, not proof that an evaluation ran. Duplicate registry keys and wrong
hashes fail. `Registry.current` applies current revocation/purpose over pins.

Defaults, DraftSettings and HardConstraints are separate types. Draft JSON accepts
only tone and display_name; a Definition further limits which are editable.
Preview is data; it does not publish or modify defaults, restrictions or bundles.
No class/SQL/callback/tool permission is read from an instance. Full ProfileBundle
compilation, publication lifecycle, dependency merges/conflicts and skill routing
remain P7.1/P7.3; this slice does not claim those implementations.

`PostgresInstances.install(Connection)` is explicit schema-owner setup. It creates
version/hash-checked assistant_assignments, assistant_mutations and assistant_pins
in the configured application schema; it changes no existing core table. No
provider calls it automatically. Use the host's current InstanceAuthority and
RepositoryContext for read/create/assign/draft/pin. The host verifies referenced
bundle publication, exact hash, ownership and definition compatibility. No
permissive production authority/store is bundled.

Create fixes a code definition for an instance. Assign changes only the bundle
for NEW sessions; draft changes only the editable draft. CAS revisions and durable
command-key/hash receipts prevent lost updates and conflicting replay. A receipt
replay returns its original revision, even after unrelated edits; current access
is still checked. Changing an instance's code definition or silently migrating an
existing session is unsupported; create a distinct instance or use the owning
future explicit migration API. Existing first-slice core instance config pins
remain immutable.

`SessionBinder` persists the original assignment snapshot and reuses the existing
SessionRepository to materialize its immutable code/bundle pins. If the process
stops between those boundaries, retry recovers that snapshot. Existing sessions
keep @7 after assignment @8; new sessions use @8. A SessionPin contains no draft
preferences. Current revocation still refuses use of an old pin. Published bundle
history and full profile publication are not duplicated here.

Tests cover ownership/hash rejection, locked drafts, CAS/replay, session pinning,
current authority, versioned install and a real deferred-commit PostgreSQL fault.
The platform-definitions gate requires exact cases and isolation proof, Composer
validation/analysis, production no-dev install and current source attribution.
Focused proof uses tests/Definitions/run.py --filter CLASS or METHOD. The source
map is generated by tests/Definitions/attribution.py --write. No donor source was
copied; inventory rows map selected target ideas to consumer tests. Earlier P5.2
historical RED, P2.4 fractional ManualClock and P3.5 audit/reset uncertainty remain
unresolved; local tests do not resolve them. No mutation score or live readiness
claim is made.
