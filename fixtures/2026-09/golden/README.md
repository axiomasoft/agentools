# fixtures/2026-09/golden/

Golden-пары канонизации (`jcs/`) и ключа идемпотентности (`idempotency/`) ревизии
`2026-09`. Формат — пара `<имя>.input.json` + `<имя>.golden.txt` (README.md
корня `fixtures/2026-09/` §7); сравнение — структурное, затем **побайтовое**
(`CFH-36`), не по разбору. `golden.txt` — UTF-8 без BOM, переводы строк `LF`,
**ровно один** завершающий перевод строки (`AOB-44`).

## `jcs/` — канонизация RFC 8785 (JCS)

**Источник:** официальный тест-набор эталонной реализации JCS
[`cyberphone/json-canonicalization`](https://github.com/cyberphone/json-canonicalization),
каталог `testdata/{input,output}/` — тот же набор, на который ссылается сам
[RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) (автор RFC и мейнтейнер
репозитория — Anders Rundgren) и на который опираются independent-реализации
JCS в других языках. Перенесено **2026-07-28**, коммит `master` на дату
переноса.

| Файл | Официальный источник | Перенос |
|:--|:--|:--|
| `rfc8785-arrays.*` | `testdata/{input,output}/arrays.json` | дословно, побайтово |
| `rfc8785-french.*` | `testdata/{input,output}/french.json` | дословно, побайтово |
| `rfc8785-structures.*` | `testdata/{input,output}/structures.json` | дословно, побайтово |
| `rfc8785-unicode.*` | `testdata/{input,output}/unicode.json` | дословно, побайтово |
| `rfc8785-values.*` | `testdata/{input,output}/values.json` | дословно, побайтово |
| `bmp-weird.*` | `testdata/{input,output}/weird.json` | **см. ниже — единственное текстовое отличие** |

`*.input.json` перенесены байт-в-байт (включая исходное форматирование
источника, переводы строк внутри JSON-документа); `*.golden.txt` — байты
`testdata/output/*.json` источника с довешенным ровно одним переводом строки
LF, где источник не оканчивался LF (правило `AOB-44` этого корпуса; источник
своей конвенции завершающего перевода строки не декларирует).

**`bmp-weird` — единственная контролируемая правка входа.** Официальный
`weird.json` кодирует ключ вне BMP (эмодзи `U+1F602`, пара `😂`)
**экранированной** `\u`-парой суррогатов — валидный JSON, но как *текст файла*
не содержит буквальной кодовой точки вне BMP (только ASCII-эскейп), а
`Implementation Rules` этого item'а требуют набор ключей вне BMP **отдельным**,
проверяемым буквальным присутствием такой кодовой точки в байтах
`*.input.json`. Правка: та же пара `😂` заменена **буквальным**
UTF-8-символом 😂 — **тот же** разобранный JSON-объект (проверено:
`json.loads(экранированный) == json.loads(буквальный)`), поэтому канонический
результат (`golden.txt`) **не пересчитывался** и перенесён из официального
`testdata/output/weird.json` без изменений. Остальные семь пар ключ/значение
файла (включая ключи `\r`, ``, кириллицу/латиницу, суррогатную область
не задействующие) перенесены без изменений.

## `idempotency/` — golden-пары ключа идемпотентности

**Формула** (`09_idempotency-errors.md`, `IDE-6`):
`args_fingerprint = "sha-256:" + hex( SHA-256( JCS( <аргументы вызова> ) ) )`.

Пары `key-composition-*` **посчитаны инструментом** (не взяты из внешнего
источника — формула наша, эталонного набора для неё не существует):
Python 3.12, `hashlib.sha256` над UTF-8-байтами `json.dumps(args,
sort_keys=True, separators=(',', ':'), ensure_ascii=False)`. Это НЕ
универсальный JCS-канонизатор (числа с плавающей точкой, суррогатные пары в
ключах и управляющие символы вне `\n\r\t` этим вызовом сериализуются НЕ по
RFC 8785) — он корректен **только** для данных без этих случаев, и все три
пары намеренно используют исключительно ASCII/кириллические строки, целые
числа и вложенные объекты/массивы без дублирующихся ключей, где сортировка
ключей по кодовым точкам совпадает с сортировкой по кодовым единицам UTF-16
(`AOB-33`), а сериализация целых совпадает с ECMAScript `Number::toString`
(`AOB-35`) — то есть ровно тот участок JCS, где `json.dumps(sort_keys=True)`
и RFC 8785 дают тождественный результат. Адверсариальные случаи (float,
экранирование, ключи вне BMP, `NaN`/дубли) покрыты `jcs/`, не здесь.

`*.input.json` несёт аргументы в **естественном** (не пересортированном)
порядке ключей — так, как их прислал бы вызывающий; демонстрирует, что
`args_fingerprint` не зависит от порядка ключей во входном сообщении, только
от канонической формы.

| Файл | Демонстрирует |
|:--|:--|
| `key-composition-001` | строка с кириллицей, целое число, порядок ключей ≠ алфавитному |
| `key-composition-002` | три строковых поля, порядок ключей ≠ алфавитному |
| `key-composition-003` | вложенный массив объектов, ключи объектов внутри массива тоже пересортировываются независимо на каждом уровне |
