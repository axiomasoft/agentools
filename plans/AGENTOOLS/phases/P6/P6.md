# P6 — Conformance: harness-протокол, раннер, baseline, четырёхслойный CI

## Phase Context

Первая фаза волны реализации (метка `DR-01` §K — «P1 conformance»; прежний номер фазы — P1, см.
карту переименования `plan.md` §4). Делает договор ревизии `2026-08` **исполняемым**: раннер
общается с адаптером каждого SDK построчным JSON по stdin/stdout (`start → config → run × N →
stop`), фикстуры и ожидания принадлежат **раннеру**, реализации не встраиваются друг в друга
(`DR-01` §J1). Severity вердикта выводится из нормативного слова правила, тихого SKIP не
существует — только статус «Not testable» с причиной (§J3). Baseline известных отказов защищён от
протухания: запись, которая начала проходить, — тоже ошибка (§J4). CI — четыре слоя в строгом
порядке, merge блокируется на любом слое и на любом языке (§J5). Golden-файлы имеют канонический
вид и сравниваются двухступенчато (§J7); ревизии и SDK версионируются lockstep (§J8).

**Несущая граница фазы: P6 ничего не нормирует, она нормы ИСПОЛНЯЕТ.** К её старту ревизия
заморожена (P5.2), поэтому расхождение «написано ↔ реализуемо» разбирается как дефект адаптера,
вектора либо текста правила, а не подгоняется. По умолчанию корпус `fixtures/2026-08/**` фазой P6
не правится ни на байт (D72); заведомо красные мутанты живут в
`conformance/tests/fixtures/mutants/`. Исключение D183 расширяет прежний D180 ровно до admission-
ремедиации P6.2: exact `clarification-004` stimulus, удаление неисполняемого `conftoken-001`,
harness protocol 1.1 для runner-owned probes и их производные manifest/coverage/tag-артефакты.
Исключение не даёт P6 права менять продуктовую семантику документов `00`–`10` либо остальные
векторы.

**Executable admission P6.2 (D183).** P6.2 больше не пишет reference adapter. Он до любой
реализации SUT доказывает три свойства входа: semantic stimuli не требуют несовместимых exact
outcomes, `run` не отдаёт oracle (`expect`) адаптеру, а `tool_calls`/`observations` снимаются
runner-owned probes через protocol 1.1 и реально сравниваются matcher-ом. Corrective delta
поимённо закрыт: D180 `clarification-004` + удаление self-report carrier `conftoken-001`; после
этого core=121, extension=92, full=213. Полный разбор —
`research/25-p6-executable-admission-chain-2026-08.md`.

**Что фаза решает сама** — только НАШИ артефакты, ревизией не нормируемые: раскладка
`conformance/**`, драйвер слоёв CI, реестр SDK, форма отчётов (D67). Полный разбор — синтез
`research/05-p6-conformance-harness-2026-08.md`.

**Гейт входа фазы.** Фаза стартует только при терминальной P5 с вердиктом `**Вердикт: GREEN**`
(`artifacts/P5-gate-b.md`), ревизией в статусе `frozen` и существующим аннотированным тегом
`spec-2026-08`: без замороженной ревизии раннер писался бы против движущегося текста, а lockstep
сверял бы манифесты с несуществующим якорем. Между items P6.6 и P6.7 стоит **гейт владельца** —
исход `DR-02` §6 по слою 2 CI (три ветки — Scope P6.7, разбор — D68).

> **Контракт фазы (contract-first).** Потребляет: замороженную ревизию `2026-08` +
> `11_conformance-harness.md` (нормативный harness-протокол, severity, baseline, четыре слоя CI,
> golden, lockstep) + `rules.json` (нормативное слово, уровень, `Not testable` с причиной) +
> корпус `fixtures/2026-08/**` трёх классов с `README.md` (формат вектора, алгоритм частичного
> матча, семантика `!field`) и производным `coverage.md` + аннотированный тег `spec-2026-08` как
> якорь lockstep (фазы P3/P4/P5); `DR-02` §4/§6 (вердикт «DTO руками» и открытый owner-gate по
> слою 2 CI). Производит: раннер `conformance/bin/run`, эталонный адаптер (полная семантика
> ревизии, in-memory), исполнение классов `behavior` (раннером) и `harness` (самотестом),
> baseline с анти-эрозией, golden-механику, четырёхслойный CI одним носителем
> (`tools/ci_gate.py`, вызываемым из `.github/workflows/ci.yml`), реестр SDK
> `conformance/sdks.json`, lockstep-сверку манифестов, коммитимый отчёт покрытия по уровням и
> вердикт `ГЕЙТ P6` (`artifacts/P6-gate.md`). Границы: НЕ реализует SDK (P7/P8) — регистрацию в
> `sdks.json` делают они сами; НЕ правит спеку, схемы и корпус (расхождение — эскалация с ценой
> «новая датированная ревизия»); НЕ решает owner-gate `DR-02` §6 (владелец) и не предрешает его
> исход; исключение D183 разрешает P6.2 только закрытый admission delta и его
> derived/provenance артефакты; НЕ настраивает remote и хостинг (Q-2 — вне фазы); НЕ выбирает стратегию релиза pub
> (Q-8 — реализуется только СВЕРКА); НЕ трогает ревизию `2026-07-draft` и её исторический корпус.

**Гейт выхода (DR-01 §K):** «раннер детерминированно гоняет все векторы против эталонного
адаптера, включая заведомо красный прогон» — проверяемо, все пять условий на ОДНОМ дереве:
(1) `conformance/bin/run` против эталонного адаптера по всему корпусу — ноль отказов, код возврата
0, число строк отчёта равно числу векторов класса `behavior` в корпусе; (2) прогон
вектора-мутанта из `conformance/tests/fixtures/mutants/` — код возврата 1 и названный mismatch;
(3) `conformance/bin/harness-selftest` по всем кейсам класса `harness` — зелёный, плюс красный на
кейсе-нарушении; (4) `conformance/reports/reference-levels.md` сгенерирован детерминированно и
показывает разбивку L1/L2/L3; (5) `python3 tools/ci_gate.py --all` зелёный локально И каждый из
четырёх слоёв доказан красным на своём отрицательном входе. Вердикт `ГЕЙТ P6: PASS` записан в
`artifacts/P6-gate.md`.

**Раскладка по репозиториям (D30).** Артефакты раннера, CI и ревизии (`conformance/**`,
`tools/**`, `.github/**`, `spec/**`, `fixtures/**`) живут в репозитории
`~/projects/packages/agentools` — репо-относительные пути в items считаются от его корня, и
команды `Validation` над ними запускаются оттуда, если не сказано иное. Файлы плана
(`artifacts/`, `findings/`, `research/`, `10_decisions/`, `phases/`, `plan.md`,

vault, команды над ними запускаются из каталога плана. Закрытие item'а — два коммита в двух
репозиториях (`plan.md` §2); хеш item-коммита для handoff берётся командой
`git -C ~/projects/packages/agentools rev-parse --short HEAD`.

**Гигиена закрытия.** Каждый item печатает в Completion Notes каноническую строку
`write-site: pre_mutation: <код> · pre_final: <код>` (машинный гейт `plan_lint`); счёт линтера

— путь машинно-специфичен, живёт здесь и в `Implementation Rules`, а не в `Validation` (D36).
