### P6.6 — Самотест harness-протокола: исполнение класса `harness`

**Intent:** Реализовать `conformance/bin/harness-selftest` — исполнитель кейсов класса `harness` (`fixtures/2026-08/harness/**`), субъект которых сам РАННЕР: воспроизвести транскрипт `runner → adapter` / `adapter → runner` лентой-адаптером и сверить, что раннер соблюдает нормированную последовательность `start → config → run × N → stop`, объявляет версию протокола и корректно реагирует на нарушения (`run` до `config`, отсутствующий `stop`, несовпадение версии протокола).
**Why:** Класс `harness` — единственный, чей субъект не SDK и не артефакт, а наш собственный раннер; `research/03-…` §3 прямо закрепляет его исполнение за фазой P6, и в фазе P4 он проверяется только структурно (оговорка честности D26/D53). Если этот класс не исполнить, гейт «раннер гоняет все векторы» окажется достигнут при непрогнанном классе — то есть ровно «покрытие на бумаге», против которого заведены три класса. `RAG:— (repo-grounded: research/03-p4-vector-corpus-2026-08.md §3 — класс harness исполняет самотест раннера, фаза P6; phases/P4.md P4.8 — ≥5 harness-кейсов и нарушения; DR-01 §J1)`.
**Scope Included:** (а) исполнитель `conformance/bin/harness-selftest --cases <каталог harness-кейсов>`: читает кейс, поднимает ленту-адаптер, воспроизводящий сторону `adapter → runner` транскрипта, запускает раннер и сверяет сторону `runner → adapter` и итоговый вердикт с `expect` кейса; (б) поддержка кейсов-нарушений: `run` до `config`, отсутствующий `stop`, несовпадение объявленной версии протокола — ожидание кейса обязано наблюдаться (раннер отвергает диалог с названной диагностикой), а не «как-нибудь падать»; (в) исполнение `mcp_errors` из CFH-55 пары P4.12: exact mapping `MissingRequiredClientCapabilityError=-32003`, `UnsupportedProtocolVersionError=-32004` проходит, изменение любого code даёт named violation `CFH-55`; это вход selftest, не сообщение harness wire; (г) закрытое перечисление статусов и коды возврата — те же, что у раннера (P6.1/P6.4), никакого собственного словаря; (д) отчёт: строка на каждый harness-кейс корпуса; (е) отрицательный прогон: заведомо испорченный кейс в `conformance/tests/fixtures/harness/` (ожидание, которого раннер не выполняет) → красный, что доказывает различающую силу самотеста.
**Scope Excluded:** правки кейсов корпуса `fixtures/2026-08/harness/**` (заморожены); поведенческие векторы (P6.1–P6.3); golden (P6.5); слои CI (P6.7 — этот item только даёт команду, которую слой вызовет); lockstep (P6.8); гейт фазы (P6.9); правки нормативного текста harness-протокола.

**Implementation Rules:** субъект самотеста — РАННЕР: лента-адаптер не содержит никакой семантики ревизии и не переиспользует эталонный адаптер (иначе проверялся бы он); кейс исполняется целиком, частичное воспроизведение транскрипта запрещено; `mcp_errors` инжектируется как вход simulated MCP peer и не превращается в новое сообщение harness-протокола; mapping кодов берётся из `CFH-55`, не из диапазона JSON-RPC и не из `title` кейса; статусы и коды возврата берутся из общего перечисления раннера; ожидание кейса-нарушения обязано наблюдаться как НАЗВАННАЯ диагностика, а не как любой ненулевой код; кейсы корпуса не правятся; плановый линтер — командой из Phase Context.
**Code Guidance:** Стиль — как в P6.1; лента-адаптер — минимальный скрипт, читающий транскрипт и печатающий свою сторону. Анти-самообман: «самотест зелёный» ничего не значит без красного прогона на испорченном кейсе — оба приводятся в Completion Notes. Для CFH-55 запрещено сравнивать expected с тем же значением без прохождения runner mapping или принимать любой code закрытого диапазона: wrong-code mutant обязан краснеть адресно. ЗАПРЕЩЕНО переиспользовать эталонный адаптер как ленту, вводить статус «пропущено» либо расширять wire schema ради test-only input.
