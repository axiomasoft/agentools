### P2.4 — Транспорт Dart: `mcp_dart` prerelease vs тонкий клиент — smoke-прототип

**Intent:** Эмпирически выбрать транспортный слой для Dart SDK: проверить на smoke-прототипе, даёт ли `mcp_dart` (prerelease с dual-era) то, что нужно modern-эре, и сколько стоит тонкий клиент против `schema.json`; выдать вердикт с критериями.
**Why:** `DR-01` §L-5 оставляет вопрос открытым и адресует его этой фазе; выбор определяет раскладку фазы P8 и объём поддержки. `RAG:✅ 2026-07-26 R-10 §4: mcp_dart stable 2.2.2 (MIT); prerelease 2.3.0-dev.3 — dual-era профиль (prefer 2026-07-28, fallback на initialization-based), input_required, Tasks, url-elicitation`; перепроверено `RAG:✅ 2026-07-27 (pub.dev/packages/mcp_dart): stable по-прежнему 2.2.2, лицензия MIT, prerelease-линия 2.3.0-dev.x (номер dev-релиза расходится по срезам страницы — точную версию берёт исполнитель из `dart pub` на дату прогона, а не из этой строки)`. Директива владельца 2026-07-26 «legacy как понятия нет» делает dual-era-ветки чужим кодом в нашем контуре — цена этого должна быть измерена, а не предположена.
**Scope Included:** (а) критерии из `research/01-target-structure-2026-08.md` §4, заполненные фактами: доступна ли инъекция per-request `_meta` (`protocolVersion`/`clientCapabilities`), виден ли `resultType`/`input_required` на уровне API, поддержан ли `server/discover`, можно ли работать БЕЗ `initialize`, лицензия и статус версии; (б) smoke-прототип: минимальный Dart-клиент, выполняющий один `tools/call` и один `server/discover` против **локального мок-сервера** (мок пишется здесь же, любым доступным способом: `dart:io` HttpServer или python3 stdlib), для обоих вариантов — поверх `mcp_dart` и «руками» (тонкий клиент), с замером объёма кода тонкого варианта; (в) вердикт + названный триггер ре-проверки после пина финала MCP (фаза P1); (г) артефакты в `bakeoff/dart-transport/**` + выжимка `findings/P2-dart-transport.md`.
**Scope Excluded:** реализация транспорта в `dart/` (фаза P8 по вердикту этого item'а); сетевые прогоны против чужих серверов; OAuth/HTTP-авторизация (не нужна ни одному нашему контуру на этом шаге); пин байтов финала MCP (фаза P1) — прототип использует доступный на дату исполнения `schema.json` только как **форму сообщений**, и вердикт формулируется так, чтобы не зависеть от его конкретных байтов.
**Inputs:** `research/01-target-structure-2026-08.md` §4 (таблица критериев) · `20_research/R-10_landscape-2026-07.md` §4 · `10_decisions/DR-01_architecture-2026-08.md` §A3 (modern-only), §L-5 · `findings/P2-bakeoff-recon-2026-07-27.md` §3 (перепроверенные версии и лицензия `mcp_dart`) · результат P2.3 (насколько дорого писать типы руками) — если P2.3 ещё не закрыт, item исполним: сравнение объёма делается внутри прототипа.

**Implementation Rules:** сравнение симметричное — один и тот же сценарий на обоих вариантах, один и тот же мок; внешние факты о пакете (версия, лицензия, наличие API) — из `pub.dev`/исходников пакета с URL и датой, а не из блогов; точная prerelease-версия фиксируется из `dart pub add mcp_dart:<constraint>`/`pubspec.lock`, а не переписывается из `findings`; прототипы живут только в `bakeoff/` (каталог `dart/` этой фазой не создаётся); мок-сервер отвечает фиксированными JSON-ответами из файлов (детерминизм, никакой генерации на лету); логи прогонов кладутся в `bakeoff/dart-transport/*.log` и обязаны быть отслеживаемыми — переисключение для этого каталога уже входит в `bakeoff/.gitignore` (P2.1), править чужой файл не нужно; если правило не сработало — эскалация, а не самовольная правка (файл в Scope другого item'а).
**Code Guidance:** Прототип — одноразовый инструмент измерения, а не заготовка SDK: без абстракций «на вырост», без интерфейсов, которые «потом переедут» (переезд решает фаза P8 по вердикту). Анти-самообман (гейт-item): вердикт «берём `mcp_dart`» ставится только если ВСЕ критерии (а) заполнены фактами и smoke прошёл; «вероятно поддерживает» — это `not verified`, а не «да». Если prerelease-API требует включения legacy-ветки, чтобы заработала modern-эра — это факт против кандидата, зафиксировать явно (директива D20). If-then: оба варианта оказались непригодны (например, prerelease нестабилен, а тонкий клиент требует непропорционально много) → НЕ выбирать «меньшее зло» молча: строка в вердикте `эскалация владельцу` + Escalation Needed: yes (trigger «unclear architecture»). If-then: по ходу выяснилось, что от вердикта зависят байты финала MCP (а не только форма) → вердикт формулируется условно и триггер ре-проверки после P1 записывается явно, с адресом (какой item фазы P8 обязан его снять).
**Validation:** пусть `T` = `findings/P2-dart-transport.md` в каталоге плана · `test -s "$T"` · в файле присутствуют все критерии таблицы §4 документа `research/01-target-structure-2026-08.md` (`grep -c '^|' "$T"` ≥ 8) · `cd bakeoff/dart-transport && dart analyze` зелёный для прототипов · `git ls-files bakeoff/dart-transport/*.log | wc -l` ≥ 2 (оба прогона smoke приложены ОТСЛЕЖИВАЕМЫМИ логами) · `grep -nE 'ВЕРДИКТ: (mcp_dart|тонкий клиент|эскалация)' "$T"` — ровно одна строка · `grep -c 'ре-проверка после P1' "$T"` ≥ 1 (триггер назван) · `git ls-files bakeoff/dart-transport/pubspec.lock` — непустой вывод (зафиксирована прогнанная версия `mcp_dart`).
**Deliverables:** `findings/P2-dart-transport.md` (критерии + вердикт + триггер) + прототипы, отслеживаемые логи и `pubspec.lock` в `bakeoff/dart-transport/`.
