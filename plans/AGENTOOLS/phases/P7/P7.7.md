### P7.7 — Подтверждение: Policy/Protocol Layer, подписанный токен, TTL, dual control, событие решения

**Intent:** Реализовать документ `04` (правила `CNF-*`) двумя раздельными слоями: Policy Layer (нужен ли гейт, precedence решений) и Protocol Layer (prepare/preview/commit одним инструментом, подписанный одноразовый self-contained токен с покрытием полей §B2, обязательный TTL §B4, `edit` порождает НОВЫЙ prepare §B3, dual control для необратимых §B5, повторная авторизация на commit §B8, обязательное событие решения по схеме §I4).
**Why:** Здесь сходятся деньги и доказуемость. Анти-tampering между preview и commit не даёт нативно ни один из шести разобранных agent-фреймворков — слой целиком наш, и его дефект не ловится ничем снаружи. Четыре отказа токена (подмена аргумента, повтор, просрочка, чужой субъект) обязаны быть РАЗНЫМИ: слитые в один, они не дают вызывающему понять, повторять ли prepare, — а просрочка нормирована как **tool execution error**, а не протокольная ошибка, именно чтобы модель могла повторить сама. Повторная авторизация на commit — защита от классического TOCTOU: между preview и commit проходит произвольное время. Событие решения — единственное, что делает решение по гейту доказуемым постфактум, и его схема §I4 требует ОБА хеша аргументов, совпадение которых является рантаймовым инвариантом допуска к commit. `RAG:— (repo-grounded: DR-01 §B2 — состав покрытия токена и четыре отказа, просрочка = tool execution error; §B3 — edit порождает новый prepare, прежнее SUPERSEDED; §B4 — TTL обязательное поле; §B5 — dual control proposer ≠ approver; §B6 — Policy отделён от Protocol; §B8 — повторная авторизация; §I4 — схема события решения и инвариант двух хешей; research/06-… §8)`.
**Scope Included:** (а) Policy Layer: нужен ли гейт для вызова, precedence `deny → ask → allow`, вход — профиль инструмента и контекст, выход — решение о необходимости гейта; НИКАКОЙ протокольной механики внутри; (б) Protocol Layer: prepare/preview/commit ОДНИМ инструментом (вызов без токена → prepare, с токеном → commit), состав preview — по документу `04`; (в) подписанный self-contained токен: непрозрачный, одноразовый, integrity-protected, покрывает `action_id`, `principal`, `tool_name`, `descriptor_digest`, `args_fingerprint`, `expires_at`, `proposal_version`; порт `TokenSigner` в `src/Contracts/` (HMAC-реализация по умолчанию), токен передаётся ТОЛЬКО обычным аргументом вызова; (г) четыре РАЗНЫХ отказа commit: несовпавший fingerprint аргументов, просроченный (как **tool execution error**), повторно использованный, предъявленный другим субъектом; (д) обязательный TTL (§B4) — поле, а не опция: отсутствие = ошибка; (е) `edit` не является решением (§B3): правка аргументов создаёт НОВОЕ предложение с новым токеном и новым preview, прежнее помечается `SUPERSEDED` в журнале; токен версионируется на ПРЕДЛОЖЕНИЕ; (ж) dual control для необратимых действий: proposer ≠ approver, нарушение — отказ; (з) повторная авторизация на commit (§B8): результат prepare НЕ кэшируется как разрешение; (и) событие решения по схеме §I4 — обязательное, с `args_hash_at_decision` и `args_hash_at_commit`, совпадение которых проверяется как рантаймовый инвариант допуска; (к) тесты, чьи ожидания взяты из векторов `CNF-*`, с перечнем заимствованных `id`.
**Scope Excluded:** вычисление `descriptor_digest` (P7.4 — здесь оно ПОТРЕБЛЯЕТСЯ); `args_fingerprint` как механизм дедупликации (P7.8 — здесь используется как поле покрытия токена); журнал как таковой (P7.5); уточнения MRTR (P7.10); полная схема аудита и её экспорт (P7.11 — здесь только событие решения §I4); конкретная политика прав потребителя — Policy Layer принимает решение по предоставленному контексту, а не реализует RBAC; ЛЮБЫЕ правки ревизии, схем и корпуса.

**Implementation Rules:** Policy и Protocol — РАЗНЫЕ классы в разных каталогах (§B6): протокольная механика внутри политики и наоборот запрещены, границу проверяет тест; состав покрытия токена берётся ДОСЛОВНО из §B2 и правила ревизии — «на всякий случай» лишнее поле ломает межъязыковую совместимость токена так же, как недостающее; подпись считается через порт `TokenSigner`, ключ приходит извне — захардкоженный секрет либо секрет по умолчанию ЗАПРЕЩЕНЫ; четыре отказа — четыре РАЗНЫХ строковых кода в модели §E1, просрочка отдаётся как tool execution error, а не как протокольная ошибка; одноразовость токена доказывается тестом повторного предъявления, а не хранением «до перезапуска»; `args_fingerprint` берётся из механики P7.8/P7.3 (канонизация), второй способ считать хеш аргументов запрещён; расхождение с вектором разбирается прогоном против эталонного адаптера, оба вывода — в отчёте; плановый линтер — командой из Phase Context.
**Code Guidance:** Стиль — как P7.5. Анти-самообман: «токен проверяется» ≠ «токен защищает» — доказательством считаются ЧЕТЫРЕ отдельных красных (подмена аргумента, повтор, просрочка, чужой субъект), каждый со своим кодом и выводом; проверка «токен непустой» доказательством не является. «Dual control реализован» без теста proposer = approver → отказ не считается сданным. Анти-подгонка: если вектор ожидает tool execution error, а реализация даёт протокольную — исправляется КЛАСС ошибки, а не ожидание вектора. ЗАПРЕЩЕНО: передавать токен в обход обычного аргумента вызова; кэшировать результат prepare как разрешение; мутировать предложение по `edit` вместо создания нового; хардкодить секрет подписи; считать `args_fingerprint` вторым способом; сливать четыре отказа в один код. If-then: документ `04` не задаёт, что делать при `edit` уже подтверждённого предложения → `🔴 Blocked` + эскалация (trigger «конфликт правил»). If-then: правило ревизии противоречит §B2 в составе покрытия токена → побеждает РЕВИЗИЯ (она нормативна, `DR-01` — решение о её содержании), расхождение называется в отчёте и эскалируется как дефект согласования с адресатом «владелец», реализация не выбирает сторону молча.
