## 1. Context

AgenTools — языконезависимый слой **agent + tools + сценарии** поверх MCP для двух контуров
экосистемы: FlexCRM (PHP, ядро CoreX) и AiFina/AiResto (Dart, ядро AxiomaErpSdk). Архитектура —
protocol-first гибрид: одна нормативная спека + два тонких нативных SDK, которые проверяются
общим набором тест-векторов. Пакет **не** третий рантайм: `corex/ai` и `axioma_assistant`
реализуют его контракты (`00_MASTER_PLAN.md` §4, решения D1–D14 владельца).

Фаза P0 (закрыта 2026-07-10, аудит GREEN 2026-07-11) выпустила ревизию `spec/revisions/2026-07-draft`
против MCP 2025-11-25. **Эта ревизия — история и не патчится.** Директива владельца 2026-07-26:
реализации нет, замороженных контрактов нет, legacy-эры не существует как понятия — выпускается
новая датированная ревизия **`2026-08`, modern-only** против MCP **2026-07-28**
(`RAG:✅ 2026-07-26 R-11 §1: на дату разведки ревизия — RC, финал 28.07; ре-верификация финала —
фаза P1`). Решения пересборки приняты и не переоткрываются:
`10_decisions/DR-01_architecture-2026-08.md` (§A–§M, 40+ решений).

План исполняет две волны. **Волна A/B (фазы P1–P5)** — подготовка и авторинг: ре-верификация
финала MCP → bakeoff генераторов и транспорт Dart → авторинг ревизии `2026-08` → тест-векторы →
адверсариальный аудит согласования с обязательным вердиктом GREEN. **Волна реализации
(фазы P6–P10)** — conformance-раннер → PHP SDK → Dart SDK → вертикальный срез в CRM → перенос в
ERP-контур. Ни одна фаза реализации не стартует до GREEN фазы P5.

Ключевой инвариант ревизии `2026-08` (`DR-01` §J2, требование владельца): каждое MUST-правило
несёт стабильный идентификатор и покрыто ≥1 тест-вектором, связь «правило ↔ вектор» проверяется
линтером **в обе стороны**.

## 2. Execution Rules

- Один item за раз; статус обновляется В ПЛАНЕ (файл фазы + Status Board здесь) до завершения работы.
- Статусы — 6 канонических строк байт-в-байт (`plan-protocol` §6).
- **Решения `DR-01` и D1–D16 не пересматриваются.** Найдено расхождение решения с фактом →
  эскалация владельцу (`plan-protocol` §10), не молчаливая правка `DR-01`.
- **Ревизия `spec/revisions/2026-07-draft` неизменяема** — ни один item плана её не патчит.
  Новая работа идёт только в `spec/revisions/2026-08/`.
- **Legacy-лексика MCP запрещена** в ревизии `2026-08` (D20): ни `initialize`, ни `Mcp-Session-Id`,
  ни server-initiated запросов, ни SSE-resumability, ни Roots/Sampling/Logging/DCR — даже в виде
  «поддерживается для совместимости». Только раздел «out of scope by design».
- Внешние факты (версии, API, «ещё актуально») — только через RAG с URL-источником; без
  источника — `[UNVERIFIED]`. RAG-выжимка пишется в `findings/<Pn>-<slug>.md` в том же ходе.
- Спека пишется на русском, нормативные слова — RFC 2119 англ. (MUST/SHOULD/MAY), идентификаторы
  и имена полей — англ.
- Код: комментарии и описания тестов по `general:writing-style` (русский, объяснять «почему»).
- Vault-файлы этой папки (`00_MASTER_PLAN`, `10_decisions`, `20_research`, `brief`, `research`) —
  источники и синтез, НЕ артефакты исполнения; артефакты кода живут в `~/projects/packages/agentools`.
- **Закрытие code-producing item'а идёт по ДВУМ репозиториям** (D30): item-коммит — в
  `~/projects/packages/agentools` (только пути из `Files`), bookkeeping-коммит — в vault-репо
  `Brain` (`05-Projects/03-Packages/AgenTools/plans/AGENTOOLS/**`). Топология «два коммита»
  (`plan-protocol` §8) сохраняется; хеш item-коммита для `handoff.md` берётся из репозитория
  артефактов: `git -C ~/projects/packages/agentools rev-parse --short HEAD`. `git add -A` и
  `git commit -a` запрещены в обоих репозиториях.
- **Bookkeeping одного плана = отдельный коммит** (D48): bookkeeping-коммит несёт файлы ТОЛЬКО
  этого плана (`plans/AGENTOOLS/**` + `plans/ACTIVE.md`). Работа над другим планом в той же
  сессии закрывается СВОИМ коммитом; смешение бухгалтерии двух планов — отклонение процесса
  (`🟢` + запись в Known Deviations), а не «мелочь оформления».
- **Счёт линтера публикуется на дереве, содержащем сам отчёт** (D49): строка `## 6. Update Log`
  — ≤300 символов; `plan-lint` прогоняется ПОСЛЕ записи строки и перезаписи `handoff.md`, до
  bookkeeping-коммита. Самоописывающая строка иначе не попадает в собственное измерение.
- После закрытия item/фазы — перезаписать `handoff.md` целиком.
- Прежний workflow-скрипт `workflows/wf-agentools-drive.js` **устарел, запуск запрещён** (D23).
- **Переходное правило Layout v2 (до P6):** закрытие пункта фиксируется записью в `journal.jsonl`, находкой или решением при необходимости и регенерацией видов; поля исхода в файле ТЗ запрещены и ловятся линтером.

## 3. Routing

Отклонения от SSOT-матрицы `plan-protocol` §9. Строки волны A/B — построчные (фазы
детализированы либо детализируются следующим проходом); строки P6–P10 — фазовые черновики до
детализации (проход 3).

**Форма ячейки route — машинный контракт, не стиль (D29).** Ячейка колонки
`Model class/effort` обязана быть голой парой `<класс>/<effort>` из замороженных лестниц
(`economy` < `implementation` < `frontier`; `low` < `medium` < `high` < `xhigh` < `max`), а
колонка `Items` — точным id (`P2.5`) либо диапазоном одной фазы (`P2.2–P2.4`). Любой хвост в
ячейке (подсказка провайдера, требуемые capabilities) ломает разбор компилятора Task Contract,
и item становится неисполним. Подсказки моделей провайдера и требуемые capabilities живут в
колонке «Почему», а не в route-ячейке.

**Колонка `Batch` — ЕДИНСТВЕННЫЙ носитель членства в группе запуска (D122).** Значение —
идентификатор группы: батч одной сессии (`B*`, канон `plan-protocol` §9 «Subphase batching»)
либо волна оркестрации (`W*`, скрипт в `workflows/`); пустая ячейка `—` = item исполняется solo.
`roadmap.md` членство ПОКАЗЫВАЕТ, но не назначает — как и модели с effort; расхождение карты с
этой колонкой чинится картой. Критерий, по которому `full`-item попадает в группу либо остаётся
solo, — D122.
