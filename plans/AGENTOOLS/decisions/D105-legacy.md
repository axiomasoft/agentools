## Решение

**Фаза P9 оркестрацию НЕ объявляет — критерий `plan-protocol` §7 перепроверен ПОСТРОЧНО по фактам items** (не унаследован от вердиктов фаз P4/P6/P7/P8). Сигнал 1 не срабатывает: шесть items из семи ссылаются `Inputs` на `Deliverables` предшествующих items ТОЙ ЖЕ фазы, а единственная формально независимая пара (P9.3, P9.4) пишет в один интеграционный модуль по одному утверждённому контракту — «N≥3» не набирается. Сигнал 2 не срабатывает по ДВУМ доводам, специфичным именно для этой фазы: внутри неё стоят ДВА гейта владельца (выбор ветки дома кода и утверждение INT-001 с предложениями дельт чужого канона) — скрипт их не проходит, а обход означает решение за владельца в чужом репозитории; и item P9.7 требует РЕАЛЬНОЙ модели с интерпретацией её ошибок, что не является детерминированной Validation по построению (заскриптованный LLM обязателен для conformance по D8 и запрещён как доказательство E2E). Альтернатива «объявить оркестрацию, раз items выглядят разделимыми» отклонена: каждый пишет в чужую кодовую базу, то есть класс `Review=full`, для которого инвариант D6 `plan-protocol` §9 запрещает поток «без подтверждения между items»
