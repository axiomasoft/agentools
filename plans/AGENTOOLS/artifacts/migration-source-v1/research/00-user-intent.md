## 3. Целевая механика traceability «правило ↔ вектор» (требование брифа №11–12)

Проектное решение, которое A2 и A3 обязаны реализовать (детали — при детализации фаз):

1. **Идентификатор правила.** Каждое нормативное предложение несёт стабильный маркер
   `<DOC>-<n>` (существующая конвенция `2026-07-draft`: `TCP-`/`LC-`/`CP-`/`SC-`/`AU-`/`IE-`,
   переходы FSM — `LC-Tn`) и **нормативное слово** RFC 2119 в том же предложении. Маркер
   стабилен внутри ревизии; смена смысла = новый маркер, не переиспользование старого.
2. **Машинночитаемый индекс правил** — производный артефакт ревизии
   (`spec/revisions/2026-08/rules.json`, генерируется из markdown, не пишется руками):
   `{rule_id, doc, normative_word: MUST|MUST NOT|SHOULD|SHOULD NOT|MAY, level: L1|L2|L3,
   text_digest}`. Генерация детерминирована; расхождение сгенерированного индекса с
   закоммиченным — красный CI (слой 1 четырёхслойного гейта J5).
3. **Вектор ссылается на правило:** поле `spec_rule_ids` (список) + `spec_rev` — обязательные.
   Ссылка на несуществующий маркер = ошибка (уже реализовано в `tools/spec_lint.py` в одну
   сторону — `spec_refs` сверяется с корпусом доков).
4. **Двунаправленный гейт (новое):**
   - **правило → вектор:** каждое правило с нормативным словом `MUST`/`MUST NOT` обязано иметь
     ≥1 вектор; `SHOULD`-правило без вектора — предупреждение; правило со статусом
     `Not testable` обязано нести причину в индексе (тихого SKIP нет — J3);
   - **вектор → правило:** каждый вектор обязан ссылаться ≥1 существующим маркером;
     осиротевший вектор — ошибка.
   Оба направления считает один линтер по `rules.json` + `fixtures/**`; вывод — таблица
   покрытия (правило, нормативное слово, векторы) для отчёта conformance.
5. **Оговорка честности:** «правило покрыто вектором» ≠ «правило проверено содержательно» —
   линтер видит только ссылку. Содержательность проверяет обзор фазы P5 (B) и adversarial-аудит.

## 4. Anti-regression: чего не воспроизводить из ревизии `2026-07-draft`

Дефекты, зафиксированные в закрытой фазе P0 (её Known Deviations и аудит 2026-07-11) — вход для
A2, чтобы новая ревизия не унаследовала те же болезни. Источник — `phases/P0.md`
(Completion Notes P0.3/P0.4/P0.7/P0.8/P0.10 + Phase Handoff, вердикт аудита GREEN).

| # | Дефект `2026-07-draft` | Правило для ревизии `2026-08` |
|:--|:--|:--|
| 1 | Перечисление материализовано дважды (`StepStartedPayload.kind` инлайн-enum ↔ `StepKind`; `error.json` `code` pattern ↔ `$defs.ErrorCategory`) | Одно перечисление = один `$defs`-узел, ссылка через `$ref`; дубль — ошибка линтера спеки |
| 2 | Схема строже прозы (`required` в payload'ах, которых проза не требует) | Проза и схема — один источник: правило порождает и текст, и `required`; расхождение ловит линтер на примерах |
| 3 | Правило отнесено к двум уровням сразу (`TCP-13` в L1 и L3) / не отнесено ни к одному (`AU-20`) | Уровень (`L1`/`L2`/`L3`) — обязательное поле индекса правил; ровно один уровень на правило |
| 4 | Покрытие правил векторами ~30 % (не измерялось автоматически) | Двунаправленный линтер (§3) — гейт, а не отчёт: MUST без вектора = красный |
| 5 | `description` схемы переобобщает нормативное правило (`idempotentHint`) | Текст `description` не вводит нормы; норма — только в markdown-правиле с маркером |
| 6 | Кросс-файловые `$ref` в `fixture.json` не резолвятся conformant-валидатором offline | `$ref` внутри ревизии — только относительные и резолвимые без сети (ограничение SEP-2106 уже в E5) |
| 7 | Ревизия планировалась к переименованию после релиза (`-draft` → `2026-XX`) | Каталог ревизии — сразу финальное имя `2026-08`; статус живёт в README, а не в имени (D19) |
