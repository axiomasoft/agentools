## 0. Рамка

`DR-01` §J9 разделил два артефакта: **опубликованная схема** (контракт провода, открытая) и
**схема авторинга** (закрытая, только для линтера). Отсюда два списка ключевых слов — **Список A**
(опубликованные схемы) и **Список B** (схемы авторинга), а не один.

Три правила, которым подчинены оба списка:

1. **Запрет требует факта ровно так же, как разрешение** (`DR-01` §E6). Каждая строка списков
   ниже несёт основание: либо конкретную строку матрицы §1 (проба + кандидат + вердикт), либо
   явную ссылку на замороженную норму `DR-01`. Оснований «на всякий случай» в списках нет.
2. **Провод терпим, строгость — у линтера** (`DR-01` §E3/§J9). Список A шире по тому, что он
   **допускает в документе** (неизвестные ключи и значения игнорируются); Список B добавляет
   ровно один механизм — закрытие, — и отвергает то, что провод обязан пережить.
3. **Потребитель схемы определяет критерий.** До этого решения предполагалось, что
   опубликованные схемы потребляет ещё и генератор кода (`DR-01` §J6). Вердикт §4 ниже этого
   потребителя снимает, и терпимость генераторов перестаёт быть ограничением списка A —
   кроме одной именованной строки (§2, `patternProperties`).

## 2. Список A — ключевые слова, разрешённые в **опубликованных схемах** ревизии `2026-08`

Потребитель: обе реализации SDK и любой сторонний клиент. Схема **открытая**: неизвестные ключи и
неизвестные значения перечислений игнорируются (`DR-01` §E3). Единственный рантайм-потребитель
после вердикта §4 — валидатор (`opis/json-schema` PHP, `json_schema` 5.2.2 Dart — пины D15).

| Ключевое слово / конструкция | Решение | Основание | Правило авторинга для фазы P3 |
|:--|:--|:--|:--|
| `$schema`, `$id`, `title`, `description`, `type`, `properties`, `required` | **разрешено** | базис корпуса: присутствуют во всех 10 пробах, ни одного отказа ни у одного кандидата | `description` не вводит норму (anti-regression D27) |
| `oneOf` + `const` + `pattern` | **разрешено, обязательная форма расширяемых словарей** | p01/wol-soft `ok`; p01/quicktype (оба языка) `ignored-gracefully` — деградирует форма типа, не документ | виды событий, категории ошибок, виды аудит-событий — только этой формой (`DR-01` §E2), голый `enum` для них запрещён |
| `enum` | **разрешено только для действительно закрытых множеств** | p06/wol-soft `ignored-gracefully` — `enum` разобран, деградировала условная логика, не перечисление | закрытым считается множество, расширение которого — намеренно ломающее изменение (`DR-01` §E7) |
| `allOf` | **разрешено** | p03/quicktype `ok` (allOf слит корректно, оба языка); p05/quicktype `ok` | композиция базовых типов — только `allOf`; закрытия на проводе нет (см. `unevaluatedProperties` ниже) |
| `$defs` + `$ref` внутри файла | **разрешено** | p05/quicktype `ok` (оба языка) | переиспользуемые подсхемы — в `$defs`, не копированием |
| `$ref` относительный на соседний файл | **разрешено** | p09/wol-soft `ok` (резолв по локальному файлу, без сети) | кросс-файловые `$ref` обязаны резолвиться офлайн (anti-regression D27: нерезолвимые `$ref` — дефект `2026-07-draft`) |
| `$ref` сетевой (`http(s)://`) | **запрещено** | норма `DR-01` §E5 (наследуется от MCP SEP-2106: запрет автодереференса сетевых `$ref`); в корпусе проб не проверялся — основание нормативное, не эмпирическое | `$id` остаётся URL-подобным идентификатором, но не адресом загрузки |
| `if` / `then` / `else` | **разрешено** | p06/wol-soft `ignored-gracefully` — конструкция **энфорсится корректно** (негативный тест: `kind=llm` без `prompt_ref` → исключение); p06/`json_schema_builder` валидирует корректно | условная форма сообщения выражается схемой, но MUST-правило обязано иметь идентификатор и вектор (`DR-01` §J2) — схема не единственный носитель нормы |
| `dependentSchemas` | **разрешено** | p06/`json_schema` 5.2.2 энфорсит из коробки (эмпирика P2.3: `FormatException: prop side_effect violated schema dependency`); p06/wol-soft не валидирует — но wol-soft после §4 не потребитель | то же ограничение, что для `if/then/else` |
| `patternProperties` | **разрешено для открытых map-объектов** — единственная строка, зависящая от решения владельца по §J6 (см. §6) | p08/wol-soft `ok` (валидация ключей по шаблону корректна, включая негативный тест); p08/`json_schema_builder` валидирует корректно. **Против:** p08/quicktype `field-lost` в ОБОИХ языках — все данные под ключевым словом теряются | применять только там, где множество ключей открыто по построению (расширения под vendor-префиксом `dev.agentools/`, `_meta`); там, где ключи известны — `properties` |
| `additionalProperties` со **схемой** (не `false`) | **разрешено** | p08 — открытые map-объекты нужны конструктивно; ни один кандидат не отказал на `additionalProperties` как схеме | предпочитать `patternProperties` там, где форма ключа нормируется |
| `additionalProperties: false` | **запрещено** | норма `DR-01` §E5/§J9 (провод не закрывается) **+ эмпирика:** round-trip `wol-soft` на p01/p02/p04/p06/p08/p09/p10 — REJECTED: закрытая схема отклоняет весь документ с неизвестным свойством, что прямо ломает must-ignore §E3 | ни во вложенных, ни в корневых опубликованных схемах |
| `unevaluatedProperties` | **запрещено** | норма `DR-01` §J9 (провод открыт) **+ эмпирика:** p03/wol-soft `ignored-gracefully` — в PHP-контуре закрытие было бы декларацией без энфорсмента, а в Dart (p03/`json_schema_builder`) — реальным, то есть закрытие вело бы себя РАЗНО в двух SDK | закрытие живёт только в схеме авторинга (Список B) |
| `$dynamicRef` / `$dynamicAnchor` | **запрещено** | p04/wol-soft `ignored-gracefully` (рекурсивная типизация потеряна) + p04/quicktype `ignored-gracefully` в обоих языках (`mixed[]` / `List<dynamic>`) **+** норма `DR-01` §E6: расширяемая рекурсия не имеет ни одного потребителя в ревизии | рекурсивные структуры (дерево шагов, вложенный контекст) — обычным `$ref` на `$defs` (p05 — путь подтверждён) |
| `prefixItems` (+ `items: false`) | **запрещено** | p07/wol-soft **`crash`** (`TypeError` на `items:false`) + p07/quicktype-php `field-lost` (tuple-семантика потеряна) + p07/quicktype-dart `ignored-gracefully` (длина и порядок потеряны) — три из трёх таргетов не сохраняют позиционную семантику | пары/кортежи выражаются объектом с именованными полями (`{algorithm, value}`), а не массивом фиксированной длины: позиционная форма несовместима с добавлением поля (`DR-01` §E7) |
| `items` (однородный массив), `minItems`, `maxItems` | **разрешено** | p07: отказы касались `items: false` и `prefixItems`, однородный `items` разобран всеми таргетами | — |
| `type: integer` / `type: number` | **разрешено, с правилом точности** | p10 — `ok` у всех трёх таргетов: `int`/`int`/`float`(`double`), точность сохранена побитово, включая `PHP_INT_MAX` | денежные и любые точные величины — **целое в минорных единицах**; `number` — только для заведомо неточных величин; запись в экспоненциальной форме в примерах и golden-файлах запрещена (взаимодействие с JCS, D5/`DR-01` §J7) |
| незнакомые/вендорные ключевые слова схемы (`x-…`) | **обязаны игнорироваться потребителем; вводятся только вместе с потребителем** | p02/wol-soft `ok` + p02/quicktype `ok` (оба языка) — вендорный ключ инертен для всех таргетов | норма `DR-01` §E6: собственное вендорное ключевое слово без названного потребителя в ревизию не вводится |

**Полнота.** Список покрывает все конструкции корпуса проб (p01–p10). Ключевые слова вне
корпуса, не влияющие на форму документа (числовые и строковые фасеты `minimum`, `maxLength`,
`format`, …), допускаются как валидационные фасеты; ключевое слово, меняющее **форму** документа
или его расширяемость, вводится правкой этого решения, а не по месту в фазе P3.

## 3. Список B — ключевые слова, разрешённые в **схемах авторинга**

Потребитель — **только линтер спеки** (`DR-01` §J9, слой 1 гейта CI §J5). Генераторы кода
потребителями этих схем не являются ни при каком исходе §6, поэтому терпимость генераторов к
Списку B неприменима по построению. Схема авторинга — закрытый вариант тех же схем, против
которого прогоняются фикстуры и примеры спеки.

| Ключевое слово | Решение | Основание |
|:--|:--|:--|
| всё, что разрешено Списком A | **разрешено** | Список B — тот же материал плюс закрытие |
| `unevaluatedProperties: false` на внешнем уровне композиции | **разрешено — это и есть механизм закрытия** | норма `DR-01` §E5 (закрытие только на внешнем уровне композиции) + эмпирика p03/`json_schema_builder`: конструкция реально энфорсится валидатором (`unknown-key.json` → «Schema is false»), то есть закрытие проверяемо, а не декларативно |
| `additionalProperties: false` | **разрешено только в листовых подсхемах без `allOf`/`$ref`** | норма `DR-01` §E5 (антипаттерн именно во вложенных и переиспользуемых подсхемах); там, где композиции нет, конструкция эквивалентна закрытию и дешевле |
| неизвестный ключ **документа** (фикстуры, примеры) | **ошибка линтера** | назначение Списка B (`DR-01` §J9): ловить опечатки в наших же векторах; ровно этот случай — вектор conformance §J9 «принимается реализациями, отвергается линтером» |
| незарегистрированное вендорное ключевое слово в НАШЕЙ схеме | **ошибка линтера** | норма `DR-01` §E6: на проводе такой ключ обязан игнорироваться (Список A), но в собственном артефакте он — опечатка, пока не заявлен потребитель |
| `$dynamicRef`/`$dynamicAnchor`, `prefixItems`, сетевой `$ref` | **запрещено** (зеркало Списка A) | схема авторинга закрывает те же схемы; конструкция, запрещённая на проводе, не может появиться в её закрытом варианте |

**Отношение списков.** `B = A ∪ {закрытие}`. По ключевым словам Список B на одну позицию шире;
по **принимаемым документам** шире Список A — он обязан пережить то, что Список B отвергает.
Именно это распределение требует `DR-01` §E3/§J9: терпимость — на проводе, строгость — у линтера.

**Именованный остаток.** Энфорсмент `unevaluatedProperties` подтверждён эмпирически только на
Dart-стороне (`json_schema_builder` 0.1.6, `json_schema` 5.2.2). Валидатор, которым будет
исполнен линтер (`opis/json-schema`, пин D15 — либо иной инструмент слоя 1 CI), корпусом проб не
прогонялся: корпус P2.1 целил в генераторы, не в валидаторы. См. триггер T-2 в §7.

## 4. Роль кодогенерации по языкам

Вопрос ставится так, как его задаёт Scope item'а: по каждому языку — «каркас типов из схем» либо
«DTO руками», плюс чем гарантируется свежесть.

### PHP — **DTO руками**

Основания (все — строки матрицы §1, ни одно не взято из документации кандидата):

- `wol-soft` 0.26.2 даёт **`crash` на p05** (`$defs` + `$ref` + `allOf`) — это не экзотика, а
  базовая композиция, на которой построены `DR-01` §E2 (открытые перечисления) и §E5 (композиция
  вместо закрытия). Генератор, падающий на несущей конструкции ревизии, непригоден как источник
  каркаса типов. Второй `crash` (p07) снят запретом `prefixItems`, первый — нет.
- `quicktype --lang php` 26.0.0 переживает корпус без падений, но: `field-lost` на **p08**
  (класс-носитель `patternProperties` сгенерирован пустым — теряются все данные уровня) и
  `field-lost` на **p07**; кроме того, round-trip на всех пробах молча теряет неизвестное
  свойство — то есть сгенерированный тип **структурно несовместим** с требованием `DR-01` §E3
  «сырое событие сохраняется целиком, без потерь». Ручной raw-preserving слой поверх генерации
  всё равно обязателен.
- Цена альтернативы измерена, а не оценена (контрольная точка D32, якорь `b803d53`): **111 строк
  на 3 типа** (~37 строк/тип) с полной валидацией, включая `dependentSchemas`, которую не
  реализовал ни один из четырёх прогнанных генераторов.

### Dart — **DTO руками**

- Зрелого schema-first генератора нет: `json_schema_builder` 0.1.6 — валидатор без generate-API
  (проверено по экспортам пакета, а не по README), `not-supported`×10 как кандидат-генератор.
- `quicktype --lang dart` 26.0.0 — тот же класс деградации, что в PHP: `field-lost` на p08,
  потеря условной семантики на p06, round-trip теряет неизвестное свойство.
- Цена измерена (D32, якорь `b3f164f`): **87 строк на 3 типа** (~29 строк/тип) при делегировании
  валидации пину `json_schema` 5.2.2 — на 24 % дешевле PHP-пути, потому что библиотека энфорсит и
  `if/then/else`, и `dependentSchemas` из коробки.

  **Поправка 2026-07-27 (P3.15, аудит F8):** 87 против 111 — это −21,6 %, не 24 %.

### Свежесть

Генерируемых артефактов не остаётся ни в одном языке, поэтому слой 2 четырёхслойного гейта CI
(`DR-01` §J5 — «свежесть кодогенерации: перегенерировать → diff должен быть пуст») теряет
предмет. **Предлагаемая замена** (решение — за владельцем, §6): слой 2 переопределяется как
**свежесть ручных DTO** — детерминированная структурная сверка «поле опубликованной схемы ↔ поле
типа SDK» в обоих языках (множество `properties` схемы против множества полей типа; расхождение —
красный CI). Семантический дрейф при этом уже покрыт независимо: traceability правило ↔ вектор
(`DR-01` §J2, механика D26) и GREASE-векторы (§E4).

## 5. Транспорт Dart

**Решение: `mcp_dart`.** Переносится из `findings/P2-dart-transport.md` (P2.4, якорь `4344265`)
без изменения формулировки вердикта; здесь оно становится решением плана.

Опорные факты прогона (мок-сервер с фиксированными фикстурами, симметричный сценарий
`server/discover` + `tools/call` на обоих вариантах):

- `McpClientOptions(protocol: McpProtocol.require2026)` → клиент шлёт **ровно** `server/discover`,
  `initialize` не вызывается ни разу (лог мока за весь прогон — 2 метода). Соответствие директиве
  D20 подтверждено наблюдением, а не README.
- Инъекция per-request `_meta` (`protocolVersion`/`clientInfo`/`clientCapabilities`) подтверждена
  эмпирически в обоих запросах; `resultType` энфорсится клиентом (первый прогон упал на фикстуре
  без поля); `input_required` — первоклассный `TaskStatus.inputRequired` публичного API.
- Тонкий клиент воспроизводит тот же двухвызовой сценарий в **2.3× большем объёме кода**
  (60 строк против 26) — и это минимальный сценарий; полный набор методов протокола увеличил бы
  разрыв кратно.
- Риск принят явно: версия — prerelease `2.3.0-dev.3` (MIT, та же лицензия, что stable 2.2.2);
  27 файлов пакета содержат dual-era код, но под `require2026` он не исполняется (0 legacy-запросов
  в логе мока). Директива D20 адресована нашей кодовой базе, не байтам зависимости.

Триггер ре-проверки — T-1 в §7.

## 6. Конфликт с `DR-01` §J6 / §J5 слой 2 — требуется решение владельца

Вердикт §4 не нарушает потолок §J6 («кодогенерация — только каркас типов, не источник
валидации»): использовать меньше разрешённого — не нарушение. Но он **снимает предмет** у двух
мест `DR-01`:

1. **Посылка §J6** — «генерация из схем даёт DTO и заглушки перечислений» — перестаёт
   выполняться: генерации нет ни в одном языке.
2. **§J5, слой 2** четырёхслойного гейта CI («свежесть кодогенерации: перегенерировать → diff
   должен быть пуст») остаётся без артефакта, то есть гейт де-факто становится трёхслойным.

Правка `DR-01` этим планом запрещена (`plan.md` §2 Execution Rules; Code Guidance item'а P2.5).
Ниже — **предложение**, а не решение; trigger эскалации — «конфликт правил».

**Предложение владельцу.** Новая D-запись со `supersedes` на посылку §J6 и на §J5 слой 2:

- потолок §J6 сохраняется дословно и не переоткрывается;
- роль кодогенерации в обоих языках — «DTO руками» (§4);
- слой 2 CI переопределяется как «свежесть ручных DTO» — структурная сверка схема ↔ тип (§4,
  «Свежесть»);
- второе следствие §J6 — запрет экзотических ключевых слов «до проведения bakeoff» — исполнено и
  закрыто: bakeoff проведён, запрет заменён Списками A и B (§2, §3).

**Альтернатива, если владелец сохраняет кодогенерацию.** Единственный переживший корпус кандидат —
`quicktype` 26.0.0 (оба языка). Цена: (а) Node-зависимость в CI обоих SDK — против D6 («нулевая
Node-зависимость»); (б) **`patternProperties` придётся перенести из Списка A в запрет** (p08:
оба таргета quicktype теряют все данные под этим ключевым словом) — открытые map-объекты
пришлось бы выражать иначе; (в) ручной raw-preserving слой поверх сгенерированных DTO всё равно
обязателен (round-trip теряет неизвестное свойство на всех пробах), то есть §E3 пишется руками в
любом случае. Пересмотр по этой ветке затрагивает **одну строку** Списка A, а не решение целиком.
