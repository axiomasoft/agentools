## 1. Почему прежняя форма не исполнима

В приложении Gate B у P4.10 есть **67** точных строк `FAIL F1/F2/F4` на **13** sole-carrier id;
`longop-002` — четырнадцатый исходный behavior-carrier, названный в F2, но его правила имеют
другие PASS-carriers. Текущий candidate добавил по одной positive pair к каждому исходному id,
однако сохранил до восьми независимых `spec_rule_ids` в одном negative. Это снова позволяет
одному реально проверенному predicate выдавать покрытие всем соседним правилам. Например,
`audit-004/104` различает только лимит baggage `AOB-31`, но заявляет `AOB-25…AOB-31`;
`confpolicy-001/101` различает повторную авторизацию `CNF-35/36`, но заявляет также
`TLP-11`, `CNF-3…6` и `CNF-8`. Зеленые `fixtures-check` и full lint проверяют форму и
traceability, а не эту различающую силу. `RAG:— (repo-grounded: artifacts/P5-gate-b.md
матрица/F1/F2/F4; git diff + fixtures-check/full lint 2026-08-04)`.

Два правила из 67 вообще не являются behavior-предметом:

- `SEC-17` запрещает **автору ревизии** фиксировать claim-схему делегирования;
- `AOB-26` запрещает именам внешнего telemetry-словаря попадать в schema/rules ревизии.

Отсутствие поля в одном runtime-event не доказывает ни один из этих запретов. Их честный носитель
— artifact/static pair, поэтому D156 передаёт их P4.12. `RAG:— (repo-grounded:
spec/revisions/2026-08/10_security.md:155-159; 08_audit-observability.md:206-209)`.

## 2. Канон P4.10: одна FAIL-норма — одна negative/positive pair

P4.10 принимает **65** behavior-строк round 1 (67 минус `SEC-17`/`AOB-26`). Для каждой строки:

1. negative fixture содержит ровно один `spec_rule_ids` — свой rule id;
2. positive fixture имеет тот же единственный rule id и id negative + 100;
3. pair отличается ровно одним формальным stimulus (либо одним значением уже формального
   stimulus); косметическая разница, иной title или простая смена `expect` не считается;
4. oracle адресен: конкретный error/event/payload/tool-call/absence assertion, который
   переворачивается при counterfactual mutation;
5. `rule_evidence` явно хранит JSON Pointer stimulus/oracle, формулировку mutation и pair ids.

Это намеренно более строгая гранулярность, чем допускает формат: экономия fixtures уже дала
ложный A3 и RED Gate B. Группировка нескольких round-1 FAIL rules в одной pair запрещена даже
если они тематически близки. `RAG:— (repo-grounded: artifacts/P5-gate-b.md §Линза 3;
plan-protocol code-guidance pattern «анти-подгонка»)`.

## 5. Машинный контракт workflow

Результат автора P4.10 обязан вернуть `rule_evidence` ровно для exact-set из 65 ids. Каждая
строка содержит `rule_id`, `source_carrier`, `negative`, `positive`, `stimulus_pointer`,
`oracle_pointer`, `counterfactual`; дубликат/пропуск/чужой id блокирует review. Отдельная запись
`retained_carriers` описывает `longop-002/102`, но не увеличивает 65. Reviewer проверяет
нормативный текст каждого id, а closer закрывает item только после точного set equality и общих
joined-tree gates. Evidence остаётся в структурированном результате W2 и переносится в
Completion Notes; терминальный единый manifest выпускает P4.13, второго канонического файла не
создаётся.

Чтобы единственная fix-итерация оставалась исполнимой, carrier делит P4.10 на пять
file-disjoint shards: `security`, `confirmation`, `lifecycle`, `audit`, `dialog`. Они параллельно
возвращают ту же schema только для собственных rule/file sets; детерминированный join объединяет
их в один P4.10 result, а единый cold-start reviewer проверяет exact 65/65. При Major/Blocker
fix повторяет те же пять shards, после чего разрешён только один общий re-review. Пересечения
write-set между shards, частичный aggregate и shard-local «APPROVE» запрещены.

Resume D155 сохраняет candidate как вход: read-only reconstruction по тем же пяти shards не
объявляет broad pairs годными; общий review выдаёт Major, единственная sharded fix-итерация
нормализует их по таблице выше. Ни reset, ни fresh-authoring, ни молчаливое сохранение broad
`spec_rule_ids` не разрешены.

## 6. DoR-вердикт

- exact вход: 14 behavior source carriers, включая F2-only `longop-002`;
- exact предмет: 65 behavior FAIL rules + 2 static rules, переданные P4.12;
- выходная cardinality не выводится из исторических `27`/`32`: P4.10 производит 65 pairs и
  одну retained F2 pair; P4.12 производит ещё две static pairs;
- базовые gates (`fixtures-check`, full lint, `git diff --check`) обязательны, но закрытие
  дополнительно требует exact `rule_evidence` и cold-start review;
- открытых design-вопросов не осталось; нормативный текст и старые terminal items не меняются.
