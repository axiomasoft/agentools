### P2.1 — Заморозить confirmation-security contract, migration и adversarial cases

**Intent:** Выпустить versioned P2 contract, который задаёт поддерживаемую safe boundary, точный binding tuple, ordering проверок, отказоустойчивые error semantics, staged migration и общий набор PHP/Dart adversarial cases.
**Why:** Current `ConfirmationProtocol::commit` принимает caller-controlled `principal`, `now`, `CommitAuthorizer`, descriptor, `proposerId` и `dualControl`; `DecisionAudit` проверяет hashes, но не связывает собственные `proposalId`, `token` и actor с разобранным token. Локальный null-check не устраняет bypass class. `RAG:—`; внешние ограничения — `research/P2-design-rag.md`.
**Scope Included:** Supported vs expert API boundary; trusted/partially-trusted roles; prepare/commit input contract; authoritative binding tuple; pre-presentation vs post-presentation validation ordering; policy missing/change/downgrade behavior; distinct approver/quorum rules; stable safe external errors and internal evidence requirements; PHP/Dart compatibility stages; machine-readable positive/negative case IDs.
**Scope Excluded:** Runtime implementation; token field layout/crypto; durable consume/DDL; event store; editing `spec/revisions/2026-08/**`; deciding final PHP namespace/Dart barrel removals; production adapters.

**Implementation Rules:** Contract distinguishes authenticated actor, proposer, commit principal and counted approvers. The binding tuple contains tenant, proposal id/version, action id, tool/action, arguments fingerprint, descriptor digest, policy id/revision, approval requirement, commit principal and expiry; raw token bytes are never an audit/log identifier. Per-call caller cannot provide clock, actor, descriptor, policy mode/revision, approval evidence, authorizer or dual-control flag. Missing/unknown/stale/mismatched trusted data denies. Four-eyes/quorum is policy-selected and organization-defined, not claimed as universal OWASP/NIST law. Pre-presentation structural/binding failures and post-presentation current-authorization outcomes are separate; P3 owns atomic consume semantics. Existing `2026-08` remains byte-identical.
**Code Guidance:** Manifest `schema_version=confirmation-security-cases/v1` has unique stable case IDs, phase (`prepare|commit`), expected semantic code/category, PHP/Dart applicability and named trust seam. Include at least: caller policy/clock/actor/descriptor/authorizer injection absent; null/same proposer; cross-tenant resource; policy missing/downgraded/changed; approval wrong proposal/version/args/descriptor/policy, duplicate approver, insufficient quorum, revoked/expired approval; authorization revoked; redacted denial. Migration inventory names every direct `ConfirmationProtocol`/`CommitAuthorizer` consumer and one P2/P7 disposition.
**Validation:** `python3 -m json.tool fixtures/hardening/confirmation-security-v1.json`; independent stdlib check proves unique nonempty IDs, closed phases/categories, required seam and exact minimum bypass set; every contract refusal maps to one manifest case and stable semantic code; migration inventory covers all PHP/Dart production/reference imports and barrel/PSR-4 reachability; `git diff --exit-code -- spec/revisions/2026-08`; primary-source links and `[RAG:✅]` claims resolve; plan lint adds no ERROR.
**Deliverables:** Normative confirmation-security contract; complete migration/consumer inventory; shared adversarial case manifest consumed by P2.2–P2.4 and later P6/P8.
