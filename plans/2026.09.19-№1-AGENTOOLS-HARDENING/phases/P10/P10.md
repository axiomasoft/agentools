# P10 — Production-grade release acceptance и owner gate

## Phase Context

P10 принимает один exact private release candidate, а не добавляет runtime-функции. Фаза
сводит P1–P9 contracts/receipts в release-acceptance matrix, приводит документацию к
фактическим guarantees и package surfaces, повторяет documented flows только из P9 subjects,
адъюдицирует residual risk и выпускает private-RC acceptance плюс G-RELEASE decision packet.
Технический PASS private candidate и разрешение внешней публикации — независимые оси.

> **Контракт фазы (contract-first).** Потребляет: terminal digest-qualified evidence P1–P9,
> exact P9 subjects и current proprietary/private identity. Производит:
> `release-acceptance-v1`, truthful docs, clean-consumer/migration receipts, final dossier,
> private-RC acceptance и non-authorizing G-RELEASE packet. Граница: P10 не публикует tag,
> GitHub release или registry version и не создаёт owner consent.

> **Phase Assurance | v1.**
> Impact: security-external
> Integration Seams: guarantee-receipts · public-docs · exact-rc-consumers · migrations-recovery · release-governance
> Live or Irreversible: no
> Audit Intent: direct-close-eligible
> Rationale: exact claim-to-evidence join, artifact-only consumers and split private/public verdict prevent a green technical dossier from minting publication authority; Review=full.

## DoR (Definition of Ready)

- [ ] P1–P9 terminal receipts and their declared producer outputs are digest-verifiable.
- [ ] P9.5 identifies the exact three private subjects and preserves hosted-capability states.
- [ ] P1 support/guarantee/resource contracts and all P6–P9 residual handoffs are current.
- [ ] Current legal/package identity is treated as proprietary/private; D5 remains owner-owned.
- [ ] No item needs publication credentials or G-RELEASE to prove private-RC fitness.

## Dependencies

`P1–P9 -> P10.1 -> P10.2 -> P10.3 -> P10.4 -> P10.5`. P10.1 exact-joins
upstream evidence without redefining it. P10.3 consumes only P9 subjects plus P10.2 docs.
P10.5 may close private acceptance while public eligibility remains `not-authorized` or
`blocked`; it cannot convert either state into publication consent.

## Execution Contours

- `release-truth`: P10.1–P10.2 share the guarantee/support/API inventory and turn it into one
  contract plus one truthful documentation surface.
- `acceptance-evidence`: P10.3–P10.4 share immutable P9 subjects and consumer evidence, but keep
  execution transcripts separate from judgement/residual-risk aggregation.
- `solo`: P10.5 waits for immutable child receipts and independently verifies the final packet;
  reuse before the dossier stabilizes would admit stale digests.

## Scope Excluded

New runtime behavior; changing upstream contracts to make acceptance green; public Packagist/pub.dev
upload; Git tag/GitHub release; publication credentials; license/legal-identity choice; pretending
the path-dependent Dart MCP companion is pub.dev-ready; replacing unavailable hosted evidence with
local claims; reopening frozen AGENTOOLS or `2026-08` history.

## Validation

Every advertised guarantee and non-guarantee has one current upstream owner and digest-qualified
evidence; stale/missing/extra claims are red. Public docs compile against exact P9 subjects and do
not leak phase/reference internals or overstate MCP/attestation/exactly-once claims. Clean PHP,
Dart-core and paired-private Dart-MCP consumers run without workspace source imports; migration,
rollback/recovery and revocation instructions are rehearsed in disposable environments. Private
acceptance requires zero unresolved private-release blocker. Public eligibility is a separate exact
set and remains non-authorized until D5 and `[OWNER-GATE:G-RELEASE]` bind exact identities, channels,
version/tag and subject digests. Validation proves no tag, release, upload, credential use or live
repository-setting mutation occurred.

## Phase Handoff

On GREEN, PLAN1 has a reproducible accepted private RC, truthful support/migration documentation,
an auditable residual-risk dossier and a decision-ready G-RELEASE packet. Optional public release
is new owner-authorized execution scope; it is not silently appended to this phase or inferred from
private acceptance.
