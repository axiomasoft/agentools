### P10.3 — Перепроверить exact RC в clean consumers и отрепетировать migration/recovery paths

**Intent:** Установить exact P9 subjects в isolated consumers, выполнить только P10.2 documented flows и доказать migration/recovery behavior without workspace or publication shortcuts.
**Why:** P7 proves package boundaries and P9 proves subject bytes, but neither proves that final documentation, support matrix and operational guidance work together against those same accepted bytes. `RAG:—`.
**Scope Included:** Independent re-hash of PHP, Dart core and paired-private Dart MCP subjects; disposable no-source consumers; documented install/configure/safe-confirmation flows; supported runtime rows selected by P1; package/API/doc manifest equality; ephemeral PostgreSQL schema install and representative upgrade/recovery drills; backup/restore and token/key/revocation procedures; raw transcripts and exact environment fingerprints.
**Scope Excluded:** Rebuilding or modifying candidate subjects; public registry resolution; production database access; destructive owner data migration; general framework integration; adding APIs to satisfy examples; interpreting private-paired MCP as pub.dev-ready.
**Inputs:** P9.3 exact subjects/content manifests/checksums · P9.4 supply-chain evidence · P9.5 aggregate receipt · P10.1 matrix · P10.2 docs/receipt · P1 support matrix · P3–P5 SQL/contracts · P7 package manifest · P8 storage/resource receipts.
**Files:** `consumers/release/php/**` · `consumers/release/dart/**` · `consumers/release/dart_mcp/**` · `consumers/release/postgres/**` · `tools/release_consumer_gate.py` · `tests/tools/test_release_consumer_gate.py` · `plans/2026.09.19-№1-AGENTOOLS-HARDENING/artifacts/P10-consumer-acceptance.json` · `plans/2026.09.19-№1-AGENTOOLS-HARDENING/findings/P10-consumer-acceptance.md`.
**Required Reads:** 1) P9.3–P9.5 contracts/subjects/receipts 2) P10.1 acceptance matrix 3) P10.2 exact documentation and snippet manifest 4) P1 support/compatibility contract 5) P3–P5 schema, cleanup, key/revocation and recovery contracts 6) P7.4 package/consumer receipt 7) P8.4/P8.5 storage/resource receipts.
**Implementation Rules:** Re-hash downloaded/staged subjects before extraction; reject any byte not named by P9. Consumers live under validated temporary roots and cannot read repository product paths after staging. PHP installs production dependencies without root dev autoload. Dart core imports supported libraries only. Dart MCP consumes a staged paired artifact and retains `public-release-blocked`. Use separate PostgreSQL processes/connections where concurrency matters and disposable namespaces only. Migration/recovery drills follow docs verbatim, preserve raw commands/exit codes and clean only validated temporary resources. A failed documented flow returns to its owning P10.2 or upstream item; consumer fixtures are not patched around product defects.
**Code Guidance:** One orchestrator may create isolated roots, caches and database namespaces but must print each native command. Add path/network/workspace sentinels and negative fixtures for digest mismatch, forbidden source import, stale snippet, missing backup, unsafe cleanup and MCP hosted-resolution substitution. Separate artifact identity from environment/runtime identity in receipts.
**Validation:** All three subjects match P9 digests and content manifests; PHP, Dart core and paired MCP clean consumers install/analyze/test and run documented minimal scenarios with no repository source/path/git dependency; every selected support row is exercised or explicitly bound to current P9 matrix evidence; PostgreSQL install/upgrade/recovery/revocation drills pass in disposable namespaces with observable state; injected wrong digest/source import/stale doc/unsafe cleanup turns red; cleanup leaves no owned temp/database residue; no registry/tag/release/settings mutation occurs; plan lint adds no ERROR.
**Deliverables:** Artifact-only consumer fixtures, migration/recovery transcripts, environment fingerprints and digest-qualified P10 consumer-acceptance receipt.
