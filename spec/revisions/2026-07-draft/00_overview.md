# 00 — Overview, глоссарий, уровни соответствия

> Ревизия спеки: `2026-07-draft` (см. `README.md`). Статус: draft.
> Нормативные ключевые слова — по [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)
> (MUST / SHOULD / MAY). Базис wire-протокола — MCP, ревизия
> [2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools).

Документ — **точка входа** в спецификацию AgenTools: назначение пакета, единый глоссарий,
конвенция нормативных слов, уровни соответствия (conformance) и нормативная таблица единой
модели побочного эффекта. Он **не вводит новых требований** — только фиксирует и увязывает
уже нормированное в документах `01_tool-contract-profile.md`–`06_idempotency-errors.md`.
Термины и правила, на которые ссылается обзор, определены в соответствующих документах;
колонка «Нормирован в» глоссария указывает точное место.

## 1. Назначение

AgenTools — языконезависимый слой **agent + tools + сценарии** поверх Model Context
Protocol. Пакет описывает, как из команды сотрудника (написанной или наговоренной)
рождается намерение, как оно разворачивается в вызовы доменных инструментов с
интерактивными уточнениями, превью и подтверждением перед записью, и как всё это
протоколируется в аудит. Ценность пакета — не ещё один рантайм, а **общий договор
семантики**: то, чего в «голом» MCP нет — жизненный цикл действия, two-phase подтверждение,
декларативные сценарии, таксономия аудита, идемпотентность и единая модель ошибок.

Спецификация состоит из нормативного текста (правила `MUST`/`SHOULD`/`MAY`, привязанные к
пронумерованным маркерам), JSON Schema 2020-12 к каждому документу и языконезависимых
тест-векторов (`fixtures/`). Тест-векторы — исполняемая часть договора: две независимые
реализации (PHP и Dart) проверяются одним и тем же набором и потому не расходятся «по
смыслу». Каноническая сериализация RFC 8785 (JCS, `05_audit-events.md` §4) гарантирует, что
разные языки дают **байт-в-байт** одинаковый вывод там, где это критично (golden-сравнения,
ключи идемпотентности).

Спека **транспорт- и продукт-нейтральна**. Она не называет конкретные приложения и не
предполагает конкретное хранилище: состояние сессии — детерминированная свёртка
append-only лога, персистентность — дело потребителя. Конкретные потребители спеки и
разграничение «кто что реализует» вынесены в информативное Приложение A; в нормативной
части имён продуктов нет.

## 2. Конвенция нормативных слов (RFC 2119)

Ключевые слова **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, **MAY** трактуются по
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) и приводятся по-английски даже в русском
тексте. Каждое нормативное правило несёт стабильный маркер вида `XX-n` (`TCP-`, `LC-`,
`CP-`, `SC-`, `AU-`, `IE-`; переходы FSM — `LC-Tn`), на который ссылаются другие документы и
тест-векторы (`fixtures/*/spec_refs`). Идентификаторы, имена полей и значения перечислений —
по-английски; человекочитаемый текст (сообщения, описания) — по-русски.

## 3. Глоссарий

Определения — краткие; полная нормативная формулировка — в документе из колонки
«Нормирован в». Термины перечислены в порядке появления в потоке действия.

| Термин | Определение | Нормирован в |
|:--|:--|:--|
| **Tool** (инструмент) | MCP-tool ревизии 2025-11-25, удовлетворяющий профилю AgenTools (имя, аннотации, `_meta`). Пишется один раз и обслуживает MCP-сервер и внутренний agent-loop. | `01`/TCP-1 |
| **Tool Descriptor** | Дескриптор инструмента: `name`/`title`/`description`/`inputSchema`/`outputSchema`/`annotations` + блок `_meta["agentools/v1"]`. | `01`/TCP-11, `schema/tool-descriptor.json` |
| **side_effect** | Класс побочного эффекта инструмента: `read` \| `draft` \| `write` \| `irreversible`. Единый источник перечисления. | `01`/TCP-11, `schema/side-effect.json` |
| **confirmation** | Политика гейта подтверждения: `none` \| `confirm` \| `double_confirm`. Дефолт выводится из `side_effect` (§6). | `01`/TCP-12, `schema/side-effect.json` |
| **prepare / commit** | Две фазы write-инструмента под одним `name`: prepare (без `confirmation_token`) считает превью и не пишет; commit (с токеном) применяет изменения. | `01`/TCP-16, `03`/CP-2, CP-3 |
| **confirmation_token** | Непрозрачный одноразовый токен (≥128 бит, TTL), привязанный к `(session_id, step_id, preview_digest)`; отличает commit от prepare. | `01`/TCP-18, `03`/CP-5, CP-7 |
| **Preview** | Детерминированное превью write-действия: `{title, summary, diff?, warnings?}`, возвращается на фазе prepare. | `03`/CP-9, `schema/confirmation.json` |
| **preview_digest / args_digest** | Один и тот же `sha256(JCS(args))` над доменными аргументами превью: на проводе — `preview_digest`, в персисте `PendingAction` — `args_digest`. | `01`/TCP-17, `03`/CP-7 |
| **PendingAction** | Запись рантайма об отложенном (ожидающем подтверждения) действии: `{token, session_id, step_id, tool, args_digest, preview, status, …}`. | `03`/CP-2, `schema/confirmation.json` |
| **Decision** | Решение пользователя по гейту: `accept` \| `decline` \| `edit` \| `revoke` (+ истечение — авто-decline). | `03` §4, `schema/confirmation.json` |
| **double_confirm** | Гейт из **двух** последовательных подтверждений (второе — с явным подтверждающим вводом), для `side_effect = irreversible`. | `01`/TCP-13, `03`/CP-20 |
| **ClarificationRequest / ClarificationAnswer** | Транспорт-агностичные объекты уточняющего вопроса и ответа: `kind ∈ {confirm, select, multi_select, text}`. | `03`/CP-24, CP-26, `schema/clarification.json` |
| **Session** (сессия) | Единица исполнения действия; находится ровно в одном из десяти состояний FSM. | `02`/LC-1 |
| **Event Log** | Append-only лог событий сессии — источник истины и аудит одновременно. | `02`/LC-8, LC-19 |
| **seq** | Монотонный (с 1, без дыр) порядковый номер события в пределах сессии. | `02`/LC-6 |
| **actor** | Автор события: `{type ∈ {user, agent, system}, id}`. | `02`/LC-5, `schema/lifecycle-event.json` |
| **Fold** (свёртка) | Детерминированное вычисление состояния сессии из её лога; одинаковый лог ⇒ одинаковое состояние на PHP и Dart. | `02`/LC-4 |
| **Checkpoint** | Пара `(session_id, seq)` — точка, из которой сессия может «висеть» и продолжиться. | `02`/LC-15 |
| **Resume Token** | Непрозрачная строка, кодирующая чекпоинт; возобновление = replay лога до `seq` + продолжение. | `02`/LC-16 |
| **Scenario** (сценарий) | Декларативная цепочка шагов `<ns>.<name>@<int>`, интерпретируемая обоими рантаймами. | `04`/SC-1, `schema/scenario.json` |
| **Step** (шаг) | Элемент сценария: `kind ∈ {llm, tool, elicitation}` + маршруты отказа, `when`, `input_map` и т.д. | `04`/SC-3 |
| **input_map / output_bind** | Отображение аргументов шага из выражений; имя, под которым результат шага доступен последующим. | `04`/SC-5, SC-8 |
| **Failure route** | Маршрут отказа шага `on_semantic_fail`/`on_technical_fail` ∈ `{abort, continue, retry(n)}`. | `04`/SC-15, SC-18 |
| **Compensation** (saga) | Идемпотентный откат write-шага; исполняется в обратном порядке при `abort`. | `04`/SC-20…SC-23 |
| **Expression** | Закрытая грамматика условий/маппингов: `$ctx`/`$steps`, литералы, `== != && \|\| !`, `missing()`. | `schema/expression.md`, `04`/SC-26…SC-31 |
| **Audit Event** | Событие таксономии аудита (13 `kind`), делит конверт и лог с lifecycle-событиями, но не меняет состояние FSM. | `05`/AU-1…AU-4 |
| **JCS / канонизация** | Каноническая сериализация JSON по RFC 8785 — фундамент golden-сравнений и ключей идемпотентности. | `05`/AU-17 |
| **Golden-файл** | Эталон канонизации: JCS-строка UTF-8 + ровно один завершающий `\n`; сравнение байт-в-байт. | `05`/AU-18 |
| **Idempotency Key** | `at1:` + `sha256hex(JCS({tenant_id, session_id, step_id, tool, args}))` — ключ дедупликации commit. | `06`/IE-1 |
| **Dedupe-запись** | Запись хранилища идемпотентности `{key, status ∈ {in_flight, done, failed}, result_digest?, stored_result?, ts}`. | `06`/IE-5 |
| **Error object** | Единый объект ошибки `{code, category, retryable, message, details?, example_of_valid_call?}`. | `06`/IE-10, IE-11 |

## 5. Уровни соответствия (conformance)

**Уровни L1/L2/L3 (D7 плана `AGENTOOLS`)** позволяют SDK заявлять зрелость независимо (паттерн
MCP SDK-тиров): реализация может быть полной на L1 и частичной на L2/L3, не теряя interop на
общем ядре. Уровни **накопительны**: L2 включает L1, L3 включает L2. Каждый тест-вектор несёт
`conformance_level` (`fixtures/README.md` §1), фиксируя уровень, на котором он обязателен.

| Уровень | Название | Что покрывает (нормативно) |
|:--|:--|:--|
| **L1** | Core | Профиль инструмента (`01`, все `TCP-*`); жизненный цикл (`02`, все `LC-*`, `LC-T*`); подтверждение одиночным гейтом `confirm` и clarification (`03`, `CP-1…CP-19`, `CP-21…CP-31`); идемпотентность и модель ошибок (`06`, все `IE-*`); канонизация JCS и конверт аудита (`05`, `AU-1…AU-19`, `AU-21`). |
| **L2** | Scenario | Всё из L1 + декларативные сценарии, выражения и маршруты отказа (`04`, `SC-1…SC-19`, `SC-24…SC-31`); аудит шагов сценария (`05`: `plan_created`, `step_started`, `step_skipped`). |
| **L3** | Full | Всё из L2 + двойное подтверждение `double_confirm` (`03`/CP-20, `01`/TCP-13); saga-компенсации (`04`/SC-20…SC-23) и их аудит (`05`: `compensation_executed`); url-mode elicitation (зарезервирован; детализируется в последующей ревизии). |

Разбиение согласовано с распределением тест-векторов (`fixtures/README.md` §4): L1-векторы
покрывают lifecycle / confirmation / idempotency / clarification / permission; L2 — сценарии;
L3-векторы (url-elicitation, `double_confirm`, исполнение компенсаций) пишутся в фазе P1 при
готовом conformance-runner'е.

## 6. Единая модель side_effect ↔ confirmation ↔ stake ↔ Tier

Таблица примиряет термины двух контуров экосистемы (D7 мастер-плана): один и тот же класс
действия называется stake-уровнем в одном контуре и Tier-уровнем в другом. **Нормативны**
для адаптеров колонки `side_effect` → `confirmation` (дефолт гейта); колонки `stake` и `Tier`
— **алиасы**, которые адаптер MUST принимать как эквивалентные соответствующему `side_effect`.
Источник перечислений и дефолтов — `schema/side-effect.json` (`x-default-confirmation`,
`x-d7-mapping`).

| `side_effect` | `confirmation` (дефолт) | Flex stake (алиас) | Axioma Tier (алиас) | Смысл |
|:--|:--|:--|:--|:--|
| `read` | `none` | low | 0 | только чтение |
| `draft` | `none` | — | 1 | запись черновика без постинга |
| `write` | `confirm` | med \| high | 2 | обратимая операционная запись |
| `irreversible` | `double_confirm` | — | — | необратимое действие (внешний платёж, отправка, необратимая проводка) |

Правила применения таблицы:

- Дефолт `confirmation` выводится из `side_effect`, если инструмент не объявил `confirmation`
  явно (`01`/TCP-12).
- Явный `confirmation` MAY **ужесточить** политику, но для `irreversible` ослабление
  (`confirm`/`none`) запрещено (`01`/TCP-13).
- Прочерк (`—`) означает, что D7 не задаёт алиас для этой строки в данном контуре; адаптер
  этого контура маппит такую строку на ближайший имеющийся уровень по своей политике, не
  ослабляя гейт.
- Аннотации MCP (`readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint`) для
  доверенного (trusted) сервера согласованы с `side_effect` (`01`/TCP-9) и служат
  enforcement-сигналом гейтов (`01`/TCP-10).

## 7. Версионирование ревизий

**Ревизии датированы** (`spec/revisions/<YYYY-MM>[-draft]/`). Текущая — `2026-07-draft`.

- **Draft-окно.** Пока ревизия в статусе `draft`, обратно несовместимые правки допустимы без
  бюрократии — договор ещё не зацементирован SDK (D3 плана). Статус `draft` держится до
  зелёного PHP SDK на уровне **L1 Core**, после чего ревизия переименовывается в релизную
  `2026-XX` (без суффикса `-draft`).
- **Immutable после релиза.** Опубликованная (релизная) ревизия **неизменяема**: любое
  breaking-изменение выходит **новой** датированной ревизией, старая остаётся доступной для
  уже привязанных к ней потребителей.
- **`spec_rev` в конверте.** Каждое событие несёт `spec_rev` (`02`/LC-5) — по нему потребитель
  знает, какой ревизией порождена запись; это же условие детерминизма replay при смене ревизии.
- **Версионирование сценариев** (`04`/SC-24) ортогонально версии ревизии: сценарий несёт
  собственную целочисленную версию `@<int>`, in-flight сессии пинятся на версию старта.
- **Версия формулы ключа** идемпотентности (`06`/IE-2) версионируется префиксом (`at1:`);
  смена состава/алгоритма — новый префикс, старые ключи смысла не меняют.

Схемы всех документов ревизии несут `$id` вида
`https://agentools.dev/schema/2026-07-draft/<file>` и диалект
`https://json-schema.org/draft/2020-12/schema` (проверяет `tools/spec_lint.py`).

## Приложение A — Потребители (информативно)

Раздел информативен и приведён для ориентира; в нормативной части спека продукт-нейтральна.
Спека — договор между двумя нативными SDK; ни один из них не является «третьим рантаймом»
(D8 плана): существующие agent-слои реализуют её контракты, а не заменяются ею.

| Понятие спеки | PHP-контур (реализует контракты) | Dart-контур (реализует контракты) |
|:--|:--|:--|
| Профиль инструмента (`01`) | единый реестр инструментов на MCP-сервер и agent-loop | in-process MCP-инструменты |
| `side_effect`/гейт (`00` §6) | stake `low`/`med`/`high` — алиасы D7 | Tier `0`/`1`/`2` — алиасы D7 |
| Уточнения (`03`) | доставка событием в UI (у используемого MCP-клиента client-side elicitation нет — D12) | MCP elicitation form-mode |
| Аудит/канонизация (`05`) | JCS-пакет экосистемы; ПДн маскируются вышестоящим шлюзом до записи | JCS реализуется самостоятельно (готового пакета нет — R-08) |
| Durable-состояние (`02`) | тенантские таблицы приложения | локальный персист + FSM |

Разграничение «кто что реализует» и стек-пины — `plans/AGENTOOLS/00_MASTER_PLAN.md` §5.5,
§6 и `20_research/R-08_library-pins.md` (vault; вне этого репозитория).
