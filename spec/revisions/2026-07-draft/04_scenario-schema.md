# 04 — Scenario Schema

> Ревизия спеки: `2026-07-draft` (см. `README.md`). Статус: draft.
> Нормативные ключевые слова — по [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119)
> (MUST / SHOULD / MAY). Термины профиля инструмента — `01_tool-contract-profile.md`;
> состояния и переходы FSM — `02_action-lifecycle.md`; гейты и уточнения —
> `03_confirmation-protocol.md`.

Документ задаёт **сценарии-как-данные** AgenTools: декларативные цепочки шагов
(`llm` / `tool` / `elicitation`), которые оба рантайма (PHP и Dart) интерпретируют
одинаково. Это уникальная добавленная стоимость пакета: ни `corex/ai`, ни
`axioma_assistant` не имеют формата многошаговых сценариев (00_MASTER_PLAN §5.6). Раз
сценарий исполняется двумя независимыми реализациями, его формат обязан быть
**исчерпывающе однозначным** — отсюда закрытая грамматика выражений (`schema/expression.md`,
D10 плана) и запрет циклов/ветвлений сверх минимума (D11 плана).

Сценарий — не оркестратор-фреймворк, а **данные поверх FSM `02`**: каждый шаг исполняется
в состояниях жизненного цикла, переходы выполняет рантайм по таблице `02`/§2, а не логика
сценария. LLM внутри `llm`-шага — decision function (`02`/LC-20), не владелец потока.

Схемы к документу: `schema/scenario.json`, грамматика выражений — `schema/expression.md`.

Нормативная форма сценария — **JSON** (валидируется против `schema/scenario.json`). YAML
допустим как авторский формат и приводится к JSON один-в-один (те же ключи и порядок
`steps`).

---

## 1. Дескриптор сценария

**SC-1 (MUST).** Сценарий идентифицируется строкой `<ns>.<name>@<int-версия>`
(`schema/scenario.json`, поле `scenario`), напр. `crm.daily_report@1`. `ns` — одна или
несколько snake-секций через точку, `name` — последняя секция; версия — положительное
целое без ведущего нуля. Версионирование — §8 (SC-24).

**SC-2 (MUST).** Сценарий несёт `metadata { title, description?, owner? }`: `title`
обязателен (человекочитаемое имя, ru), `description`/`owner` — опциональны. Метаданные
информативны и на семантику исполнения не влияют.

## 2. Шаг: общая форма

**SC-3 (MUST).** Сценарий содержит непустой упорядоченный массив `steps`. Каждый шаг —
объект с обязательными `id`, `kind`, `on_semantic_fail`, `on_technical_fail` и полями,
специфичными для `kind` ∈ {`llm`, `tool`, `elicitation`} (§2.1–2.3). Набор полей шага
**закрыт** (`additionalProperties:false`): произвольные ключи запрещены.

**SC-4 (MUST).** `id` — snake-идентификатор, **уникальный** в пределах сценария. JSON
Schema уникальность массива по ключу элемента не выражает — это правило **проверяет
рантайм** при загрузке сценария (дубль `id` = невалидный сценарий).

**SC-5 (MUST).** `input_map` — отображение `{ <param>: <expr> }`, где `<param>` — имя
входного аргумента шага, а значение — **выражение** грамматики `schema/expression.md`,
дающее ссылку (`$ctx.…` / `$steps.…`) либо литерал. `input_map` осмыслен для `llm`/`tool`
и запрещён для `elicitation` (§2.3).

**SC-6 (MUST).** Для `kind = llm` промпт и схема вывода задаются **ссылками на
версионируемые ассеты рантайма**, а не инлайн-текстом: `prompt_ref` (ссылка на промпт-ассет)
и `output_schema` (ссылка на схему структурированного вывода в реестре рантайма). Инлайнить
текст промпта запрещено (канон §2.7 R-06 flex: промпты версионируются как ассеты).

**SC-7 (MUST).** Поле-носитель действия зависит от `kind`: `tool` — имя инструмента по
профилю `01` (`tool`, шаблон TCP-5); `elicitation` — объект `clarification`
(`ClarificationRequest`, `03`/`schema/clarification.json`). Перекрёстные поля запрещены
(`tool`-шаг не несёт `prompt_ref`/`clarification` и т.д.) — выражено в `scenario.json`
через `allOf`/`if`-`then`.

**SC-8 (MUST).** Результат успешно исполненного шага доступен последующим шагам как
`$steps.<имя>`, где `<имя>` = `output_bind`, либо `id` шага по умолчанию. Порядок
доступности — только «слева направо»: шаг MUST NOT ссылаться на результат шага, стоящего
позже в `steps`.

### 2.1 `kind = llm`

Модель структурирует вход (голос/текст → черновик) по `output_schema`. Исполняется в
`RUNNING` (`02`/LC-20). `input_map` MAY передавать значения в промпт-ассет. Невалидный
вывод модели — semantic-отказ (§6, SC-18).

### 2.2 `kind = tool`

Вызов инструмента по `01`. На уровне FSM: `RUNNING → EXECUTING_TOOL` (LC-T5), успех
`→ RUNNING` (LC-T14). Для инструмента с `side_effect ∈ {write, irreversible}` включается
two-phase-гейт `03` (prepare → `WAITING_APPROVAL` → commit); политика гейта — §5.
`compensate` — §7.

### 2.3 `kind = elicitation`

Уточняющий вопрос пользователю; поле `clarification` — `ClarificationRequest` (`03`). На
уровне FSM: `RUNNING → WAITING_INPUT` (LC-T4), ответ `→ RUNNING` (LC-T10). Исходы ответа
(`answered`/`declined`/`cancelled`) и их маршрутизация — `03`/CP-26, CP-27. `input_map`,
`approval`, `compensate` для `elicitation` запрещены.

## 3. Условие исполнения `when`

**SC-9 (MUST).** `when` — опциональное выражение грамматики `schema/expression.md`,
которое MUST вычисляться в **boolean**. Результат не-boolean (напр. голая строка `$ctx.today`)
= ошибка вычисления → technical_fail шага (§6, SC-30). Отсутствие `when` эквивалентно
`when = true`.

## 4. Семантика исполнения

**SC-10 (MUST).** Шаги исполняются **строго последовательно** в порядке массива `steps`.
Порядок значим; параллельных ветвей в v1 нет.

**SC-11 (MUST).** Циклы, `goto`, переходы к произвольному шагу, else-ветки, вложенные
сценарии — **запрещены** (D11 плана). Единственная разветвляющая конструкция — `when`
(пропуск шага) и маршруты отказа (§6). Поток монотонно движется вперёд по `steps`.

**SC-12 (MUST).** Если `when` шага вычислилось в `false`, шаг **пропускается**: рантайм
эмитит audit-событие `step_skipped` (таксономия — `05_audit-events.md`, P0.7) и переходит
к следующему шагу; состояние FSM при пропуске **не меняется** (сессия остаётся в `RUNNING`).
Пропущенный шаг не создаёт `$steps.<id>` — ссылка на него в дальнейшем даст `missing = true`
(`schema/expression.md`, SC-28).

## 5. Гейт подтверждения шага

**SC-13 (MUST).** У `tool`-шага поле `approval` ∈ {`inherit`, `force`} задаёт политику
гейта (дефолт `inherit`): `inherit` — гейт выводится из `side_effect` инструмента по
`01`/TCP-12 (`read`/`draft` → без гейта, `write` → `confirm`, `irreversible` →
`double_confirm`); `force` — сценарий **принудительно** требует гейт `confirm`, даже если
инструмент по своему `side_effect` гейта не имеет.

**SC-14 (MUST).** `force` только **ужесточает**: он не понижает политику инструмента. Для
инструмента с `irreversible` (`double_confirm`) `force` остаётся `double_confirm`; ослабить
гейт сценарий не вправе (`01`/TCP-13). Механика самого гейта (prepare→preview→commit,
токен, исходы) — целиком `03`.

## 6. Маршруты отказа: semantic vs technical

**SC-15 (MUST).** Каждый шаг несёт два маршрута отказа — `on_semantic_fail` и
`on_technical_fail` — каждый ∈ { `"abort"`, `"continue"`, `{ "strategy": "retry",
"attempts": n }` }, где `n ∈ [1..3]`:

- `abort` — прервать сценарий; запустить компенсации (§7) и завершить сессию отказом;
- `continue` — проигнорировать отказ шага и перейти к следующему шагу;
- `retry` — повторить шаг (ограничения — SC-16).

**SC-16 (MUST).** Маршрут `retry` нормативно допустим **только** для `on_technical_fail`
и **только** если шаг идемпотентен (для `tool`-шага — `idempotent_commit`, `01`/TCP-14;
enforce идемпотентности — `06_idempotency-errors.md`). Рантайм MUST отвергать `retry` на
`on_semantic_fail` и `retry` у неидемпотентного шага как невалидный сценарий. (Тип
маршрута в `scenario.json` для обоих полей единый — это структурное послабление; запрет
`retry` на `on_semantic_fail` — правило рантайма.)

**SC-17 (MUST).** Backoff `retry` — **детерминированный, фиксированный**: перед i-й
повторной попыткой (i от 1) пауза `2^i` секунд (2, 4, 8). Джиттера нет — детерминизм нужен
для воспроизводимости при replay (`02`/LC-4) и в conformance.

**SC-18 (MUST).** Различение отказов:

- **semantic_fail** — модель не смогла выполнить задачу либо вернула невалидный вывод
  **после встроенного одного повтора валидации** (структурированный вывод не прошёл схему
  дважды). Это отказ «по смыслу», повтор тем же входом его не исправит.
- **technical_fail** — сбой инфраструктуры: транспорт, тайм-аут (`timeout_s`, SC-25),
  квота/rate-limit провайдера, ошибка вычисления выражения (`schema/expression.md`, §4).
  Это отказ «по среде», повтор может помочь.

**SC-19 (MUST).** `retry` на `on_semantic_fail` смысла не имеет (SC-18): у semantic-отказа
уже есть встроенный повтор валидации, а повтор тем же входом даст тот же результат. Поэтому
`on_semantic_fail` ∈ {`abort`, `continue`} (SC-16).

### Привязка маршрутов к FSM

| Маршрут (сработал) | Поведение FSM |
|:--|:--|
| `retry` (technical) | шаг → `FAILED_RETRYABLE` (LC-T7 / LC-T15) → `retry` → `RUNNING` (LC-T22); исчерпание попыток → `FAILED_TERMINAL` (LC-T23) |
| `abort` | компенсации (§7, обратный порядок) → `FAILED_TERMINAL` (LC-T8 / LC-T16, `session_failed`) |
| `continue` | отказ поглощён; переход к следующему шагу, сессия остаётся `RUNNING` |

## 7. Компенсации (saga)

**SC-20 (MUST).** Компенсация шага объявляется полем `compensate { tool, input_map? }`:
`tool` — имя инструмента-компенсатора (`01`/TCP-5), `input_map` — его аргументы
(выражения грамматики; доступны `$ctx` и `$steps` уже исполненных шагов).

**SC-21 (MUST).** `compensate` объявляется **только** у `tool`-шага с
`side_effect ∈ {write, irreversible}` (откатывать нечего у `read`/`draft` и у не-tool
шагов). `side_effect` живёт в дескрипторе инструмента (`01`), не в шаге, поэтому это
правило **проверяет рантайм**.

**SC-22 (MUST).** При срабатывании `abort` (SC-15) рантайм исполняет компенсации всех
ранее **успешно завершённых** компенсируемых шагов в **обратном** порядке — от шага,
предшествующего точке отказа, к первому (saga-откат, R-04). Затем сессия переходит в
`FAILED_TERMINAL`.

**SC-23 (MUST).** Компенсация MUST быть **идемпотентной** (её `idempotent_commit`,
`01`/TCP-14; ключ — `06`): при resume/повторной доставке откат не должен задвоиться. Отказ
самой компенсации — терминальный инцидент, требующий вмешательства оператора; рантайм
фиксирует его audit-событием (`05`) и оставляет сессию в `FAILED_TERMINAL`.

## 8. Тайм-аут шага и версионирование

**SC-25 (MUST).** `timeout_s` (опционально) — предельное время исполнения шага в секундах.
Истечение = **technical_fail** шага (SC-18), маршрутизируется `on_technical_fail`.

**SC-24 (MUST).** Версия сценария — положительное целое в `@<int>` (SC-1). Опубликованная
версия **неизменяема**: любое breaking-изменение (переименование/удаление шага, смена
`kind`/`tool`, несовместимая правка `input_map` или грамматики условий) публикуется как
**новая** версия с инкрементом. Уже запущенные (in-flight) сессии **продолжают
исполняться на той версии, с которой начаты** (версия пинится в начале сессии) — это
обязательное условие детерминизма replay (`02`/LC-4). Новые сессии стартуют на последней
версии.

## 9. Выражения

**SC-26..SC-31** — грамматика, семантика и обработка ошибок выражений вынесены в
`schema/expression.md` (нормативная часть спеки; правила `SC-26`…`SC-31` определены там):
два корня ссылок `$ctx`/`$steps` (SC-26), дереференс отсутствующего пути вне `missing()` =
ошибка (SC-27), `missing(Reference) → bool` (SC-28), строгое равенство без коэрсии и
boolean-операнды логических операторов (SC-29), ошибка вычисления = technical_fail шага
(SC-30), реализация AST-интерпретатором без `eval`/`compile` (SC-31). Контрольная таблица
примеров «выражение → результат» — там же (§5), она же зерно тест-векторов P0.9.

## Примеры

### Пример 1 — `crm.daily_report@1` (полный сценарий)

Канонический сценарий «отчёт о проделанной работе» (00_MASTER_PLAN §5.4): модель
структурирует наговоренный текст в черновик; если в черновике нет даты — добор уточнением;
затем запись через write-инструмент с гейтом подтверждения. Валиден против
`schema/scenario.json`. Это же зерно фикстур P0.9.

```json
// example: scenario.json
{
  "scenario": "crm.daily_report@1",
  "metadata": {
    "title": "Отчёт о проделанной работе за день",
    "description": "Наговоренный/написанный текст → черновик → добор недостающих полей → запись с подтверждением.",
    "owner": "flex.crm"
  },
  "steps": [
    {
      "id": "extract",
      "kind": "llm",
      "prompt_ref": "crm/daily_report/extract@1",
      "output_schema": "DailyReportDraft",
      "on_semantic_fail": "abort",
      "on_technical_fail": { "strategy": "retry", "attempts": 2 }
    },
    {
      "id": "clarify",
      "kind": "elicitation",
      "when": "missing($steps.extract.date)",
      "clarification": {
        "id": "clr_report_date",
        "question": "На какую дату оформить отчёт? Формат ГГГГ-ММ-ДД.",
        "kind": "text"
      },
      "on_semantic_fail": "abort",
      "on_technical_fail": "abort"
    },
    {
      "id": "save",
      "kind": "tool",
      "tool": "crm_report_create",
      "input_map": {
        "body": "$steps.extract.text",
        "date": "$ctx.today"
      },
      "approval": "inherit",
      "on_semantic_fail": "abort",
      "on_technical_fail": { "strategy": "retry", "attempts": 2 }
    }
  ]
}
```

Соответствие авторскому наброску §5.4 (нормативная форма строже эскиза): краткая запись
`on_technical_fail: retry(2)` → объект `{ "strategy": "retry", "attempts": 2 }` (SC-15);
ссылка `$extract.text` → укоренённая `$steps.extract.text` (грамматика требует корень
`$ctx`/`$steps`, `schema/expression.md`/SC-26); шаг `save` — `side_effect = write`
инструмента `crm_report_create` (`01`, Пример 2) ⇒ гейт `confirm` при `approval: inherit`
(SC-13), two-phase — по `03`.

### Пример 2 — компенсируемый write-шаг (фрагмент)

Иллюстрация `compensate` (§7) и `approval: force`: платёжный шаг помечен как
компенсируемый; при `abort` последующего шага рантайм откатит платёж идемпотентной
компенсацией в обратном порядке (SC-22, SC-23).

```json
{
  "id": "charge",
  "kind": "tool",
  "tool": "fina_payment_charge",
  "input_map": { "amount_minor": "$steps.invoice.total_minor", "currency": "$ctx.currency" },
  "approval": "force",
  "compensate": {
    "tool": "fina_payment_refund",
    "input_map": { "charge_id": "$steps.charge.charge_id" }
  },
  "on_semantic_fail": "abort",
  "on_technical_fail": { "strategy": "retry", "attempts": 3 }
}
```

Комментарий: `approval: force` навешивает гейт подтверждения (SC-13); `compensate`
допустим, т.к. шаг — `tool` с денежным `side_effect` (SC-21); откат `fina_payment_refund`
идемпотентен (SC-23).
