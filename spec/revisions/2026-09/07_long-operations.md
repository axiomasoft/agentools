# 07 — Long Operations: два обязательных пути, привязка к задаче, сверка, кооперативная отмена

> Ревизия спеки: `2026-09` (состав и статус — `README.md`). Базис wire-протокола — MCP
> ревизии `2026-07-28`, зафиксированной пином `spec/vendor/mcp/2026-07-28/PIN.md`.
> Конвенции, глоссарий и уровни соответствия — `00_overview.md`; жизненный цикл действия и
> таблица переходов — `03_action-lifecycle.md`; гейт перед записью — `04_confirmation.md`;
> уточнения и их единственный биндинг — `05_clarification-mrtr.md`; сценарии —
> `06_scenarios.md`. Нормативные ключевые слова — по
> [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

Документ нормирует **длинную операцию** — действие, результат которого не готов к моменту
ответа на вызов. Предмет здесь не производительность, а наблюдаемость исхода: пока результат
не записан, единственное, чем две реализации могут договориться о состоянии дел, — журнал
действия.

Форму документа задают три факта, а не предпочтение. Первый: расширение задач контрагента —
**факультативная возможность**, поэтому длинная операция обязана быть выразима и без неё;
реализация, умеющая только путь поверх задачи, неработоспособна у offline-first контура, где
задач нет вовсе. Второй: перечисление задач контрагента протоколом не даётся, поэтому
утраченный вызывающим идентификатор задачи невосстановим — отсюда обязанность записать его в
журнал до первого наблюдения статуса. Третий: отмена **кооперативна** — контрагент
подтверждает намерение, но не обязан останавливать работу, поэтому «действие отменено» не
может быть результатом вызова отмены и наблюдается только из журнала.

## 1. Границы документа

Документ владеет двумя путями длинной операции, привязкой действия к задаче контрагента,
отображением статусов задачи на записи журнала, состоянием сверки и кооперативной отменой на
уровне действия. Он **не** нормирует: перечень состояний и таблицу переходов (документ `03` —
единственный носитель), механику реестра эффектов и эпохи исполнителя (документ `03`,
`ALC-24`…`ALC-28`), гейт перед записью (документ `04`), примитив уточнения и его биндинг
(документ `05`), исход прогона сценария (документ `06`), коды типизированных ошибок
(документ `09`), покрытие обоих путей векторами (документ `11` и корпус ревизии).

Имя возможности расширения задач, состав его методов и зрелость его публикации — внешний
факт контрагента: ревизия нормирует **поведение** реализации при наличии и при отсутствии
расширения, а не дату и не имя (`00_overview.md` `OVR-4`).

## 2. Два пути длинной операции

**LOP-1 (MUST NOT, L2).** Автор сценария и автор инструмента MUST NOT требовать расширение
задач контрагента как жёсткую зависимость: оно есть факультативная возможность, и её
отсутствие MUST NOT делать сценарий или инструмент неисполнимым. Обратное сделало бы
неработоспособным весь offline-first контур, у которого задач нет.

**LOP-2 (MUST, L2).** Реализация, заявляющая соответствие ревизии, MUST поддерживать **оба
пути** длинной операции: поверх задачи контрагента и синхронным вызовом без задач. Оба пути
покрываются векторами корпуса, и заявление уровня без прохождения векторов обоих путей не
принимается: «поддерживается только через задачи» есть частичная реализация, а не выбор
архитектуры.

**LOP-3 (MUST, L2).** Синхронный путь MUST быть полноценным: действие ведёт тот же журнал,
проходит тот же гейт (документ `04`), записывает те же события реестра эффектов
(`ALC-24`) и наблюдается теми же состояниями, что и действие поверх задачи. Отсутствие
задачи меняет ровно одно — чем наблюдается ход работы: состоянием действия из его журнала, а
не статусом внешнего объекта.

**LOP-4 (MUST NOT, L2).** Реализация MUST NOT выводить из отсутствия задачи ослабление ни
одного требования ревизии: ни отказ от журналирования, ни пропуск гейта, ни синхронный
результат вместо записанного исхода. Синхронность пути есть свойство доставки ответа, а не
разрешение не записывать.

**LOP-5 (MUST, L2).** На синхронном пути незавершённость работы MUST наблюдаться состоянием
действия — `running` либо `applying` — и продолжение работы после сбоя MUST идти по
`ALC-26` новой эпохой исполнителя. Второго механизма «долгой работы без задачи» ревизия не
вводит: он был бы вторым носителем того же факта.

## 3. Сигнал хода и два канала его доставки

**LOP-6 (MUST, L2).** Единственным легитимным сигналом хода длинной операции поверх задачи
MUST быть смена статуса задачи. Иных сигналов ревизия не нормирует и на них не опирается.

**LOP-7 (MUST NOT, L2).** Реализация MUST NOT обещать процент выполнения длинной операции и
MUST NOT выводить его ни из одного канала доставки статуса. Протокол пина процента не даёт,
и вычисленная реализацией доля есть догадка, которую вторая реализация посчитает иначе.

**LOP-8 (MUST, L2).** Смена статуса задачи MUST доставляться одним из двух каналов —
опросом статуса вызывающим либо уведомлением контрагента, на которое вызывающий подписан, —
и оба канала MUST трактоваться как носители **одного и того же** сигнала. Опрос есть
умолчание; наличие канала уведомлений не вводит второго вида сигнала и не меняет его состава.

описывает push-канал `notifications/tasks` с подпиской через `subscriptions/listen`, «Polling

дословно. Имена методов принадлежат расширению контрагента и ревизией не переобъявляются

**LOP-9 (MUST, L2, Not testable: канал уведомлений существует только у контрагента, объявившего его поддержку — у остального контрагента вектор подписки не исполняется).** Реализация, получившая смену статуса каналом уведомлений, MUST обработать её тем же путём, что и статус, полученный опросом: одна и та же смена статуса MUST давать одну и ту же запись журнала независимо от канала. Две ветки обработки одного сигнала расходятся молча, и расхождение видно только на редком канале.

## 4. Привязка действия к задаче

**LOP-10 (MUST, L2).** Полученный идентификатор задачи MUST быть записан в журнал действия
событием `task_bound` **до первого опроса статуса или подписки на уведомления** — что из
этого происходит раньше. Переходы — `ALC-T23` и `ALC-T24`: привязка состояния действия не
меняет. Формулировка «до первого опроса» без второй ветки обходится подпиской, и
идентификатор теряется ровно в том сбое, против которого правило введено.

**LOP-11 (MUST NOT, L2).** Реализация MUST NOT рассчитывать на восстановление утраченного
идентификатора задачи перечислением задач контрагента: такого способа протокол пина не даёт.
Единственный носитель идентификатора — журнал действия, и это делает `LOP-10` условием
работоспособности, а не гигиеной.

## 5. Отображение статусов задачи на журнал

Таблица ниже **нормативна**: каждая строка адресуется маркером правила, и при расхождении
строки с текстом правила нормативен текст правила (`00_overview.md` `OVR-7`). Имена статусов
взяты из расширения задач контрагента и ревизией не переобъявляются.

| Статус задачи | Что записывается в журнал | Состояние действия | Правило |
|:--|:--|:--|:--|
| `working` | ничего | не меняется | LOP-12 |
| `input_required` | `input_recorded` по документу `05` | `created` либо `running` — переходы `ALC-T2`, `ALC-T5` | LOP-13 |
| `input_required` у действия в состоянии `applying` | ничего | типизированная ошибка | LOP-14 |
| `completed` | `action_completed` | `completed` | LOP-12 |
| `failed` | `action_failed` | `failed` | LOP-12 |
| `cancelled` | `action_cancelled` при выполненных гардах `ALC-T36`…`ALC-T38` | `cancelled` | LOP-12, LOP-25 |

**LOP-12 (MUST, L2).** Наблюдённый статус задачи MUST отображаться на запись журнала по
таблице выше, и таблица MUST быть единственным носителем этого отображения. Статус, не
названный таблицей, MUST обрабатываться по правилу must-ignore документа `09`: он
записывается как наблюдался и состояния действия не меняет.

**LOP-13 (MUST, L2).** Статус `input_required` MUST обрабатываться как уточнение по документу
`05`: полезная нагрузка задачи есть четвёртая точка приложения того же примитива, а не второй
механизм диалога. Этим закрывается адрес, оставленный правилом `CLR-8`; собственного примитива
уточнения документ не вводит.

**LOP-14 (MUST, L2).** Статус `input_required`, наблюдённый у действия в состоянии `applying`,
MUST давать типизированную ошибку (документ `09`) и MUST NOT порождать раунд уточнения:
внешний эффект уже запрошен, и запрос недостающего ввода поверх него означает, что контрагент
и вызывающий разошлись в том, какая работа выполняется.

## 6. Утрата привязки и состояние сверки

**LOP-15 (MUST, L2).** Утрата привязки к задаче MUST записываться событием
`task_binding_lost` с причиной из закрытого перечня `expired` и `unknown`. Перечень закрыт:
решение `DR-01` §G4 называет ровно два наблюдаемых случая — задача истекла и задача
контрагенту неизвестна, — а третья причина от них наблюдением не отличима.

**LOP-16 (MUST, L2).** Исход `task_binding_lost` MUST определяться реестром эффектов
действия: при отсутствии эффекта с записанным `effect_requested` без исхода действие остаётся
в `running` (`ALC-T25`), при наличии такого эффекта действие переходит в
`reconciliation_required` (`ALC-T26`). Утрата привязки сама по себе отказом действия не
является: неизвестен исход внешнего эффекта, а не судьба действия.

**LOP-17 (MUST NOT, L2).** В состоянии `reconciliation_required` реализация MUST NOT повторять
применение эффекта автоматически и MUST NOT считать отсутствие ответа контрагента признаком
неприменённого эффекта. Обязанность прочитать реестр эффектов перед повторной попыткой
нормирует `ALC-25`; здесь она усилена запретом повтора без выясненного исхода, потому что
канал, которым исход выяснялся, утрачен.

**LOP-18 (MUST, L2).** Выход из `reconciliation_required` MUST быть ровно одним из двух:
запись фактического исхода эффекта событием `effect_confirmed` либо `effect_failed`
возвращает действие в `running` (`ALC-T27`, `ALC-T28`), а зафиксированная невозможность
выяснить исход записывается событием `action_failed` и переводит действие в `failed`
(`ALC-T30`). Состояние без названного выхода было бы тупиком свёртки.

**LOP-19 (MUST NOT, L2).** Реализация MUST NOT трактовать `reconciliation_required` как
терминальное состояние и MUST NOT завершать действие успехом, не записав исход эффекта:
`action_completed` из этого состояния таблица переходов не допускает. Возобновление в этом
состоянии получает новую эпоху (`ALC-T29`) и сверку начинает заново.

## 7. Кооперативная отмена

**LOP-20 (MUST, L2).** Запрос отмены действия MUST записываться событием
`cancellation_requested`, и предикат **«отмена в силе»** MUST вычисляться как наличие такого
события в журнале действия. Запрос отмены состояния действия не меняет — переходы `ALC-T31`…
`ALC-T35`.

**LOP-21 (MUST NOT, L2).** Реализация MUST NOT хранить признак отмены отдельным полем
состояния, флагом проекции или девятым состоянием действия: признак выводится из журнала и
имеет ровно один носитель. Отмена ортогональна оси состояний, и выражение ортогонального
признака состоянием требовало бы удваивать перечень при каждом следующем таком признаке.

**LOP-22 (MUST NOT, L2).** Ревизия механизма отзыва запроса отмены не вводит, и реализация
MUST NOT считать отмену отзываемой: событие `cancellation_requested` записано навсегда.
Потребителя у отзыва в ревизии нет (`00_overview.md` `OVR-5`).

**LOP-23 (MUST NOT, L2).** Реализация MUST NOT возвращать «действие отменено» как синхронный
результат вызова отмены: вызов подтверждает принятие намерения. Фактический исход MUST
наблюдаться из журнала и есть ровно одно из `completed`, `failed`, `cancelled` — работа могла
успеть завершиться или упасть после запроса отмены.

**LOP-24 (MUST NOT, L2).** Реализация MUST NOT выводить из «отмена в силе» обязанность
контрагента остановить работу и MUST NOT запрещать действию запрашивать внешний эффект после
запроса отмены: отмена кооперативна, и запрет эффекта разошёлся бы с фактическим поведением
контрагента.

**LOP-25 (MUST NOT, L2).** Реализация MUST NOT записывать `action_cancelled`, пока у действия
есть эффект с записанным `effect_requested` без исхода. Инвариант выражен **формой таблицы**
документа `03`: строки в `cancelled` есть только из `created`, `running` и
`awaiting_confirmation` (`ALC-T36`…`ALC-T38`), а из `applying` и `reconciliation_required` их
нет. Сначала записывается исход эффекта, затем — отмена; иначе отмена объявляется поверх
эффекта с неизвестным исходом.

## 8. Граница: отмена и прогон сценария

**LOP-26 (MUST, L2).** Отмена нормируется ревизией **на уровне действия**; взаимодействие
отмены с прогоном сценария ревизия `2026-09` не нормирует, и исход прогона `CANCELLED`
документом `06` не заводится. Реализация MUST NOT выводить из настоящего документа поведение
прогона сценария, шаг которого отменён: отменённое действие шага не является ни семантическим,
ни техническим отказом шага в смысле `SCN-6`, и маршрут отказа для него ревизией не назначен.
Граница названа правилом намеренно — умолчание две реализации заполнили бы по-разному.

## 9. Схемы и примеры

`schema/task-binding.json` описывает запись привязки действия к задаче и владеет закрытым
перечислением причины утраты привязки, а также открытыми перечислениями канала доставки и
статуса задачи. Форму самой задачи схема не переописывает — она принадлежит расширению
контрагента (`OVR-4`). Производный закрытый вариант живёт в `schema/authoring/` и сгенерирован
`tools/close_schema.py`.

**LOP-27 (MUST, L2).** Запись привязки MUST нести идентификатор действия и идентификатор
задачи; канал доставки, наблюдённый статус и причина утраты привязки записываются, когда
наблюдались. Значение идентификатора задачи непрозрачно: реализация MUST NOT выводить из него
срок, принадлежность и состав работы.

Пример 1 — путь поверх задачи: привязка записана до первого наблюдения статуса, канал —
уведомления (`LOP-10`, `LOP-8`).

```json
// example: task-binding.json
{
  "action_id": "act-9b02",
  "task_id": "task-5f7c1d",
  "channel": "notification",
  "observed_status": "working"
}
```

Пример 2 — та же привязка утрачена: контрагент отвечает, что задача истекла, а у действия
записан `effect_requested` без исхода, поэтому действие уходит в `reconciliation_required`
(`LOP-15`, `LOP-16`).

```json
// example: task-binding.json
{
  "action_id": "act-9b02",
  "task_id": "task-5f7c1d",
  "channel": "poll",
  "observed_status": "unknown_to_counterparty",
  "lost_reason": "expired"
}
```

Пример 3 — то же действие синхронным путём: расширения задач у контрагента нет, привязка не
записывается вовсе, и ход работы наблюдается состоянием действия из его журнала (`LOP-3`,
`LOP-5`). Событие ниже — запрос внешнего эффекта того же действия, записанный до попытки
применения (`ALC-24`).

```json
// example: lifecycle-event.json
{
  "event_id": "ev-9b02-0004",
  "action_id": "act-9b02",
  "seq": 4,
  "expected_prev_seq": 3,
  "ts": "2026-09-05T11:02:47.310Z",
  "actor": { "type": "agent", "id": "agent-fina-1" },
  "kind": "effect_requested",
  "event_version": 1,
  "spec_rev": "2026-09",
  "epoch": 1,
  "payload": {
    "effect_id": "eff-payment-9b02",
    "idempotency_key": "at1:4d20ba6f11",
```
