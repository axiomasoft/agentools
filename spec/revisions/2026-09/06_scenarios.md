# 06 — Scenarios: сценарий как данные, язык выражений, лимиты, компенсации

> Ревизия спеки: `2026-09` (состав и статус — `README.md`). Базис wire-протокола — MCP
> ревизии `2026-07-28`, зафиксированной пином `spec/vendor/mcp/2026-07-28/PIN.md`.
> Конвенции, глоссарий и уровни соответствия — `00_overview.md`; жизненный цикл действия и
> таблица переходов — `03_action-lifecycle.md`; гейт перед записью — `04_confirmation.md`;
> уточнения — `05_clarification-mrtr.md`. Грамматика языка выражений — `schema/expression.md`.
> Нормативные ключевые слова — по [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

Документ нормирует **сценарий** — декларативную цепочку шагов, которую два независимых
рантайма обязаны истолковать одинаково, — и **язык выражений**, которым шаг описывает своё
условие и свои аргументы. Предмет здесь не удобство авторов сценариев, а воспроизводимость:
сценарий есть данные, и всё, что делает его исполнение предсказуемым, обязано быть выражено в
самих данных, а не в поведении конкретного рантайма.

Три решения задают форму документа и приняты по фактам, а не по вкусу. Язык выражений —
собственный и закрытый: у единственного зрелого кандидата с общим набором соответствия обе
реализации на Dart частичны, и импорт внёс бы дрейф PHP и Dart на уровне спецификации самого
языка. Режим компиляции выражений запрещён нормой, а не советом: уязвимость `CVE-2026-54133`
(CVSS 9.3) возникла именно из компилирующего режима вычислителя, и тот же класс — в
`CVE-2026-1615`. Количественные лимиты обязательны, потому что отсутствие динамического
исполнения не устраняет отказ в обслуживании через глубокую рекурсию и большие коллекции, а
ни один из обследованных языков лимитов по умолчанию не задаёт.
RAG:✅ 2026-07-26 — R-11 §8: обе реализации CEL на Dart частичны при полном соответствии
реализации на PHP; `CVE-2026-54133` в `jmespath.php` из режима `CompilerRuntime`, аналог —
`CVE-2026-1615`; ни один обследованный язык не задаёт лимитов по умолчанию; компенсация как
первоклассный примитив отсутствует у CNCF Serverless Workflow 1.0.3, AWS ASL и Argo,
единственная нормативная модель — BPMN (компенсируются только успешно завершённые активности,
в обратном порядке).

Уровень документа по умолчанию — `L2` (`00_overview.md` §4); объявленных отклонений нет.
Артефакты документа — `schema/scenario.json` и `schema/expression.md`.

## 1. Границы документа

Документ владеет формой сценария и шага, маршрутами отказа, языком выражений и его лимитами,
компенсациями и исходом прогона. Он **не** нормирует: жизненный цикл отдельного действия и
таблицу переходов (документ `03`), гейт перед записью (документ `04`), уточнения и их биндинг
(документ `05`), длинные операции и задачи (документ `07`), идемпотентность вызова и коды
ошибок (документ `09`), реализацию вычислителя (фазы SDK).

Навигация сложнее прямого пути — обход коллекции, фильтрация, выборка — в ревизию `2026-09`
не вводится: точка расширения без потребителя запрещена (`00_overview.md` `OVR-5`). Кандидат
на эту роль назван разведкой и будет введён вместе с первым сценарием, которому он реально
нужен, а не заранее.

## 2. Сценарий и шаг

**SCN-1 (MUST, L2).** Сценарий MUST быть данными: последовательностью шагов, порядок которых
задан их позицией в перечне и ничем иным. Второго носителя порядка — поля «следующий шаг»,
приоритета, веса — ревизия не вводит: два носителя порядка расходятся молча.

**SCN-2 (MUST, L2).** Каждый шаг сценария MUST быть действием в смысле документа `03` — со
своим журналом, своим жизненным циклом и своей идентичностью. Сценарий второго журнала не
заводит и состояния шагов не хранит: состояние прогона выводится из журналов его шагов.

**SCN-3 (MUST, L2).** Идентификатор шага MUST быть уникален в пределах сценария и MUST служить
адресом результата шага в выражениях. Отдельного псевдонима результата ревизия не вводит:
второй адрес одного значения — лишняя степень свободы, на которой две реализации расходятся.

**SCN-4 (MUST NOT, L2).** Автор сценария MUST NOT помещать в сценарий исполняемый код, шаблон
host-языка или ссылку на внешний файл поведения. Всё, что сценарий умеет, выражается его
объявленными полями и языком выражений; расширение поведения выражается новым инструментом,
а не новой формой сценария.

**SCN-5 (MUST, L2).** Сценарий MUST нести идентификатор ревизии, по правилам которой он
истолковывается (`00_overview.md` `OVR-23`). Рантайм, встретивший чужую ревизию, MUST
отказаться исполнять сценарий, а не истолковывать его по правилам своей.

## 3. Маршруты отказа шага

**SCN-6 (MUST, L2).** Реализация MUST различать два класса отказа шага: **семантический** —
инструмент отработал и отказал по доменной причине, — и **технический** — исполнение или
вычисление не состоялось. Класс отказа MUST определять маршрут: `on_semantic_fail` либо
`on_technical_fail`. Один маршрут на оба класса запрещён: доменный отказ повторять
бессмысленно, а технический — ровно то, что повторяют.

**SCN-7 (MUST, L2).** Маршрут отказа MUST быть одним из закрытого перечня `abort`, `retry`,
`continue`. Перечень закрыт: добавление исхода есть намеренно ломающее изменение, выходящее
новой датированной ревизией по окну депрекации `00_overview.md` `OVR-24`.

**SCN-8 (MUST, L2).** Маршрут `retry` MUST нести конечное число попыток, и повтор MUST
исполняться с тем же идемпотентным ключом, что и исходный вызов (документ `09`). Повтор с
новым ключом повтором не является — это второй вызов, и именно так рождается дубль записи в
домене.

**SCN-9 (MUST NOT, L2).** Автор сценария MUST NOT выражать маршрут отказа переходом к
произвольному шагу и MUST NOT возвращать исполнение в уже исполненный шаг. Граф исполнения
сценария есть цепочка, и это свойство проверяется статически до первого вызова; цикл сделал бы
и бюджет шагов, и разворот компенсаций неопределёнными.

**SCN-10 (MUST, L2).** Исчерпание попыток `retry` MUST быть эквивалентно `abort` того же
класса отказа. Молчаливое превращение исчерпанных попыток в `continue` запрещено: оно
превращает наблюдаемый отказ в незаметный пропуск шага.

**SCN-11 (MUST, L2).** Маршрут `continue` MUST записывать отказ шага в журнал этого шага, и
результат отказавшего шага MUST оставаться отсутствующим для выражений: ссылка на него ведёт
себя как ссылка на неисполненный шаг (`schema/expression.md` §2). Иначе последующий шаг не
отличит «шаг отказал» от «шаг вернул пустое значение».

## 4. Язык выражений

**SCN-12 (MUST, L2).** Выражения MUST употребляться ровно в двух местах шага: условие
исполнения `when` и значения отображения аргументов `input_map`, включая отображение
компенсации. Результат `when` MUST быть логическим значением; результат отображения — значение
любого типа языка.

**SCN-13 (MUST, L2).** Грамматика языка выражений MUST быть той, что задана файлом
`schema/expression.md`, и этот файл MUST быть её **единственным** носителем: его продукции,
таблица приоритетов, семантика типов, закрытый перечень ошибок вычисления и таблица
контрольных точек нормативны в силу настоящего правила. Изложение грамматики прозой в любом
документе ревизии запрещено: два носителя одной грамматики — ровно тот дефект, который
`00_overview.md` `OVR-16` запрещает для перечислений, и для языка он дороже.

**SCN-14 (MUST, L2).** Вычислитель выражений MUST быть чистым обходом дерева разбора, и
реализация MUST NOT компилировать выражение в код host-языка, MUST NOT обращаться к средствам
динамического исполнения host-языка и MUST NOT кэшировать выражение в исполняемом виде. Это
норма, а не рекомендация: разобранная разведкой уязвимость с оценкой 9.3 возникла именно из
компилирующего режима вычислителя, а не из ошибки в грамматике.

**SCN-15 (MUST, L2).** Реализация MUST отвергать выражение, содержащее конструкцию вне
грамматики — вызов функции, кроме `missing`, индексацию, арифметику, — как синтаксическую
ошибку, до вычисления. Правило сформулировано наблюдаемо намеренно: запрет `SCN-14` покрывается
вектором корпуса «выражение с попыткой инъекции host-кода отвергается» (`schema/expression.md`
строка E15), а не заявлением реализации о своей архитектуре.

## 5. Лимиты вычислителя

Лимиты назначены консервативно: внешних данных о типичных размерах выражений и коллекций на
дату ревизии нет, ни один обследованный язык значений по умолчанию не публикует. Поэтому
каждое значение ниже несёт фразу «пересматривается по данным фазы P6» — оно контракт, а не
догадка, но контракт с назначенным моментом пересмотра.

**SCN-16 (MUST, L2).** Глубина дерева разбора выражения MUST быть не более **32** уровней
вложенности; превышение — ошибка вычисления. Значение пересматривается по данным фазы P6.

**SCN-17 (MUST, L2).** Длина выражения MUST быть не более **512** кодовых точек Unicode.
Единица счёта — кодовая точка, а не байт: счёт в байтах дал бы разным реализациям разные
пределы на одном тексте. Значение пересматривается по данным фазы P6.

**SCN-18 (MUST, L2).** Число элементов коллекции, разыменованной ссылкой или скопированной
отображением аргументов, MUST быть не более **1000**; превышение — ошибка вычисления.
Ограничение относится к значению, которое вычислитель обязан материализовать, и потому
действует и там, где выражение выглядит как простое чтение пути. Значение пересматривается по
данным фазы P6.

**SCN-19 (MUST, L2).** Бюджет вычисления одного выражения MUST выражаться числом посещённых
узлов дерева разбора и MUST быть не более **10000** узлов. Бюджет намеренно **не**
формулируется во времени: время исполнения не воспроизводится между рантаймами и машинами, а
счётчик посещённых узлов при детерминированном порядке вычисления
(`schema/expression.md` §3) одинаков в обеих реализациях. Значение пересматривается по данным
фазы P6.

**SCN-20 (MUST, L2).** Число шагов, исполняемых одним прогоном сценария, MUST быть не более
**64**, считая повторы `retry` и шаги компенсации. Значение пересматривается по данным фазы P6.

**SCN-21 (MUST, L2).** Превышение любого лимита MUST быть типизированной ошибкой (документ
`09`) класса технического отказа шага и MUST маршрутизироваться `on_technical_fail`.
Прекращение прогона без записи, обрыв соединения и молчаливое усечение результата запрещены:
лимит — часть контракта, и его срабатывание наблюдаемо.

**SCN-22 (MUST, L2).** Рантайм MAY ужесточить любой лимит и MUST NOT ослабить его, а
действующие значения MUST публиковаться отчётом соответствия (документ `11`). Ослабление
лимита делает сценарий, исполнимый в одном контуре, неисполнимым в другом — то есть отменяет
переносимость, ради которой лимиты и введены.

## 6. Компенсации

**SCN-23 (MUST, L2).** Компенсация шага MUST объявляться плоскими полями самого шага. Второго
списка компенсируемых шагов ревизия не вводит: реестр компенсируемых шагов есть производная от
объявлений, и отдельный список разошёлся бы с ними при первой же правке сценария.

**SCN-24 (MUST, L2).** Компенсации MUST исполняться только для шагов, завершившихся **успешно**,
и в порядке, обратном порядку их исполнения. Шаг, который не начинался или отказал, откатывать
нечего; обратный порядок обязателен, потому что прямой порядок откатывал бы зависимость раньше
зависящего от неё.

**SCN-25 (MUST, L2).** Компенсация MUST быть идемпотентной и MUST исполняться с тем же
идемпотентным ключом при повторе (документ `09`). Разворот запускается в том числе после
сбоя исполнителя, и неидемпотентная компенсация в этот момент удваивает откат.

**SCN-26 (MUST, L2).** Провал компенсации MUST давать исход прогона `COMPENSATION_FAILED`,
отличный от `FAILED`. Это разные домены отказа: `FAILED` означает, что желаемое не сделано, а
`COMPENSATION_FAILED` — что сделанное не удалось отменить, и второй случай требует человека,
а не повтора.

**SCN-27 (MUST, L2).** Провал компенсации MUST останавливать разворот и MUST фиксировать
идентификатор шага, на котором разворот остановлен. Продолжение разворота «по остальным шагам»
запрещено: оно оставляет систему в состоянии частичного отката, о котором никто не знает.

**SCN-28 (MUST, L2).** Исход прогона сценария MUST быть одним из закрытого перечня
`COMPLETED`, `FAILED`, `COMPENSATED`, `COMPENSATION_FAILED`.

**SCN-29 (MUST NOT, L2).** Реализация MUST NOT трактовать исход прогона сценария как состояние
действия: перечень состояний действия закрыт `03_action-lifecycle.md` `ALC-11`, прогон
сценария в него ничего не добавляет и переходов в таблицу переходов того же документа не вносит
(`ALC-14` здесь беспредметен). Исходы прогона записаны прописными буквами, а состояния
действия — строчными, и это различение регистра намеренно.

## 7. Границы с гейтом и уточнением

**SCN-30 (MUST, L2).** Шаг, вызов которого вернул требование ввода, MUST обрабатываться по
документу `05` и MUST NOT считаться отказом шага ни одного из двух классов: уточнение есть
продолжение вызова, а не его исход. Требование гейта, возникшее на шаге, обрабатывается по
документу `04` и точно так же отказом шага не является.

## 8. Схемы и примеры

`schema/scenario.json` описывает сценарий и владеет закрытыми перечислениями маршрута отказа
и исхода прогона; отображения аргументов оставлены открытыми намеренно — их состав задаёт
`inputSchema` вызываемого инструмента, а не эта схема. `schema/expression.md` — единственный
носитель грамматики (`SCN-13`). Производный закрытый вариант схемы живёт в `schema/authoring/`
и сгенерирован `tools/close_schema.py`.

Пример 1 — линейный сценарий: второй шаг исполняется по условию и читает результат первого
(`SCN-1`, `SCN-3`, `SCN-12`).

```json
// example: scenario.json
{
  "scenario_id": "invoice_intake",
  "title": "Приём счёта: разбор вложения и создание черновика",
  "spec_rev": "2026-09",
  "steps": [
    {
      "id": "extract",
      "tool": "fina_document_extract",
      "input_map": {
        "document_id": "$ctx.document_id"
      },
      "on_technical_fail": {
        "action": "retry",
        "attempts": 3
      }
    },
    {
      "id": "draft",
      "tool": "fina_invoice_draft",
      "when": "!missing($steps.extract.total_minor) && $steps.extract.currency == \"RUB\"",
      "input_map": {
        "counterparty_id": "$steps.extract.counterparty_id",
        "amount_minor": "$steps.extract.total_minor"
      },
      "on_semantic_fail": {
        "action": "abort"
      }
    }
  ]
}
```

Пример 2 — сценарий с компенсацией: резерв отменяется, если последующая отправка не удалась;
разворот идёт в обратном порядке и только по успешно завершённым шагам (`SCN-23`, `SCN-24`).

```json
// example: scenario.json
{
  "scenario_id": "payment_send",
  "title": "Отправка платежа с резервированием средств",
  "spec_rev": "2026-09",
  "steps": [
    {
      "id": "reserve",
      "tool": "fina_funds_reserve",
      "input_map": {
        "account_id": "$ctx.account_id",
        "amount_minor": "$ctx.amount_minor"
      },
      "compensate": {
        "tool": "fina_funds_release",
        "input_map": {
          "reservation_id": "$steps.reserve.reservation_id"
        }
      }
    },
    {
      "id": "send",
      "tool": "fina_payment_send",
      "input_map": {
        "reservation_id": "$steps.reserve.reservation_id",
        "counterparty_id": "$ctx.counterparty_id"
      },
      "on_technical_fail": {
        "action": "abort"
      },
      "on_semantic_fail": {
        "action": "abort"
      }
    }
  ]
}
```

Пример 3 — сценарий, отвергаемый до первого вызова: условие второго шага содержит вызов,
которого в языке нет, и разбор выражения даёт синтаксическую ошибку (`SCN-15`,
`schema/expression.md` строка E15). Сам документ сценария схеме соответствует — отвергается
выражение, а не форма.

```json
// example: scenario.json
{
  "scenario_id": "rejected_expression",
  "title": "Отвергаемое выражение: вызов вне грамматики",
  "spec_rev": "2026-09",
  "steps": [
    {
      "id": "extract",
      "tool": "fina_document_extract",
      "input_map": {
        "document_id": "$ctx.document_id"
      }
    },
    {
      "id": "draft",
      "tool": "fina_invoice_draft",
      "when": "$ctx.tenant == exec(\"id\")",
      "input_map": {
        "counterparty_id": "$steps.extract.counterparty_id"
      },
      "on_technical_fail": {
        "action": "abort"
      }
    }
  ]
}
```
