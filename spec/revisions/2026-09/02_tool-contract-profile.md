# 02 — Tool Contract Profile: профиль инструмента, дайджест дескриптора, схемная гигиена

> Ревизия спеки: `2026-09` (состав и статус — `README.md`). Базис wire-протокола — MCP
> ревизии `2026-07-28`, зафиксированной пином `spec/vendor/mcp/2026-07-28/PIN.md`.
> Конвенции, глоссарий и уровни соответствия — `00_overview.md`; вендорный префикс, база
> `$id` и единственный ключ данных — `01_extension-identity.md`. Нормативные ключевые слова
> — по [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

Документ задаёт **профиль MCP-инструмента AgenTools**: что обязан нести дескриптор, как
называется инструмент, что лежит в блоке расширения, как считается дайджест дескриптора и по
каким правилам пишутся схемы всей ревизии. Профиль — то, что обе реализации и оба контура
обязаны уметь выразить одинаково; он же несёт первую защиту от подмены инструмента.

Уровень документа по умолчанию — `L1` (`00_overview.md` §4). Объявленное отклонение ровно
одно: метка происхождения аргумента — `L3`. Схемы к документу —
`schema/tool-descriptor.json` и `schema/side-effect.json`.

---

## 1. Базис: дескриптор инструмента протокола

**TLP-1 (MUST, L1).** Инструмент AgenTools MUST быть корректным инструментом MCP ревизии
пина: поля `name`, `title`, `description`, `inputSchema`, `outputSchema` и `annotations`
трактуются строго по протоколу. Профиль их не переопределяет — он сужает использование
(разделы 2–3) и добавляет метаданные в точке расширения (раздел 4).

**TLP-2 (MUST, L1).** Дескриптор инструмента AgenTools MUST нести `name`, `description`,
`inputSchema` и блок расширения `_meta["dev.agentools/action"]`. Поле `description` записывается
как actionable-description из ровно четырёх непустых строк в фиксированном порядке:
`Purpose: <назначение>`, `Call when: <условия вызова>`, `Required arguments: <имена обязательных
аргументов либо none>`, `Example: <пример вызова>`. Инструмент без блока расширения — обычный
MCP-инструмент, к которому нормы ревизии не применяются.

Эта форма проверяет наличие четырёх операционных компонентов, но не утверждает эффективность
описания для конкретной модели. Модельное качество измеряется отдельно в P10.6.

**TLP-3 (SHOULD, L1).** Автор инструмента SHOULD задавать `title` — человекочитаемое имя для
интерфейса; `name` для показа человеку не предназначен и используется как программный адрес.

**TLP-4 (SHOULD, L1).** Автор инструмента SHOULD объявлять `outputSchema` для инструментов,
результат которых потребляется программно или рендерится интерфейсом: без него превью и
проекции строятся на догадках о форме результата.

**TLP-5 (MUST, L1).** Реализация, объявившая `outputSchema`, MUST возвращать структурированный
результат, соответствующий этой схеме. Расхождение результата с объявленной схемой —
ошибка реализации, а не «более богатый ответ».

**TLP-6 (MUST NOT, L1).** Автор инструмента MUST NOT вводить на верхнем уровне дескриптора
поля, не определённые протоколом: любое расширение живёт только внутри `_meta` под ключом
данных `dev.agentools/action` (`01_extension-identity.md` `EXT-7`). Это и есть то, что
оставляет дескриптор корректным для контрагента без поддержки расширения.

## 2. Имя инструмента

**TLP-7 (MUST, L1).** `name` MUST соответствовать регулярному выражению
`^[a-z][a-z0-9]*(_[a-z0-9]+)+$` длиной не более 64 символов и MUST быть уникальным в пределах
одного каталога инструментов. Ведущие, хвостовые и сдвоенные подчёркивания, а также символы
вне `[a-z0-9_]` запрещены грамматикой.

**TLP-8 (SHOULD, L1).** Автор инструмента SHOULD строить имя по схеме
`{module}_{resource}_{verb}` (например `crm_report_create`): префикс модуля отделяет
пространства имён двух контуров, а порядок `resource`/`verb` остаётся рекомендацией —
устоявшиеся формы вроде `resto_open_shift` допустимы.

## 3. Аннотации как сигнал политики

Аннотации протокола (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`)
для недоверенного сервера — подсказки. В контуре AgenTools каталог инструментов свой, и
профиль поднимает их до сигнала политики, не делая вторым носителем класса эффекта.

**TLP-9 (MUST, L1).** Автор инструмента MUST задавать все четыре аннотации явно. Опора на
консервативные значения по умолчанию запрещена: неявное значение нельзя ни сверить, ни
покрыть вектором, а расхождение двух реализаций по умолчанию — ровно тот класс дефекта,
который ревизия предотвращает.

**TLP-10 (MUST, L1).** Аннотации MUST быть согласованы с классом эффекта по таблице ниже;
несогласованный дескриптор невалиден и отвергается ещё в каталоге, а не при вызове.

| `side_effect` | `readOnlyHint` | `destructiveHint` |
|:--|:--|:--|
| `read` | `true` | `false` |
| `draft` | `false` | `false` |
| `write` | `false` | `false` |
| `irreversible` | `false` | `true` |

**TLP-11 (MUST NOT, L1).** Реализация MUST NOT выводить требование гейта подтверждения из
аннотаций: единственный носитель класса эффекта — `side_effect` (`00_overview.md` `OVR-21`),
а требование гейта выводится из него по таблице `00_overview.md` §6. Аннотации остаются
сигналом для интерфейса и каталога.

## 4. Блок `_meta["dev.agentools/action"]` дескриптора

**TLP-12 (MUST, L1).** Блок расширения дескриптора MUST нести `side_effect`; остальные поля
блока — `confirmation`, `idempotent_commit`, `permissions_hint`, `content_origin` —
опциональны и вводятся правилами ниже. Перечень полей блока закрыт этим правилом: поле, не
названное здесь и не введённое другим документом ревизии со своим правилом, данными профиля
не является.

**TLP-13 (MUST NOT, L1).** Реализация, встретившая неизвестное значение `side_effect`,
MUST NOT трактовать его как более слабый класс эффекта: неизвестное значение обрабатывается
как требующее гейта (`00_overview.md` `OVR-19`), а не как `read`.

**TLP-14 (MAY, L1).** Автор инструмента MAY задать `confirmation` явно, чтобы **ужесточить**
политику гейта относительно выведенной из `side_effect`. Ослабление запрещено
(`00_overview.md` `OVR-20`), а механика самого гейта — предложение, токен, решения, аудит
решения — нормируется документом `04` и здесь не повторяется.

**TLP-15 (SHOULD, L1).** Автор инструмента SHOULD объявлять `idempotent_commit` для
инструментов класса `write` и `irreversible`: без него повтор применения нельзя отличить от
нового намерения. Ключ идемпотентности и состояния дедупликации — документ `09`.

**TLP-16 (SHOULD, L1).** Автор инструмента SHOULD объявлять `permissions_hint` — справочный
перечень требуемых прав для каталогизации. Механизмом авторизации это поле не является:
энфорсмент прав нормируется документом `10` и живёт в рантайме.

**TLP-17 (MUST NOT, L1).** Адаптер контура MUST NOT вносить в дескриптор второй носитель
класса эффекта: собственные уровни риска (`stake`, `Tier` и подобные) остаются на стороне
адаптера и отображаются на `side_effect` без ослабления гейта (`00_overview.md` `OVR-21`).

## 5. `descriptor_digest` и класс ошибки `descriptor_drift`

Официальный реестр MCP верифицирует пространство имён сервера и **не подписывает** содержимое
объявления: гарантию неизменности дескриптора обязан дать слой выше. Контрмера названа прямо —
дайджест описания инструмента и сверка с базовым значением в пределах сессии.
RAG:✅ 2026-07-26 — R-11 §11 (OWASP MCP03, Tool Poisoning и rug pull): контрмера
«tool description fingerprinting/hashing baseline with session comparison»; реестр MCP не
подписывает `server.json`.

**TLP-18 (MUST, L1).** Вход дайджеста дескриптора MUST быть объектом ровно из пяти членов:
`name`, `description`, `inputSchema`, `outputSchema` и `extension` — значение ключа данных
`dev.agentools/action`. Необязательный член, отсутствующий в дескрипторе, опускается; подстановка
`null` или пустого объекта вместо отсутствующего члена запрещена — иначе две реализации получат
разные байты на одном и том же дескрипторе.

**TLP-19 (MUST, L1).** Реализация MUST вычислять `descriptor_digest` в три шага, именно в этом
порядке: (1) построить объект входа по `TLP-18`; (2) сериализовать его канонизацией JCS
(RFC 8785, документ `08`) — порядок членов при этом задаёт не автор дескриптора, а сама
канонизация, поэтому «порядок полей» не является предметом договорённости; (3) взять SHA-256 от
полученных байтов UTF-8. Представление значения — строка формы `^sha-256:[0-9a-f]{64}$`;
единственное значение префикса ревизии — `sha-256`, смена алгоритма выходит новой ревизией.

**TLP-20 (MUST NOT, L1).** Реализация MUST NOT включать во вход дайджеста поля, не
перечисленные в `TLP-18` — в частности `title` и `annotations`. Оба меняются по причинам
интерфейса и политики, не меняя контракта вызова; их включение превратило бы правку подписи
кнопки в дрейф дескриптора.

**TLP-21 (MUST, L1).** Один и тот же дескриптор MUST давать **байт-идентичный**
`descriptor_digest` в реализации PHP и в реализации Dart. Это межъязыковой инвариант, а не
свойство одной реализации: он проверяется вектором с золотым значением, а не сравнением
реализации с самой собой.

**TLP-22 (MUST, L1).** Реализация MUST вычислять `descriptor_digest` на фазе подготовки
действия и сверять его на фазе применения. Несовпадение MUST давать отдельный класс ошибки
`descriptor_drift`: дескриптор инструмента изменился между подготовкой и применением, и
предъявленное пользователю предложение больше не описывает то, что будет выполнено.

**TLP-23 (MUST NOT, L1).** Реализация MUST NOT подменять `descriptor_drift` общей ошибкой
авторизации, валидации аргументов или истечения токена. Класс ошибки различает атаку подмены
инструмента и штатный отказ; слитый в общий класс, он перестаёт быть наблюдаемым.

## 6. Метка происхождения аргумента

**TLP-24 (MAY, L3).** Автор инструмента MAY объявить в блоке расширения `content_origin` —
метку происхождения содержимого аргумента, например `untrusted_external`. Уровень `L3`, потому
что метка выражает в контракте единственную часть паттерна разделения привилегированной и
карантинной модели, которая вообще выразима в контракте; сама изоляция — свойство рантайма, и
реализация уровня ядра остаётся полноценной без неё.

**TLP-25 (MUST, L3).** Реализация, получившая аргумент с меткой `untrusted_external`, MUST
направить вызов изолированным маршрутом; сам маршрут нормируется документом `10`. Уровень
`L3`, потому что правило действует только там, где объявлена метка уровня `L3` из `TLP-24`:
без неё требование беспредметно.

## 7. Схемная гигиена ревизии

Правила этого раздела адресованы **автору ревизии** и покрываются прогоном линтера, а не
поведением SDK. Они действуют на все схемы ревизии, а не только на схемы этого документа.

**TLP-26 (MUST NOT, L1).** Автор ревизии MUST NOT закрывать опубликованную схему: ни
`additionalProperties: false`, ни `unevaluatedProperties` в `schema/**` не допускаются.
Закрытая схема на проводе превращает любое будущее опциональное поле в ломающее изменение и
прямо противоречит правилу must-ignore (`DR-01` §E3, §J9).

**TLP-27 (MUST, L1).** Закрытие MUST жить только в производных схемах авторинга
`schema/authoring/**`, которые пишет генератор `tools/close_schema.py`. Ручная правка
закрытой схемы запрещена: пара «открытая плюс закрытая», написанная руками, расходится ровно
тем дрейфом, ради ловли которого разделение и введено.

**TLP-28 (MUST, L1).** Перечислимое множество значений MUST выражаться формой `oneOf` из
`const`-ветвей известных значений плюс ветвь расширения с `pattern`. Голый `enum` допускается
только для действительно закрытого множества — такого, расширение которого автор считает
намеренно ломающим изменением.

**TLP-29 (MUST NOT, L1).** Автор ревизии MUST NOT применять в схемах ревизии `$dynamicRef`,
`$dynamicAnchor`, `prefixItems` и сетевой `$ref`: ни один из трёх разобранных таргетов не
сохраняет их семантику, а сетевой `$ref` запрещён нормой протокола. Рекурсивные структуры
выражаются обычным `$ref` на `$defs`.

**TLP-30 (MUST, L1).** `patternProperties` MUST применяться только там, где множество ключей
открыто по построению — карта расширений, `_meta`, вендорные пространства имён; там, где
ключи известны заранее, применяется `properties`. Строка действует при **условии T-3**
(`DR-02` §7): решение владельца в пользу сохранения кодогенерации пересматривает именно эту
строку, и только её — остальные правила раздела от него не зависят.

**TLP-31 (MUST, L1).** Пара или кортеж значений MUST выражаться объектом с именованными
полями (например `{algorithm, value}`), а не массивом фиксированной длины: позиционная форма
несовместима с добавлением поля и теряет семантику у генераторов.

**TLP-32 (MUST, L1).** Точная величина (денежная сумма, количество, любой счётчик) MUST
записываться целым числом в минорных единицах. Экспоненциальная запись числа в примерах,
векторах и golden-файлах запрещена: канонизация JCS фиксирует форму сериализации, и запись
вида `1e3` даёт расхождение байтов при том же значении.

**TLP-33 (MUST, L1).** Автор ревизии MUST отклонять схему, чья физическая глубина
schema-bearing узлов превышает 16. Корневая схема имеет глубину `0` и входит в число
подсхем. Ребро глубины и новая подсхема возникают только при переходе по schema-bearing
keywords: значениям карт `$defs`/`definitions`/`properties`/`patternProperties`/
`dependentSchemas`; одиночным схемам `items`/`contains`/`not`/`if`/`then`/`else`/
`additionalProperties`/`unevaluatedProperties`/`propertyNames`/`contentSchema`; элементам
массивов `allOf`/`anyOf`/`oneOf`/`prefixItems`.

**TLP-34 (MUST, L1).** Автор ревизии MUST отклонять схему, в которой число физических
подсхем превышает 256. Значения прочих ключей (`description`, `examples`, произвольные
данные) не считаются. `$ref` при этом не разыменовывается: сетевой `$ref` отвергается
отдельным правилом, локальные ссылки проверяются на офлайн-разрешимость; физический счёт не
превращается в обход потенциально циклического графа.

## 8. Схемы и примеры

`schema/tool-descriptor.json` описывает форму дескриптора, `schema/side-effect.json` —
классификацию эффекта и оба перечисления (`side_effect`, `confirmation`) единственным узлом
`$defs`, подключаемым ссылкой. Производные закрытые варианты живут в `schema/authoring/` и
сгенерированы `tools/close_schema.py`.

Пример 1 — инструмент чтения: гейт не требуется, идемпотентность применения неприменима
(фазы применения нет).

```json
// example: tool-descriptor.json
{
  "name": "crm_report_list",
  "title": "Список отчётов о работе",
  "description": "Purpose: Возвращает страницу отчётов сотрудника за период.\nCall when: Пользователю нужен список отчётов без изменения данных.\nRequired arguments: period\nExample: crm_report_list({\"period\":\"2026-07\"})",
  "inputSchema": {
    "type": "object",
    "properties": {
      "period": { "type": "string" },
      "cursor": { "type": "string" }
    }
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "items": { "type": "array" },
      "next_cursor": { "type": "string" }
    }
  },
  "annotations": {
    "readOnlyHint": true,
    "destructiveHint": false,
    "idempotentHint": true,
    "openWorldHint": false
  },
  "_meta": {
    "dev.agentools/action": {
      "side_effect": "read",
      "permissions_hint": ["crm.report.read"]
    }
  }
}
```

Пример 2 — инструмент необратимого действия: `destructiveHint` согласован с классом эффекта
(`TLP-10`), `confirmation` ужесточён явно (`TLP-14`), объявлена идемпотентность применения
(`TLP-15`) и метка происхождения аргумента (`TLP-24`).

```json
// example: tool-descriptor.json
{
  "name": "fina_payment_send",
  "title": "Отправить платёж",
  "description": "Purpose: Отправляет платёжное поручение во внешнюю систему.\nCall when: Подтверждённый платёж нужно необратимо передать провайдеру.\nRequired arguments: counterparty_id, amount_minor, purpose\nExample: fina_payment_send({\"counterparty_id\":\"cp_42\",\"amount_minor\":12500,\"purpose\":\"invoice-17\"})",
  "inputSchema": {
    "type": "object",
    "properties": {
      "counterparty_id": { "type": "string" },
      "amount_minor": { "type": "integer" },
      "purpose": { "type": "string" }
    },
    "required": ["counterparty_id", "amount_minor", "purpose"]
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "payment_id": { "type": "string" }
    }
  },
  "annotations": {
    "readOnlyHint": false,
    "destructiveHint": true,
    "idempotentHint": true,
    "openWorldHint": true
  },
  "_meta": {
    "dev.agentools/action": {
      "side_effect": "irreversible",
      "confirmation": "double_confirm",
      "idempotent_commit": true,
      "permissions_hint": ["fina.payment.send"],
      "content_origin": "untrusted_external"
    }
  }
}
```

Сумма записана целым числом в минорных единицах (`TLP-32`); `amount_minor` объявлен
`integer`, а не `number`, потому что величина точная.
