# 08 — Audit & Observability: собственная таксономия аудита, канонизация JCS, span links, стоимость, baggage

> Ревизия спеки: `2026-09` (состав и статус — `README.md`). Базис wire-протокола — MCP
> ревизии `2026-07-28`, зафиксированной пином `spec/vendor/mcp/2026-07-28/PIN.md`.
> Конвенции, глоссарий и уровни соответствия — `00_overview.md`; конверт события, свёртка и
> хеш-цепочка журнала — `03_action-lifecycle.md`; гейт перед записью и аудит решения —
> `04_confirmation.md`; сценарии, лимиты и компенсации — `06_scenarios.md`. Нормативные
> ключевые слова — по [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

Документ нормирует **аудит и наблюдаемость**: собственную таксономию аудит-событий, их место в
журнале действия, канонизацию JSON, которой пользуются дайджест дескриптора, ключ
идемпотентности, хеш-цепочка журнала и golden-сравнения, а также границу между записью,
доказывающей факт, и телеметрией, помогающей отладке.

Форму документа задают три факта. Первый: внешний словарь семантических соглашений для
атрибутов вызова модели **не стабилизирован** — ни один его атрибут не имеет статуса Stable, а
переименования идут через флаг совместимости; словарь такой зрелости нормативной схемой не
становится, поэтому схема аудита — собственная, а перевод в чужой словарь вынесен в отдельный
адаптер с собственной версией маппинга. Второй: метрики стоимости внешний словарь не даёт
вовсе, поэтому стоимость считается своей формулой из записанного потребления токенов. Третий:
ожидание решения по гейту измеряется часами и сутками, а span такой длительности не переживает
ни перезапуск процесса, ни агрегаты бэкенда — поэтому долгий гейт span не держит, а связывает
два span'а ссылкой через сохранённый в журнале контекст.
RAG:✅ 2026-07-26 — R-11 §12: атрибуты вызова модели вынесены в отдельный репозиторий
семантических соглашений, на июль 2026 **ни один из них не Stable** (все Development), переход
на новые имена — через opt-in флаг совместимости; метрики стоимости в словаре нет вовсе; для долгих
человеко-гейтированных операций практика — не держать span открытым, а связывать span links
через сохранённый trace-контекст; лимиты W3C Baggage — не более 64 элементов и не более
8192 байт суммарно.

Уровень документа по умолчанию — `L3` (`00_overview.md` §4). Объявленное отклонение одно:
раздел канонизации — `L1`, потому что от неё зависит паритет ключей идемпотентности и
дайджестов между двумя реализациями, а реализация уровня ядра пользуется ею с первого вектора.
Схема к документу — `schema/audit-event.json`; состояний и переходов документ не вводит.

## 1. Границы документа

Документ владеет таксономией аудит-событий и их местом в журнале, составом того, что в аудит не
попадает, полем корреляции трассировки, правилами span'ов вокруг гейта, собственной метрикой
стоимости, ограничениями baggage, канонизацией JSON и сериализационным видом golden-файла.

Он **не** нормирует: конверт события, свёртку и таблицу переходов (документ `03` — единственный
носитель), механику гейта и запись аудита решения (документ `04`), формулу ключа
идемпотентности и коды типизированных ошибок (документ `09`), процедуру двухступенчатого
сравнения golden и версионирование фикстур (документ `11`), срок хранения журнала, физическое
хранилище и модель доступа к нему (`00_overview.md` §9), реализацию адаптера экспорта (SDK).

Имя, состав и версия внешнего словаря телеметрии — внешний факт: ревизия нормирует **границу**
с ним и обязанности адаптера, а не содержание чужого словаря (`00_overview.md` `OVR-4`).

## 2. Аудит-событие и его место в журнале

**AOB-1 (MUST, L3).** Аудит-событие MUST быть записью **того же** журнала действия, что и
события жизненного цикла, и MUST нести конверт документа `03` (`ALC-5`) без добавлений: схема
аудита подключает определения конверта ссылкой и собственных определений его полей не заводит.
Второй журнал и второй конверт были бы вторым носителем одного факта, а сшивка двух
последовательностей по времени не восстанавливает порядок (`ALC-7`).

**AOB-2 (MUST, L3).** Вид аудит-события MUST записываться значением `kind` формы
`audit.<имя>` и MUST NOT входить в перечень видов событий раздела 3 документа `03`. Ось
состояний действия и таксономия аудита разведены намеренно: аудит отвечает на вопрос «что
произошло и по какому основанию», а не «в каком состоянии действие».

**AOB-3 (MUST NOT, L3).** Реализация MUST NOT выводить из аудит-события переход состояния
действия: в перечислении видов события документа `03` вид аудита проходит ветвью расширения,
поэтому свёртка обрабатывает его путём `ALC-15` — записывает целиком, занимает свой `seq`,
участвует в хеш-цепочке и состояния не меняет. Ни состояния, ни перехода документ не вводит, и
обязанность `ALC-14` здесь беспредметна.

**AOB-4 (MUST NOT, L3).** Реализация MUST NOT отвергать журнал из-за присутствия в нём
аудит-события и MUST NOT исключать аудит-события из нумерации `seq` и из хеш-цепочки. Изъятие
записи из цепочки делает цепочку непроверяемой ровно на том классе записей, ради которого она
и введена.

**AOB-5 (MUST NOT, L3).** Автор ревизии MUST NOT заводить вид аудита для факта, носитель
которого уже назван: решение по гейту записывается событием `confirmation_resolved` с телом
аудита решения (`CNF-40`), и второго носителя факта согласия ревизия не допускает (`CNF-41`).
То же относится к запросу, подтверждению и отказу внешнего эффекта (`ALC-24`).

## 3. Таксономия аудита

**AOB-6 (MUST, L3).** Перечисление видов аудит-события MUST быть **открытым** и выражаться
формой `oneOf` из `const`-ветвей известных значений плюс ветвь-расширение с шаблоном
продуктового префикса; единственный носитель перечисления — `schema/audit-event.json`.
Голое закрытое перечисление сделало бы добавление вида ломающим изменением автоматически.
Ветвь-расширение MUST исключать пространство `audit.`: вид ревизии удовлетворял бы двум
ветвям сразу, а значение, удовлетворяющее двум ветвям `oneOf`, схемой отвергается — открытость
перечисления обернулась бы отказом на собственных значениях.

**AOB-7 (MUST, L3).** Вид аудита MUST иметь **названного производителя** — правило ревизии,
при исполнении которого событие возникает (колонка «Производитель» таблицы ниже). Вид без
производителя в ревизии не заводится: точка расширения «на будущее» протухает к моменту, когда
реально понадобится (`OVR-5`).

**AOB-8 (MUST, L3).** Наблюдаемый факт MUST записываться видом и составом `payload` по таблице
ниже, и таблица MUST быть единственным носителем этого соответствия. Вид, не названный
таблицей и не разобранный реализацией, MUST обрабатываться по правилу must-ignore документа
`09`: записывается как наблюдался и состояния действия не меняет.

| `kind` | Производитель | Когда возникает | Обязательный `payload` |
|:--|:--|:--|:--|
| `audit.policy_evaluated` | `CNF-3`, `CNF-4`, `CNF-5` | вычислен вердикт политики по вызову | `tool_name`, `side_effect`, `verdict` |
| `audit.cost_recorded` | §H4 настоящего документа поверх `ALC-17` | записан результат вызова модели | `tokens_in`, `tokens_out`, `amount_minor`, `currency`, `price_table_version` |
| `audit.limit_exceeded` | `SCN-21` | превышен лимит вычислителя либо прогона | `limit_name`, `limit_value`, `observed` |
| `audit.scenario_run_finished` | `SCN-28` | прогон сценария завершён | `scenario_id`, `outcome` |
| `audit.compensation_executed` | `SCN-24`, `SCN-27` | шаг развёрнут компенсацией | `scenario_id`, `step_id` |

**AOB-9 (MUST, L3).** `audit.policy_evaluated` MUST записываться при каждом вычислении вердикта
политики и MUST нести имя инструмента, класс его побочного эффекта и сам вердикт. Событие
отвечает на вопрос «почему гейт не спрашивал», который иначе не имеет носителя: отсутствие
записи о вердикте неотличимо от отсутствия политики.

**AOB-10 (MUST, L3).** `audit.cost_recorded` MUST нести потребление токенов раздельно по входу
и выходу, вычисленную сумму целым в минорных единицах, код валюты и версию таблицы цен, по
которой сумма получена. Без версии таблицы сумма невоспроизводима: та же запись при другой
таблице даёт другое число, и расхождение читается как дефект реализации.

**AOB-11 (MUST, L3).** `audit.limit_exceeded` MUST нести имя лимита, его действовавшее значение
и наблюдённую величину. Типизированную ошибку превышения нормирует `SCN-21`; событие фиксирует,
**какой** лимит и **насколько** сработал, — без этого пересмотр лимитов по данным эксплуатации
опирается на догадку.

**AOB-12 (MUST, L3).** `audit.scenario_run_finished` MUST нести идентификатор сценария и исход
прогона из закрытого перечня `SCN-28`, а при остановленном развороте — идентификатор шага, на
котором разворот остановлен (`SCN-27`). Собственного журнала прогон сценария не заводит
(`SCN-2`), поэтому это событие есть единственная запись о его исходе.

**AOB-13 (MUST, L3).** `audit.compensation_executed` MUST нести идентификаторы сценария и
развёрнутого шага. Само исполнение компенсации есть действие со своим журналом (`SCN-2`);
событие фиксирует **принадлежность** развёрнутого шага прогону, которая из журнала отдельного
действия не выводится.

## 4. Что в аудит не попадает

**AOB-14 (MUST, L3).** `payload` аудит-события MUST состоять из идентификаторов, значений
перечислений, дайджестов и целых величин и MUST NOT нести сырой пользовательский текст,
значения аргументов вызова и тела доменных записей. Маскирование персональных данных —
обязанность вышестоящего шлюза контура; ревизия немаскированных персональных данных не хранит и
не переносит.

**AOB-15 (MUST, L3).** Денежная величина в `payload` MUST записываться целым в минорных
единицах вместе с кодом валюты по ISO 4217, и реализация MUST NOT записывать её числом с
плавающей точкой. Сериализация дробных чисел — сложная часть канонизации (`AOB-35`), и аудит её
избегает, оставаясь воспроизводимым между двумя реализациями.

**AOB-16 (MUST NOT, L3).** Аудит-событие MUST NOT нести токен подтверждения и любую его часть:
единственный носитель следа предъявления токена — запись аудита решения (`CNF-37`), и второй
след ревизии не нужен. Запрет адресован и производным носителям — телеметрии (`AOB-28`) и
baggage (`AOB-30`).

## 5. Корреляция трассировки

**AOB-17 (MAY, L3).** Запись журнала MAY нести блок корреляции `trace` с идентификатором
трассы и идентификатором span'а. Носителем блока является `payload`, а не новое поле конверта:
перечень полей конверта закрыт `ALC-5`, и поле, им не названное, живёт в `payload` по прямому
указанию того же правила.

**AOB-18 (MUST NOT, L3).** Реализация MUST NOT делать запись журнала зависимой от доступности
телеметрии: недоступность экспортёра MUST NOT препятствовать записи события и MUST NOT менять
её состав. Источник истины по комплаенсу — журнал, по отладке — телеметрия, и подмена первого
вторым теряет факт вместе с недоступным бэкендом.

**AOB-19 (MUST NOT, L3).** Реализация MUST NOT использовать идентификатор трассы как
идентификатор действия, как ключ идемпотентности или как основание дедупликации и MUST NOT
восстанавливать из телеметрии факты, отсутствующие в журнале. Поле введено для корреляции двух
картин, а не как второй идентификатор действия.

## 6. Span и долгий гейт

**AOB-20 (MUST, L3).** Span фазы подготовки MUST закрываться записью предложения
(`confirmation_requested`), а trace-контекст этого span'а MUST сохраняться в журнале блоком
`trace` (`AOB-17`). Сохранённый контекст — единственное, что связывает подготовку с применением
через ожидание произвольной длины.

**AOB-21 (MUST, L3).** На применении реализация MUST открывать **новый** span и MUST связывать
его с сохранённым контекстом ссылкой (span link), а не продолжать прежний span. Ссылка выражает
причинную связь двух завершённых отрезков работы; продолжение прежнего span'а выражало бы
непрерывную работу, которой не было.

**AOB-22 (MUST NOT, L3).** Реализация MUST NOT держать span открытым на время ожидания решения
по гейту и на время длинной операции. Срок ожидания решения измеряется часами и сутками
(`04_confirmation.md`), а span такой длительности не переживает перезапуск процесса и искажает
агрегаты бэкенда: наблюдаемость подменяется наблюдением за самим наблюдателем.

## 7. Стоимость

**AOB-23 (MUST, L3).** Стоимость действия MUST вычисляться реализацией из записанного
потребления токенов и **собственной** таблицы цен, версия которой записывается событием
(`AOB-10`). Внешний словарь телеметрии метрики стоимости не определяет, поэтому заимствовать
здесь нечего, а расхождение двух реализаций в сумме наблюдается как расхождение в деньгах.

**AOB-24 (MUST NOT, L3).** Реализация MUST NOT выводить стоимость из полей ответа контрагента,
не записанных в журнал, и MUST NOT пересчитывать записанную стоимость задним числом по новой
таблице цен. Событие фиксирует сумму на версию таблицы, действовавшую в момент записи;
пересчёт — производная витрина, а не правка факта (`ALC-31`).

## 8. Адаптер экспорта

**AOB-25 (MUST, L3).** Перевод записей журнала во внешний словарь телеметрии MUST выполняться
**отдельным адаптером**, версия маппинга которого версионируется независимо от ревизии. Словарь
атрибутов вызова модели не стабилизирован, и его переименования обязаны стоить смены версии
маппинга, а не смены ревизии.

**AOB-26 (MUST NOT, L3).** Схема аудит-события и правила ревизии MUST NOT содержать имён
атрибутов внешнего словаря телеметрии: имена живут в адаптере и только в нём. Проверяемое
следствие — изменение чужого словаря не порождает изменения ни одной схемы ревизии
(`AOB-27`).

**AOB-27 (MUST, L3).** Адаптер MUST употреблять только актуальные имена атрибутов словаря —
`gen_ai.provider.name` для поставщика модели, `input_tokens` и `output_tokens` для потребления
токенов — и MUST NOT употреблять их легаси-алиасы. Поддержка двух наборов имён сразу
воспроизводит ту самую неоднозначность, ради ухода от которой словарь вынесен за границу ядра.
RAG:✅ 2026-07-26 — R-11 §12: переименования `gen_ai.system` → `gen_ai.provider.name`,
`usage.prompt_tokens`/`completion_tokens` → `input_tokens`/`output_tokens`; переход через
opt-in `OTEL_SEMCONV_STABILITY_OPT_IN`, ни один атрибут не Stable.

**AOB-28 (MUST NOT, L3).** Адаптер MUST NOT выносить в телеметрию то, чего не хранит аудит
(`AOB-14`), и токен подтверждения (`AOB-16`). Телеметрия уходит за периметр контура и хранится
по чужой политике, поэтому её состав не может быть шире состава аудита.

## 9. Baggage

**AOB-29 (MUST, L3).** В baggage MUST помещаться только непрозрачные идентификаторы —
действия, тенанта, сценария. Значение непрозрачно: получатель не вправе выводить из него состав
работы, принадлежность и права.

**AOB-30 (MUST NOT, L3).** Реализация MUST NOT помещать в baggage персональные данные, значения
аргументов вызова и токен подтверждения либо любую его часть. Baggage распространяется по всем
исходящим вызовам контура автоматически, поэтому ошибка состава здесь утекает дальше и тише
любой другой.

**AOB-31 (MUST, L3).** Лимиты W3C — не более 64 элементов и не более 8192 байт суммарно — MUST
быть частью контракта реализации, и превышение MUST давать типизированную ошибку (документ
`09`), а не молчаливое усечение. Усечённый baggage теряет идентификатор корреляции незаметно
для обеих сторон.

## 10. Канонизация JSON (RFC 8785)

Канонизация — единственное место ревизии, где две независимые реализации обязаны совпасть
**побайтно**: от неё зависят дайджест дескриптора (`02_tool-contract-profile.md`), отпечаток
аргументов и ключ идемпотентности (документ `09`), вход хеш-цепочки журнала (`ALC-36`) и
golden-сравнения корпуса (документ `11`). Поэтому каждый инвариант ниже — отдельное правило:
формулировка «канонизация по RFC 8785» без перечня инвариантов не проверяется вектором и
расходится ровно в тех местах, где реализации языков расходятся по умолчанию.

**AOB-32 (MUST, L1).** Канонической формой JSON-значения ревизии MUST быть форма
[RFC 8785 (JCS)](https://www.rfc-editor.org/rfc/rfc8785), и второй канонической формы ревизия
не вводит. Уровень `L1`, потому что на этой форме стоят ключ идемпотентности и дайджест
дескриптора, которыми реализация уровня ядра пользуется с первого вектора.

**AOB-33 (MUST, L1).** Ключи объекта MUST сортироваться как последовательности кодовых единиц
UTF-16 беззнаковым сравнением, независимо от локали и таблиц сортировки; при совпадающем
префиксе более короткий ключ идёт раньше. Уровень `L1`, потому что порядок ключей входит в
байты, по которым сравниваются дайджесты двух реализаций.

**AOB-34 (MUST, L1).** Ключ, содержащий кодовую точку вне BMP, MUST сравниваться по своим
суррогатным парам, а не по кодовым точкам: порядок, полученный сравнением кодовых точек,
отличается от требуемого именно на этом классе ключей. Уровень `L1`, потому что это названное
место расхождения реализаций, и оно обязано быть покрыто вектором, а не соглашением.

**AOB-35 (MUST, L1).** Числа MUST сериализоваться по правилу ECMAScript `Number::toString`:
целое — без дробной части и незначащих нулей, значения вне диапазона фиксированной записи — с
экспонентой. Уровень `L1`, потому что сериализация чисел есть сложная часть алгоритма, и её
расхождение даёт разные байты на одинаковом входе.

**AOB-36 (MUST, L1).** Канонизация MUST отвергать `NaN` и бесконечности типизированной ошибкой
(документ `09`) и MUST NOT подставлять вместо них `null` или строку. Уровень `L1`, потому что
подстановка превращает необрабатываемое значение в правдоподобный дайджест, который вторая
реализация не воспроизведёт.

**AOB-37 (MUST, L1).** Канонизация MUST отвергать объект с дублирующимися ключами и MUST NOT
применять правило «последний выигрывает». Уровень `L1`, потому что выбор победителя — свойство
парсера языка, и два парсера выбирают по-разному на одном входе.

**AOB-38 (MUST NOT, L1).** Канонизация MUST NOT применять нормализацию Unicode ни к ключам, ни
к строковым значениям: строка сериализуется в том виде, в каком получена. Уровень `L1`, потому
что скрытая нормализация меняет байты входа и делает дайджест зависимым от библиотеки, а не от
значения.

**AOB-39 (MUST, L1).** Строки MUST экранироваться ровно так: `"` как `\"`, `\` как `\\`,
кодовые точки U+0008, U+0009, U+000A, U+000C и U+000D — короткими последовательностями
`\b`, `\t`, `\n`, `\f`, `\r`, прочие управляющие из диапазона U+0000…U+001F — формой `\u00hh`
со строчными шестнадцатеричными цифрами; остальные кодовые точки записываются как есть в UTF-8
без экранирования. Уровень `L1`, потому что регистр шестнадцатеричных цифр и выбор между
короткой и числовой формой дают разные байты при одинаковом значении.

**AOB-40 (MUST, L1).** Массивы MUST сохранять исходный порядок элементов; литералы MUST
записываться как `null`, `true` и `false`; между токенами канонической формы MUST NOT быть
пробелов, переводов строк и отступов. Уровень `L1`, потому что форматирующие пробелы — умолчание
сериализаторов обоих языков, и без запрета они попадают в дайджест.

**AOB-41 (MUST, L1).** Выход канонизации MUST быть последовательностью байтов UTF-8 без метки
порядка байтов. Уровень `L1`, потому что метка порядка байтов добавляется редакторами и
библиотеками молча и сдвигает весь дайджест.

**AOB-42 (MUST, L1).** Соответствие канонизации MUST проверяться **свойством результата** —
байтовым равенством канонической формы на названном входе, — а не именем употреблённой
библиотеки; выбор библиотеки есть дело реализации. Уровень `L1`, потому что вектор корпуса
обязан быть исполним для обеих реализаций, а имя библиотеки исполнимым требованием не является.

**AOB-43 (MUST, L1).** Автор корпуса ревизии MUST включить в него официальные тест-векторы
RFC 8785 и **отдельный** вектор с ключами вне BMP (`AOB-34`). Уровень `L1`, потому что без
этого вектора самое известное место расхождения реализаций остаётся непроверенным, а
соответствие уровня ядра — заявленным, но не доказанным.

**AOB-44 (MUST, L1).** Golden-файл ревизии MUST быть канонической формой в UTF-8 без метки
порядка байтов, с переводами строк `LF` и **ровно одним** завершающим переводом строки;
процедуру двухступенчатого сравнения и версионирование фикстур нормирует документ `11`. Уровень
`L1`, потому что это сериализационный вид того же канонического результата, и его расхождение
неотличимо от расхождения самой канонизации.

## 11. Схемы и примеры

`schema/audit-event.json` описывает аудит-событие и владеет перечислением видов аудита и формой
блока корреляции трассировки. Конверт подключается **ссылкой** на `schema/lifecycle-event.json`:
собственных определений полей конверта схема аудита не заводит, а перечисляет их состав,
объявляя, что аудит-запись несёт тот же конверт (`AOB-1`). Производный закрытый вариант живёт в
`schema/authoring/` и сгенерирован `tools/close_schema.py`.

Пример 1 — вердикт политики по вызову write-инструмента: гейт требуется классом эффекта, и
запись объясняет основание (`AOB-9`).

```json
// example: audit-event.json
{
  "event_id": "ev-4c8d-0003",
  "action_id": "act-4c8d",
  "seq": 3,
  "expected_prev_seq": 2,
  "ts": "2026-09-11T07:41:19.204Z",
  "actor": { "type": "system", "id": "runtime-policy" },
  "kind": "audit.policy_evaluated",
  "event_version": 1,
  "spec_rev": "2026-09",
  "payload": {
    "tool_name": "fina_payment_send",
    "side_effect": "irreversible",
    "verdict": "ask"
  }
}
```

Пример 2 — стоимость записанного вызова модели: сумма целым в минорных единицах с кодом валюты
и версией таблицы цен, блок корреляции сохранён в `payload` (`AOB-10`, `AOB-15`, `AOB-17`).

```json
// example: audit-event.json
{
  "event_id": "ev-4c8d-0004",
  "action_id": "act-4c8d",
  "seq": 4,
  "expected_prev_seq": 3,
  "ts": "2026-09-11T07:41:23.870Z",
  "actor": { "type": "agent", "id": "agent-fina-1" },
  "kind": "audit.cost_recorded",
  "event_version": 1,
  "spec_rev": "2026-09",
  "payload": {
    "tokens_in": 4180,
    "tokens_out": 512,
    "amount_minor": 1240,
    "currency": "RUB",
    "price_table_version": "2026-09-01",
    "trace": {
      "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
      "span_id": "00f067aa0ba902b7"
    }
  }
}
```

Пример 3 — исход прогона сценария, разворот которого остановлен провалом компенсации: запись о
самом исходе прогона существует только здесь (`AOB-12`, `SCN-27`, `SCN-28`).

```json
// example: audit-event.json
{
  "event_id": "ev-4c8d-0011",
  "action_id": "act-4c8d",
  "seq": 11,
  "expected_prev_seq": 10,
  "ts": "2026-09-11T07:44:02.501Z",
  "actor": { "type": "system", "id": "runtime-scenario" },
  "kind": "audit.scenario_run_finished",
  "event_version": 1,
  "spec_rev": "2026-09",
  "payload": {
    "scenario_id": "fina.month_close",

```
