# 04 — Confirmation: политика гейта, предложение, токен, решения, аудит решения

> Ревизия спеки: `2026-08` (состав и статус — `README.md`). Базис wire-протокола — MCP
> ревизии `2026-07-28`, зафиксированной пином `spec/vendor/mcp/2026-07-28/PIN.md`.
> Конвенции, глоссарий, уровни соответствия и единая модель `side_effect` — `00_overview.md`;
> форма дескриптора и `descriptor_digest` — `02_tool-contract-profile.md`; состояния действия и
> таблица переходов — `03_action-lifecycle.md`. Нормативные ключевые слова — по
> [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

Документ нормирует **гейт перед записью**: как решается, нужен ли он, как он устроен, чем
предъявленное пользователю предложение связано с тем, что будет исполнено, и что остаётся в
аудите после решения. Это центральное продуктовое требование ревизии и самый большой кусок,
которого нет в протоколе.

Токен применения — не параллельный механизм: протокол сам предписывает для состояния,
переживающего границу вызова, «explicit, server-minted handles passed as ordinary tool
arguments», и токен подтверждения есть ровно эта форма. Гейт же не выражается механизмом
уточнений: уточнение живёт внутри одного логического вызова и не переживает рестарт, а
подтверждение висит часами и сутками.
RAG:✅ 2026-07-26 — R-11 §7, §9: анти-tampering между превью и применением нативно не даёт ни
один из шести разобранных agent-фреймворков (готовый примитив есть только у Stripe: «тот же
ключ и другие параметры — ошибка»); срок ожидания решения не документирует ни один (LangGraph
дословно — «waits indefinitely»); режим «четырёх глаз» не документирует ни один; таксономии
аудита решения как нормативного требования нет нигде.

Уровень документа по умолчанию — `L1` (`00_overview.md` §4). Объявленное отклонение ровно одно:
dual control — `L3`. Схемы к документу — `schema/confirmation.json` и
`schema/decision-audit.json`.

---

## 1. Границы документа

Документ владеет политикой гейта, предложением, токеном, решениями, сроком ожидания, dual
control и аудитом решения. Он **не** нормирует: коды ошибок и их формат (документ `09`),
состояния действия и переходы между ними (документ `03` — здесь только ссылки на маркеры),
уточнения и их биндинг (документ `05`), реализацию подписи токена (фазы SDK), модель прав
контуров-потребителей (вне ревизии).

**CNF-1 (MUST NOT, L1).** Реализация MUST NOT выражать подтверждение механизмом уточнений:
уточнение не переживает рестарт, число его раундов и долговечность состояния запроса гарантиями
протокола не покрыты, и подтверждение, ожидающее сутки, через него невыразимо. Разведение
двух примитивов — предмет документа `05`.

## 2. Policy Layer: нужен ли гейт

Раздел отвечает на один вопрос — **требуется ли подтверждение**. Механики гейта он не касается:
правило этого раздела ссылается на Protocol Layer только явной ссылкой на маркер.

**CNF-2 (MUST, L1).** Входом политики MUST быть класс побочного эффекта инструмента
`side_effect` и объявленная политика инструмента `confirmation`
(`02_tool-contract-profile.md` `TLP-12`, `TLP-14`); требование гейта по умолчанию выводится по
таблице `00_overview.md` §6. Второго входа политика не имеет: аннотации дескриптора входом не
являются (`02_tool-contract-profile.md` `TLP-11`).

**CNF-3 (MUST, L1).** Вердикт политики MUST быть ровно одним из закрытого перечня `deny`,
`ask`, `allow`. Перечисление закрыто: добавление вердикта есть намеренно ломающее изменение,
выходящее новой датированной ревизией по окну депрекации `00_overview.md` `OVR-24`.

**CNF-4 (MUST, L1).** При нескольких применимых правилах политики результат MUST вычисляться по
precedence `deny` → `ask` → `allow`: `deny` побеждает `ask`, `ask` побеждает `allow`. Порядок
объявления правил и их текстовая специфичность на исход MUST NOT влиять — иначе два рантайма
дают разные ответы на одном и том же наборе правил.

**CNF-5 (MUST, L1).** Правила разных уровней области видимости (контур, тенант, пользователь,
инструмент) MUST сводиться применением `CNF-4` ко множеству вердиктов **всех** уровней.
Правило «ближайший уровень выигрывает» запрещено: оно позволяет узкому уровню отменить `deny`
широкого.

**CNF-6 (MUST NOT, L1).** Политика MUST NOT ослаблять требование гейта, выведенное из класса
эффекта: ужесточение допустимо, ослабление — нет (`00_overview.md` `OVR-20`). Для класса
`irreversible` отказ от гейта запрещён любой политикой и любым уровнем области видимости.

**CNF-7 (MUST, L1).** Отсутствие применимого правила политики MUST трактоваться как вердикт,
выведенный из класса эффекта, а не как `allow`. Пустая политика — это «как предписано классом
эффекта», и никогда «разрешено всё».

**CNF-8 (MUST NOT, L1).** Реализация MUST NOT переносить в Policy Layer решения о механике
гейта — состав превью, свойства токена, перечень решений, форму аудита. Смешение слоёв в одном
разделе — задокументированный источник расхождения реализаций, и разделение введено против
него.

## 3. Protocol Layer: подготовка, превью, применение

**CNF-9 (MUST, L1).** Подготовка и применение действия MUST исполняться **одним** инструментом:
имя инструмента одно, фаза различается аргументом вызова. Второго инструмента-применителя
ревизия не вводит — иначе каталог инструментов удваивается, а политика и права начинают
описываться дважды.

**CNF-10 (MUST, L1).** Фаза подготовки MUST быть детерминированной и MUST NOT применять эффект:
она вычисляет превью и записывает предложение. Недетерминированный ввод, использованный при
подготовке, журналируется (`03_action-lifecycle.md` `ALC-17`), чтобы превью воспроизводилось.

**CNF-11 (MUST, L1).** Превью предложения MUST нести: перечень изменений с указанием сущности и
её идентификатора, точные величины целым числом в минорных единицах
(`02_tool-contract-profile.md` `TLP-32`), перечень предупреждений и идентификатор предложения с
его версией. Превью — то, что предъявляется человеку, поэтому «сводка в свободной форме» вместо
перечня изменений формой превью не является.

**CNF-12 (MUST, L1).** Применение MUST исполнять ровно то, что описано превью предложения,
идентифицированного предъявленным токеном. Расхождение MUST быть отказом, а не «более точным
исполнением»: инвариант «показанное есть исполненное» и есть смысл гейта.

**CNF-13 (MUST NOT, L1).** Реализация MUST NOT выводить требование гейта заново на фазе
применения из аргументов вызова: требование выведено политикой на подготовке и зафиксировано
предложением. Повторно на применении проверяются **права** (`CNF-35`), а не необходимость гейта.

## 4. Токен подтверждения

**CNF-14 (MUST, L1).** Токен MUST быть непрозрачным для вызывающего и для модели: его структура
ревизией не документируется, и разбор токена на стороне вызывающего запрещён. Наблюдаемы только
факт наличия токена и исход его предъявления.

**CNF-15 (MUST, L1).** Токен MUST быть защищён от подделки и MUST покрывать `action_id`,
`principal` — субъекта, допущенного к применению, — `tool_name`, `descriptor_digest`,
`args_fingerprint`, `expires_at` и `proposal_version`. Конкретный алгоритм защиты ревизией не
нормируется: он есть свойство рантайма, а нормируются проверяемые свойства токена и различимые
отказы `CNF-18`…`CNF-21`.

**CNF-16 (MUST, L1).** Токен MUST быть одноразовым: успешное применение MUST погашать токен, и
повторное предъявление того же токена MUST быть отказом (`CNF-20`), а не повторным применением.

**CNF-17 (MUST NOT, L1).** Токен MUST NOT передаваться иначе, чем обычным аргументом вызова
инструмента: передача через метаданные сообщения, заголовки транспорта или состояние соединения
запрещена. Это ровно та форма, которую предписывает протокол для состояния, живущего между
вызовами.

**CNF-18 (MUST, L1).** Применение MUST отклонить токен, чей `args_fingerprint` не совпадает с
fingerprint фактически предъявленных аргументов. Это подмена аргументов между превью и
применением, и она MUST быть отказом независимо от того, «безопаснее» ли новые аргументы.

**CNF-19 (MUST, L1).** Применение MUST отклонить токен, срок которого истёк, и этот отказ MUST
возвращаться как ошибка исполнения инструмента, а не как протокольная ошибка — чтобы модель
могла самостоятельно повторить подготовку и предъявить новое предложение человеку.

**CNF-20 (MUST, L1).** Применение MUST отклонить токен, предъявленный повторно, — включая
случай, когда первое предъявление завершилось отказом контрагента: погашение токена есть
свойство предъявления, а не успеха.

**CNF-21 (MUST, L1).** Применение MUST отклонить токен, предъявленный принципалом, отличным от
покрытого токеном. В режиме dual control (`CNF-32`) токеном покрывается субъект, допущенный к
применению, поэтому правило действует без исключений.

**CNF-22 (MUST, L1).** Каждый из четырёх отказов `CNF-18`, `CNF-19`, `CNF-20` и `CNF-21` MUST
быть различим отдельным кодом ошибки (коды нормирует документ `09`). Подмена одного отказа
другим или общим кодом запрещена: неразличимые отказы делают попытку подмены аргументов
наблюдаемо равной штатной просрочке.

**CNF-23 (MUST, L1).** Применение MUST сверить `descriptor_digest`, покрытый токеном, с
дайджестом текущего дескриптора инструмента и при несовпадении дать отдельный класс ошибки
дрейфа дескриптора (`02_tool-contract-profile.md` `TLP-22`), а не один из четырёх отказов выше:
изменился инструмент, а не предъявленные аргументы или субъект.

## 5. Предложение, его версия и решения

**CNF-24 (MUST, L1).** Предложение MUST быть версионируемой единицей гейта: оно несёт
`proposal_id` и `proposal_version`, и версия принадлежит **предложению**, а не действию. У
одного действия за его жизнь MAY быть несколько предложений, каждое со своим токеном.

**CNF-25 (MUST, L1).** Решение по гейту MUST быть одним из `approve`, `reject`, `revoke`,
`expire`. Перечисление открытое в смысле документа `09`: неизвестное значение решения получатель
MUST трактовать как **не разрешающее** — must-ignore не ослабляет гейт.

**CNF-26 (MUST NOT, L1).** Правка аргументов решением по гейту НЕ является: она MUST порождать
новое предложение с новым токеном и новым превью, а прежнее предложение MUST переходить в
состояние `superseded` (в терминах `DR-01` §B3 — `SUPERSEDED`). Правка предложения на месте
уничтожает инвариант `CNF-12`, и именно поэтому «редактирование» не входит в перечень решений.

**CNF-27 (MUST, L1).** Состояние предложения MUST быть одним из закрытого перечня `pending`,
`approved`, `rejected`, `revoked`, `expired`, `superseded`. Это состояния **предложения**;
состояния действия и допустимые переходы между ними нормирует документ `03`
(`ALC-11` и таблица `ALC-T1`…`ALC-T22`), и второго перечня состояний действия здесь нет.

**CNF-28 (MUST NOT, L1).** Реализация MUST NOT изменять записанное предложение — ни его
аргументы, ни превью, ни срок. Изменение выражается новым предложением по `CNF-26`.

## 6. Срок ожидания решения

**CNF-29 (MUST, L1).** Предложение MUST нести `expires_at` — дедлайн ожидания решения.
Предложение без дедлайна невалидно: ожидание «неопределённо долго» ревизией не допускается, и
это тот системный пробел индустрии, который ревизия закрывает нормой.

**CNF-30 (MUST, L1).** Истечение срока MUST переводить действие в терминальное состояние
истечения переходом `ALC-T14` документа `03`, а решение MUST записываться значением `expire`
события `confirmation_resolved`. Отдельного вида события для истечения ревизия не вводит: два
носителя одного факта разошлись бы молча.

**CNF-31 (MUST, L1).** Значение срока MUST быть конфигурируемым по классу побочного эффекта и
MUST NOT быть константой реализации. Срок ожидания решения и срок дедупликации применения
(документ `09`) — **разные** таймеры и MUST NOT выводиться один из другого.

## 7. Dual control

**CNF-32 (MAY, L3).** Для класса побочного эффекта `irreversible` реализация MAY включить режим
dual control. Уровень `L3`, потому что режим есть усиление процедуры, а не условие взаимной
работы двух реализаций: SDK без него остаётся полноценным на ядре, и вектор ядра его не
требует.

**CNF-33 (MUST, L3).** В режиме dual control субъект, инициировавший подготовку, и субъект,
допущенный к применению, MUST быть разными принципалами, и проверка MUST быть рантаймовым
инвариантом допуска к применению, а не рекомендацией текста. Уровень `L3`, потому что правило
действует только там, где режим включён (`CNF-32`), и без него беспредметно.

**CNF-34 (MUST NOT, L3).** Реализация MUST NOT считать dual control выполненным на основании
различия ролей субъектов: сравниваются идентификаторы принципалов. Совпадение идентификаторов
при разных ролях есть один и тот же человек, а смысл режима — второй человек. Уровень `L3`,
потому что уточняет проверку `CNF-33`.

## 8. Повторная авторизация на применении

**CNF-35 (MUST, L1).** Права субъекта MUST проверяться независимо на подготовке **и** на
применении. Между фазами проходит произвольное время, и права могли быть отозваны — это
классическая гонка проверки и использования.

**CNF-36 (MUST NOT, L1).** Реализация MUST NOT трактовать результат подготовки — предложение,
превью или токен — как разрешение и MUST NOT кэшировать его как разрешение. Токен доказывает,
**что** согласовано, и не доказывает, что субъект всё ещё вправе это исполнить.

## 9. Аудит решения

**CNF-37 (MUST, L1).** Решение по гейту MUST порождать обязательную запись аудита решения с
полями `proposal_id`, `token`, `decision`, `actor_id`, `actor_role`, `decided_at`, `reason`,
`args_hash_at_decision` и `args_hash_at_commit`. Перечень — минимум: реализация MAY добавить
поля, но MUST NOT опустить ни одно из перечисленных.

**CNF-38 (MUST, L1).** `args_hash_at_decision` и `args_hash_at_commit` MUST быть значениями
одного и того же вычисления `args_fingerprint` (документ `09`), взятыми в двух точках времени —
на момент решения и на момент применения. Их равенство MUST быть рантаймовым инвариантом допуска
к применению: при несовпадении применение MUST быть отклонено тем же отказом, что и `CNF-18`.
Второго способа сверить аргументы ревизия не вводит.

**CNF-39 (MUST, L1).** `args_hash_at_commit` MUST быть заполнен только для решения `approve`,
дошедшего до применения; при решениях `reject`, `revoke` и `expire` отсутствие значения есть
нормативная форма записи, а не пропуск поля.

**CNF-40 (MUST, L1).** Запись аудита решения MUST быть телом события `confirmation_resolved`
журнала действия (`03_action-lifecycle.md` `ALC-24` описывает соседний вид события, конверт —
`ALC-5`), а не отдельным хранилищем: факт согласия человека обязан иметь **один** носитель.

**CNF-41 (MUST NOT, L1).** Реализация MUST NOT держать факт согласия во втором источнике истины
— отдельной таблице решений, кэше интерфейса, поле доменной сущности. Проекция для чтения
допустима, источник истины один — журнал действия (`03_action-lifecycle.md` `ALC-1`).

## 10. Схемы и примеры

`schema/confirmation.json` описывает предложение с превью и владеет закрытыми перечислениями
состояния предложения и вердикта политики. `schema/decision-audit.json` описывает запись аудита
решения и владеет открытым перечислением решений — оба перечисления живут единственным узлом
`$defs` и подключаются ссылкой. Производные закрытые варианты живут в `schema/authoring/` и
сгенерированы `tools/close_schema.py`.

Пример 1 — предложение, записанное фазой подготовки: вердикт политики ужесточён относительно
выведенного из класса эффекта (`CNF-6`), превью несёт точную величину целым в минорных единицах
(`CNF-11`), срок ожидания задан (`CNF-29`).

```json
// example: confirmation.json
{
  "proposal_id": "prop-7f31-1",
  "proposal_version": 1,
  "action_id": "act-7f31",
  "tool_name": "fina_payment_send",
  "state": "pending",
  "expires_at": "2026-08-05T09:14:22Z",
  "args_fingerprint": "sha-256:4d1a9f0c8b7e6d5c4b3a29180f7e6d5c4b3a29180f7e6d5c4b3a29180f7e6d5c",
  "descriptor_digest": "sha-256:1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718293a4b5c6d7e8f90a",
  "policy": {
    "effect": "ask",
    "source_scope": "tenant",
    "hardened": true
  },
  "preview": {
    "summary": "Отправка платёжного поручения контрагенту ООО «Ромашка»",
    "changes": [
      {
        "entity": "payment",
        "entity_id": "pay-draft-118",
        "field": "amount_minor",
        "after": 1450000
      }
    ],
    "warnings": [
      "Действие необратимо: отзыв платежа средствами контура невозможен"
    ]
  }
}
```

Блок ниже — **информативный**, а не нормативный пример (`00_overview.md` `OVR-18`): схемы
