## 1. Executive summary

**Общая оценка.** Для проекта возрастом ~2 месяца и единственного автора зрелость необычно высокая: `declare(strict_types=1)` + `final readonly` везде, PHPStan `level: max`, Infection (mutation testing), shared-fixtures между PHP/Dart/reference, подписанный HS256-токен подтверждения с «закрытым» набором claim'ов, hash_equals, ограничением размера, проверкой дубликатов ключей и канонического round-trip, PostgreSQL-арбитры через UNIQUE-ограничения, lease-fencing, SHA-пины всех GitHub Actions, `permissions: {}` по умолчанию, `persist-credentials: false`, дайджест-проверка скачиваемых сканеров, собственный policy-checker для workflow. Парсер выражений сценариев — «настоящий» парсер + tree-walker с лимитами, без `eval`. Это сильная база; ниже — то, что отделяет её от «идеала».

**Главная проблема — не код, а процесс вокруг кода:**

1. **CI на GitHub фактически не работает**: все job'ы последних запусков `ci`, `private-rc`, `extended` на `main` и на всех PR Dependabot завершаются `failure` за 2–5 секунд, **без единого шага** (`steps: []`, `runner_id: 0`). То есть все ваши многоуровневые гейты (supply-chain, OSV, gitleaks, matrix, conformance) в облаке не отработали по существу. Причина не определена (подозреваю биллинг/лимит минут или политику Actions — **[гипотеза]**), но это нужно починить первым.
2. **`main` не защищена**, нет обязательных проверок/ревью, GitHub secret scanning/push protection/Dependabot security updates выключены, коммиты не подписаны, тегов и релизов нет. Dependabot-PR'ы висят 6–12 дней.
3. **Репозиторий раздут артефактами процесса**: `plans/` ≈ 14 МБ (в т.ч. файлы по 1,8–2,1 МБ и дубли), сгенерированные отчёты/SBOM/receipts, локальные состояния Cursor (`php/.cursor/state/*.jsonl`), конфигурация чужой экосистемы (`.agents/plugins`, `.swissknifeman`, `.serena`, `.claude`…). Это затрудняет ревью, сканирование секретов и сопровождение.

**Главные находки по безопасности (в коде SDK):**

- `CredentialGuard::validateAccessToken()` по умолчанию доверяет эмитенту `'issuer-trusted'` (тестовая константа в production-классе), доверяет самодекларируемым полям `integrity=verified`/`audience`, а `rejectTokensInArguments()` проверяет только один уровень вложенности аргументов.
- Эталонный `RegistryToolPort` (образец для интеграторов) разрешает вызов, если у дескриптора **нет** `permissions_hint` (default-allow), не валидирует аргументы по `inputSchema` и не оборачивает исключения обработчика.
- `IdempotencyCoordinator` делает один `heartbeat` *до* вызова инструмента, без таймаута и без обработки `Throwable` → при долгой/упавшей операции возможен takeover lease'а и повторный побочный эффект.
- Секреты подписи (`SigningKey::$secret`, `HmacTokenSigner::$secret`) не помечены `#[\SensitiveParameter]` — могут попасть в стектрейсы/логи.
- Runtime-защита от prompt-injection через вывод инструментов (`content_origin = untrusted_external`) в прочитанном коде SDK только *валидируется как значение* в `ActionProfile`; по поиску кода GitHub других использований в `php/src` не найдено (индекс поиска мог быть неполным — **[гипотеза]**).

**Что делать в первую очередь (≈ 1–2 дня):** (1) выяснить и устранить причину падения Actions; (2) включить ruleset на `main` (PR + обязательные checks + запрет force-push + подписанные коммиты); (3) исправить `CredentialGuard` и default-allow в `RegistryToolPort`; (4) `#[\SensitiveParameter]`; (5) вынести `plans/`+генерируемые артефакты из основного репозитория; (6) положить production-DDL Postgres в пакет (сейчас он лежит в `fixtures/`, а `docs/migrations.md` утверждает обратное).

## 4. Раздел 2 — Безопасность

### 4.1 Модель угроз и что уже закрыто [подтверждено]
Хорошо: `eval/unserialize/shell_exec/proc_open` в прочитанных файлах `php/src` не встречаются (**полный grep по всему дереву не выполнялся**: код не клонировался); SQL — только prepared statements с именованными параметрами, все константы `*_SQL` статичны; `PublishedSchemaValidator` читает схемы только из локального каталога и регистрирует их в локальном резолвере; в `TokenEnvelope` — закрытый список claim'ов, запрет `alg: none`, жёсткий `HS256`, `hash_equals`, лимит 8 КБ, `json_decode` с глубиной 2, отклонение дубликатов ключей, сравнение канонической формы с исходной строкой, окно skew ≤ 300 с, `HARD_MAX_LIFETIME` 7 дней; `SigningKey` требует ≥ 32 байт; идемпотентность — UNIQUE-арбитры + fence-токены; `ExpressionEvaluator` — лимиты длины/глубины/узлов/коллекций, без `eval`.

Классы SSRF/path traversal/shell-injection в SDK неприменимы напрямую: SDK не делает сетевых запросов и не исполняет команды (единственная FS-операция — `glob`/`file_get_contents` в доверенном каталоге схем). Это **ответственность интегратора** — и SDK мог бы помочь, см. SEC-2/SEC-4.

### 4.2 Находки

**SEC-1 (P1/S). `CredentialGuard` — заглушка в production-классе.** [подтверждено] `php/src/Ops/CredentialGuard.php`:
1. `validateAccessToken(array $credential, array $trustedIssuers = ['issuer-trusted'])` — значение по умолчанию это фикстурная строка. Интегратор, забывший передать список, получит «доверенного эмитента» `issuer-trusted`. Нужен fail-closed: пустой список по умолчанию → всегда отказ.
2. `rejectionReason()` доверяет полям самого `$credential`: `audience`, `source`, `issuer`, **`integrity === 'verified'`**. Класс не проверяет подпись/JWKS — он проверяет *заявление о проверке*. Если массив собирает недоверенный код (или он пришёл из аргументов инструмента), защита пустая. Класс должен принимать *уже верифицированный* объект (value object, создаваемый только в доверенном верификаторе), а не `array`.
3. `rejectTokensInArguments()` обходит `$arguments` на **один** уровень: `is_array($value) && ($value['kind'] ?? null) === 'access_token'`. Токен, вложенный глубже (`{"a":{"b":{"kind":"access_token"}}}`), проходит. Нужен рекурсивный обход с лимитом глубины.
4. Контекст ошибки содержит `'stimulus_pointer' => '/given/driver_state/credentials/0/audience'` — JSON-указатель на фикстуру conformance в production-ответе. Утечка тестовой обвязки в контракт SDK.
```php
// Предлагаемое направление
final readonly class VerifiedAccessToken { // создаётся только верификатором
    private function __construct(public string $issuer, public string $audience, public string $subject) {}
    public static function fromVerified(/* результат проверки подписи */): self { /* … */ }
}
final class CredentialGuard {
    /** @param non-empty-list<string> $trustedIssuers  — без значения по умолчанию */
    public function __construct(private array $trustedIssuers, private string $audience) {
        if ($trustedIssuers === []) { throw new \InvalidArgumentException('trustedIssuers is required'); }
    }
    public function assertAcceptable(VerifiedAccessToken $t): void { /* issuer/audience */ }
    /** @param array<array-key,mixed> $args */
    public function assertNoTokensIn(array $args, int $maxDepth = 8): void { /* рекурсивно */ }
}
```
*Стандарт:* RFC 8725 (JWT BCP) — явный allow-list алгоритмов, проверка `iss`/`aud`, не доверять данным без верификации.

**SEC-2 (P1/M). Эталонный реестр инструментов небезопасен по умолчанию.** [подтверждено] `php/reference/Adapters/RegistryToolPort.php`:
- `isPermitted()`: `$required = $descriptor->actionProfile->permissionsHint ?? []; if ($required === []) { return true; }` — **default-allow**. Забытый `permissions_hint` делает инструмент доступным всем (и в `discover()`, и в `call()`). Название «hint» вводит в заблуждение: оно используется как *enforcement*.
- `call()` не валидирует `$arguments` по `$descriptor->inputSchema` (хотя в SDK есть `opis/json-schema` и `PublishedSchemaValidator`) и не проверяет, что результат `handler(...)` — `ToolExecutionResult` (есть только `@var`-аннотация).
- Исключения обработчика не перехватываются (`IdempotencyCoordinator` ловит только `ToolExecutionException`), нет таймаута, лимита размера результата, редактирования секретов в ответе.
- Субъект (`$principals`, `$authorization`) хранится в экземпляре через `bindSubject()` — небезопасно для долгоживущих воркеров (RoadRunner/Swoole/queue), где один экземпляр обслуживает разных субъектов.

Это каталог `reference/` (не попадает в production-архив), но именно его будут копировать интеграторы, и аналога в `src/` нет.
*Решение:* добавить в `src/` production-реестр и диспетчер (см. FLX-1):
```php
interface ToolHandler { public function handle(array $args, CallContext $ctx): ToolExecutionResult; }
final class ToolDispatcher implements ToolPort {
    public function call(string $tool, array $args, string $key, CallContext $ctx): ToolExecutionResult {
        $entry = $this->registry->get($tool);
        if ($entry === null) { return self::failure(ErrorCategory::NOT_FOUND, ToolErrorCode::ToolNotFound); }
        if (!$this->policy->allows($ctx->subject, $entry->descriptor)) {            // default-DENY
            return self::failure(ErrorCategory::PERMISSION, ToolErrorCode::ToolNotAllowed);
        }
        $this->validator->assertValid($args, $entry->descriptor->inputSchema);       // JSON Schema 2020-12
        try { $r = $this->withDeadline($ctx, fn () => $entry->handler->handle($args, $ctx)); }
        catch (\Throwable $e) { $this->logger->error('tool failed', ['tool' => $tool, 'e' => $e]);
                                return self::failure(ErrorCategory::INTERNAL, ToolErrorCode::ToolFailed); }
        $this->limits->assertResultSize($r);
        return $r;
    }
}
```
*Стандарты:* OWASP LLM06:2025 Excessive Agency (минимум функциональности и прав, авторизация вниз по потоку, HITL для высокорисковых действий); MCP Tools spec (серверам следует валидировать входы, применять контроль доступа, ограничивать частоту и санитизировать выход).

**SEC-3 (P1/M). Lease-fencing не покрывает длинные/упавшие вызовы.** [подтверждено] `IdempotencyCoordinator::invoke()`:
- `heartbeat()` вызывается один раз *перед* `$this->tools->call()`. Дефолтная аренда — `PT30S`; инструмент, работающий дольше, теряет lease: другой воркер сделает `takeover` (`TAKEOVER_SQL … lease_until <= :now`). Для `NativeKey`-инструментов takeover → повторный вызов; для остальных → `ambiguousEffect`. Исходный воркер при `complete()` получит `lostLease` и вернёт вызывающему **ошибку при том, что эффект мог быть применён**.
- Нет таймаута вызова (`ToolPort` не принимает deadline) и нет `try/finally`: `Throwable` из инструмента (кроме `ToolExecutionException`) оставляет запись `in_progress` до истечения аренды, повторная попытка клиента получит `concurrent_in_flight`.
*Решение:* (1) `CallContext` с deadline; `lease ≥ deadline + запас`; (2) периодический heartbeat (в PHP — воркер/`Fiber`/`pcntl_alarm`, либо обязать инструмент вызывать `$ctx->renew()`); (3) `catch (\Throwable)` → `fail($lease, StoredToolResult(error: INTERNAL))` + возврат `failure`; (4) документировать `lostLease` как «эффект неизвестен» (сейчас — категория `conflict`/retryable, что провоцирует повтор).

**SEC-4 (P1/M). Prompt-injection через результаты инструментов.** [подтверждено частично] В `ActionProfile` поле `content_origin` допускает `untrusted_external` или `vendor.value`, но по GitHub code search (`untrusted_external` в `php/src`) найден **только** `ActionProfile.php`; в `ConfirmationService`, `ScenarioRunner`, `ToolExecutionResult` использований нет (в прочитанных файлах). То есть признак есть, а *поведения*, которое из него следует, в SDK не видно (**[гипотеза]**: возможна реализация в непрочитанных файлах/Dart; индекс code search мог быть неполным).
Что требует OWASP LLM01:2025 и cheat-sheet: разделять инструкции и недоверенные данные, ограничивать привилегии после чтения недоверенного контента (dual-LLM / quarantine), человеческое подтверждение для действий высокого воздействия, структурный вывод вместо свободного текста.
*Решение:* ввести «taint»-флаг на `ToolExecutionResult` (`provenance: untrusted_external`) и правило оркестратора: *если в сессии есть результат с `content_origin=untrusted_external`, то любой последующий инструмент с `side_effect ∈ {write, irreversible}` требует `ConfirmationService`* (даже если дескриптор говорит `confirmation: none`). Покрыть фикстурой в `fixtures/` (чтобы PHP/Dart вели себя одинаково). Результаты, возвращаемые в LLM, оборачивать маркером источника и лимитировать по размеру.

**SEC-5 (P1/S). Секреты в стектрейсах.** [подтверждено] `SigningKey::__construct(…, string $secret, …)` и `HmacTokenSigner::__construct(private string $secret)` — без `#[\SensitiveParameter]`; в `SigningKey` свойство `public string $secret` (readonly, но публичное) попадёт в `var_dump/print_r`/сериализацию логгеров. PHP ≥ 8.2 умеет редактировать параметры в бэктрейсах (у вас `php >= 8.3`).
```php
final readonly class SigningKey {
    public function __construct(
        public KeyId $id,
        public string $algorithm,
        #[\SensitiveParameter] private string $secret,   // private + accessor
        public KeyState $state = KeyState::Active,
    ) { /* … */ }
    public function mac(string $input): string { return hash_hmac('sha256', $input, $this->secret, true); }
    public function __debugInfo(): array { return ['id' => $this->id, 'algorithm' => $this->algorithm]; }
}
```
Тогда `TokenEnvelope` вызывает `$key->mac(...)`, а не читает `->secret`. Примечание: атрибут не действует на параметры *интерфейсных* методов (ставить на реализации). Также в `HmacTokenSigner` нет проверки длины ключа (в `SigningKey` — ≥ 32 байт) — непоследовательно; а `TokenEnvelope` вызывает `hash_hmac` напрямую, минуя порт `Contracts\TokenSigner`.

**SEC-6 (P2/M). Самописный токен и три «канонизатора».** [подтверждено] `TokenEnvelope` реализует собственный формат `at1.<b64(json)>.<b64(hmac)>` («JWT-подобный, но не JWT»), собственный canonical JSON (`canonicalJson`, `encodeString` — **третья** реализация канонизации наряду с `Canonicalizer` (RFC 8785) и классом `JsonObjectNameValidator`) и **второй** сканер дубликатов ключей (`rejectDuplicateNames`/`readJsonString`/`skipJsonValue`). Защитные слои хороши (канонический round-trip в `parse()` закрывает расхождения парсеров), но поддерживать три однотипных парсера — риск расхождения.
Замечания к деталям (**[гипотеза]**, нужен тест): `unb64()` использует `base64_decode(..., true)` — строгий режим PHP может не отвергать ненулевые «хвостовые» биты, поэтому для MAC-части возможны несколько строковых представлений одного токена (защита: `record->tokenDigest !== digestToken($token)` в `ConfirmationService::commit` и `jti`-арбитр — материальной уязвимости не вижу, но «malleability» стоит закрыть: перекодировать и сравнить). `ksort($claims)` для числоподобных ключей в PHP 8 сравнивает числом — для вашего фиксированного набора ключей безопасно.
*Рекомендации:* (1) вынести дубли в один `JsonStrictScanner` и один канонизатор; (2) оценить PASETO v4 (`paragonie/paseto`) — версионированный формат без выбора алгоритма — как замену `at1`, либо зафиксировать в спецификации, что `at1` — осознанно минимальный профиль, и заказать независимый ревью; (3) fuzz/property-based тесты парсера (mutation testing у вас уже есть, но он проверяет тесты, а не входы).
*Стандарт:* RFC 8725 §3.1 (алгоритмы), проверка `iss`/`aud`, явная типизация токенов (у вас это `purpose`).

**SEC-7 (P2/S). Порядок «consume → authorize».** [подтверждено] В `ConfirmationService::commit()` вызов `$this->store->consume(...)` стоит **до** `resolvePolicy`/approval/`authorize`. Любой отказ политики или авторизации «сжигает» одноразовый токен; пользователь вынужден заново проходить `prepare`. Это fail-closed и, возможно, намеренно (исход фиксируется `refineOutcome`), но тогда документируйте: *отказ ≠ повторяемая попытка*. Исход выводится `str_contains($failure->error->code, 'policy'|'authorization')` — хрупкая строковая эвристика; для `approval_*`, `quorum_*`, `separation_*`, `principal_mismatch` исход остаётся `presented`. Замените на `ConfirmationFailure::outcome(): ConsumeOutcome` (enum) и добавьте исходы approval-ветки (в DDL `CHECK (outcome IN (…))` — только 4 значения, нужна миграция). Также лишний `try { … } catch (ConfirmationFailure $f) { throw $f; }` вокруг `TokenEnvelope::parse` (так же в `LongOperationCoordinator::observeTaskStatus`) — удалить.

**SEC-8 (P2/S). Скачивание и распаковка сканеров.** [подтверждено] `tools/ci_matrix.py::install_cli_tool`:

**SEC-9 (P2/S). Dev-хуки Cursor.** [подтверждено] `.cursor/hooks.json` регистрирует лишь `security.safe-dirs` (`failClosed: true`) — разумно, а `DEVELOPMENT.md` честно называет его «узким guardrail, а не sandbox». Но по коду `lifecycle.py`: `_safe_dirs` проверяет **только первый токен** команды (`_first_command_token(command) not in {"rm","rmdir"}` → `allow`), поэтому `ls && rm -rf x`, `sh -c 'rm …'`, `find -delete`, `git clean -fdx` проходят; модуль `safedirs.py` загружается через `spec.loader.exec_module` из путей **вне репозитория** (`packages/harness/...` либо жёсткий fallback `~/projects/packages/swissknifeman/...`); незарегистрированный `_review_gate` выполняет `bash -c <check_command>` из `~/.claude/hooks/review-gate/config.json`. **SEC-10 (P2/S). `AuditRedaction`.** [подтверждено] Работает по *именам* ключей: allow-list (`ALLOW`) + суффиксы `_id`/`_digest` + deny-list. Значения не проверяются: `customer_email_id => "ivan@example.com"` пройдёт; ключ `trace` разрешён с любым значением (в т.ч. вложенным массивом). `DENY` избыточен (всё вне `ALLOW` и так отвергается); `redactDocument()` *молча удаляет* ключи из `DENY`, но *бросает* на прочих неизвестных — две разные политики в одном классе. Рекомендуется: типизированные события аудита (readonly DTO вместо `array`), значения `*_id` — по regex `^[A-Za-z0-9._:-]{1,128}$`, `trace` — строго `traceparent` (W3C).

**DB-1 (P1/S). **DB-2 (P1/M). Postgres-схема и адаптеры.** [подтверждено/гипотезы]
1. *Индексы под обслуживание.* `PdoPostgresIdempotencyStore::CLEANUP_SQL` — `DELETE … WHERE state='completed' AND expires_at < :now`; `PdoPostgresConfirmationTokenStore::CLEANUP_SQL` — `WHERE expires_at + make_interval(secs => :retention_seconds) < :now`. Индексов на `expires_at` в DDL нет (только PK/UNIQUE), второй запрос ещё и несаргабелен (выражение над колонкой). Перепишите: `WHERE expires_at < :now - make_interval(secs => :retention_seconds)` + `CREATE INDEX … ON confirmation_consumed_tokens (expires_at)`; для leases — частичный индекс `WHERE state='completed'`. (Ваш контракт запрещает *partial unique* индексы на неистекших строках — обычный частичный индекс для DELETE-скана это не нарушает.)
2. *Append-only и изоляция тенантов — только комментарием.* DDL события: «Application DELETE is forbidden». Принудите на уровне БД: `REVOKE UPDATE, DELETE, TRUNCATE ON agentools_events FROM app_role;` + триггер `BEFORE UPDATE OR DELETE … RAISE EXCEPTION`. Для мультитенантности — Row-Level Security: `ALTER TABLE … ENABLE ROW LEVEL SECURITY; … FORCE ROW LEVEL SECURITY; CREATE POLICY … USING (tenant_id = current_setting('app.tenant_id', true)) WITH CHECK (tenant_id = current_setting('app.tenant_id', true))` и `SELECT set_config('app.tenant_id', :t, true)` в начале транзакции (transaction-local — безопасно с пулами). Сейчас «тенант» — просто часть ключа; ошибка в одном запросе приложения = утечка между тенантами.
3. *`PDO` мутируется адаптером.* Все три конструктора вызывают `$pdo->setAttribute(ATTR_ERRMODE, ERRMODE_EXCEPTION)` на соединении вызывающего — скрытый побочный эффект на общее соединение. Лучше проверить `getAttribute(ATTR_ERRMODE) === ERRMODE_EXCEPTION` и бросить `InvalidArgumentException`, либо документировать.
4. *Время и hash-chain* **[гипотеза]**: `ts` — `TIMESTAMPTZ`; `PdoPostgresEventStore::hydrate()` → `timestamp()` → `(new DateTimeImmutable($value))->format(DATE_ATOM)`. Postgres отдаёт `timestamptz` в часовом поясе *сессии*, поэтому строка при чтении может отличаться от записанной (`Z` vs `+03:00`). Если `ActionEvent::hashInput()` включает `ts` (не читал), то `tailEvent()` → `$chain->hash($previous)` даст хэш, зависящий от `TimeZone` сессии. Проверка: интеграционный тест с `SET TIME ZONE 'Europe/Moscow'` vs `'UTC'` на append+load+verify chain. Страховка: всегда `setTimezone(UTC)` при `hydrate` либо хранить `ts` как `TEXT` в каноническом формате.
5. *`global_position` через `IDENTITY`.* Нумерация по sequence не совпадает с порядком коммита транзакций; если появятся подписчики/проекции, читающие «по возрастанию `global_position`», они могут пропускать запоздало закоммиченные строки. Для текущего SDK (подписок нет) — заметка на будущее **[гипотеза]**.
6. *Повторяющийся код.* Хелперы `assoc/stringField/intField/intValue` скопированы в `PdoPostgresEventStore` и `PdoPostgresIdempotencyStore` → `final class RowReader`.

## 5. Раздел 3 — Паттерны проектирования

### 5.1 Что хорошо [подтверждено]
- **Порты и адаптеры**: `Contracts\ToolPort`, `LlmPort`, `Clock`, `TokenSigner`, `ConfirmationTokenStore`, `IdempotencyStore`, `EventStore` — интерфейсы в `Contracts`, реализации `PdoPostgres*` и in-memory (testkit). DI — через конструктор, глобального состояния/синглтонов нет.
- **Result-тип вместо исключений на границе инструмента**: `ToolExecutionResult` (success/failure) + `ToolExecutionException` как транспорт ошибки внутри; `ToolErrorCode` — enum (45 кейсов в формате `agentools.<category>.<name>`) с `category()`, `retryable()`.
- **Неизменяемость**: `final readonly class`, именованные конструкторы (`ConfirmationFailure::because(...)`), `private __construct` у value-объектов.
- **Версионирование событий**: `EventUpcasterChain`; `ExtensionNegotiator`, «open enum + MustIgnoreEnvelope», GREASE-векторы в фикстурах — зрелый подход к эволюции протокола.
- **Закрытое выражение-DSL** вместо `eval`: `ExpressionEvaluator` (лексер → парсер → walker) с `ExpressionLimits`.
- Идентификаторы правил (`SEC-3`, `SCN-13`, `LOP-10`, `TLP-18`) в исключениях — отличная трассируемость к спецификации.

### 5.2 Находки

**DES-1 (P1/S) [гипотеза]. Ключ идемпотентности в `ScenarioRunner`.** `idempotencyKey = "{$scenarioId}:{$stepId}"` (+ скоуп таблицы `(tenant, tool, key)`). Ключ не содержит идентификатора запуска/действия. Два разных запуска одного сценария с теми же шагами в одном тенанте получат один и тот же ключ → второй запуск вернёт сохранённый результат первого (либо `keyReuse`, если аргументы отличаются). Если это ожидаемая семантика («сценарий идемпотентен на уровне тенанта») — задокументируйте; иначе включите `actionId`/`runId` и номер попытки ретрая (для `retryable` ошибок ключ должен быть стабилен в рамках одной логической попытки). Проверьте по спецификации сценариев.

**DES-2 (P2/M). Контекст вызова и политика повторов.**
- `ToolPort::call(string $tool, array $arguments, string $idempotencyKey)` — нет `CallContext` (deadline, `traceparent`, principal/tenant, cancellation, `attempt`). Из-за этого `RegistryToolPort` держит субъекта в состоянии экземпляра (`bindSubject`), `IdempotencyCoordinator` не может прокинуть deadline, а трассировка невозможна.
- Ретраи `ScenarioRunner`: счётчик `attempt`, но без задержки (backoff + jitter) и без ограничения общим дедлайном; решение о повторе — по политике шага, а не по `ToolExecutionResult->error->retryable`. Мёртвая ветка `if ($action === 'continue')` в `handleFailure` (остальные значения отсечены раньше); лимит `64` захардкожен в двух местах.
- `LongOperationCoordinator` хранит состояние в полях (`$taskId`, `$status`…) — один экземпляр = одна операция, в имени и документации это не отражено.
```php
interface ToolPort {
    public function call(CallRequest $request, CallContext $ctx): ToolExecutionResult;
}
final readonly class CallContext {
    public function __construct(
        public Subject $subject, public TenantId $tenant, public ?\DateTimeImmutable $deadline,
        public ?TraceParent $trace, public int $attempt = 1, public ?CancellationToken $cancel = null,
    ) {}
}
interface RetryPolicy { public function delayFor(int $attempt, ToolExecutionResult $failure): ?\DateInterval; }
// ExponentialBackoff(base: 200ms, factor: 2, max: 10s, jitter: full) — "AWS full jitter"
```

**DES-3 (P2/S). Время.** `Contracts\Clock` (в `ConfirmationService`), `?\Closure $clock` (в `IdempotencyCoordinator`), прямое `new DateTimeImmutable('now')` по умолчанию, и параметр `$now` в методах Pdo-хранилищ. Унифицируйте под **PSR-20 `Psr\Clock\ClockInterface`** (де-факто стандарт, `symfony/clock`, `lcobucci/clock` и др. реализуют) — вместо собственного `Clock`; в Pdo-классах не принимать `$now` снаружи, где можно взять время из БД (`now()`), иначе возможен рассинхрон часов PHP и Postgres относительно `lease_until`.

**DES-4 (P2/M). Ошибки.**
- `RegistryToolPort` создаёт коды вне enum (`agentools.permission.missing_subject`, `.invalid_subject`, `.tool_not_allowed`, `agentools.not_found.tool`), хотя в SDK есть `ToolErrorCode` — архитектурный тест (`phpat`/`deptrac` или простой `rg`) «только `ToolErrorCode`» это закроет.
- `ErrorCategory` — класс со строковыми константами, а `ToolErrorCode` — enum; категории тоже должны быть enum (с `Tool*`-проекцией в строку для JSON).
- `ConfirmationService` — 14 параметров конструктора (god-constructor): сгруппируйте в `ConfirmationConfig` (readonly DTO) и `ConfirmationCollaborators`. То же: `ScenarioLimits`, `IdempotencyConfig` (сейчас `leaseDuration`, `?\Closure $clock`… передаются россыпью).
- Для `Throwable` из чужого кода — единая «граница»: ловить, логировать с `trace_id`, возвращать `INTERNAL` без утечки сообщения.

**DES-5 (P2/S). Дубли и обходы.**
- `Ops\MetricCardinality` — обёртка над `Persistence\MetricCardinality` с теми же методами. Оставить один.
- `Schema/Canonicalizer.php` содержит два публичных класса (`Canonicalizer` и `JsonObjectNameValidator`) — нарушение PSR-4 «один класс — один файл» (работает только пока класс подгружается вторым после первого); автозагрузчик в классмапе (`optimize-autoloader`/`classmap-authoritative`) может не найти `JsonObjectNameValidator`.
- `LongOperationCoordinator::forbiddenProgressKeys()` собирает запрещённые слова конкатенацией (`'pro'.'gress_'.'pct'`), чтобы собственный `spec_lint` не срабатывал на литерал. Лучше исключение из линтера (allowlist на файл/строку) или константа в одном месте с pragma-комментарием, чем обфускация в коде.
- AST выражений (`ExpressionEvaluator`) — массивы со строковыми типами узлов; перейти на `readonly` узлы (sealed-иерархия: `Literal`, `Path`, `BinaryOp`, `Call`…) — PHPStan проверит исчерпывающий `match`.

### 5.3 Наблюдаемость [подтверждено отсутствие в прочитанном]
Нет интеграции с PSR-3 (`LoggerInterface`) и каких-либо span/метрик на границе вызова инструмента (есть `MetricCardinality` как *защита* от высокой кардинальности — это хорошо, но самих метрик нет). Стандарт — OpenTelemetry GenAI semantic conventions: span `execute_tool {gen_ai.tool.name}`, атрибуты `gen_ai.operation.name=execute_tool`, `gen_ai.tool.name`, `gen_ai.tool.call.id`, `gen_ai.tool.type`; аргументы/результаты инструмента (`gen_ai.tool.call.arguments/result`) — **opt-in** (могут содержать чувствительные данные), что хорошо сочетается с вашим `AuditRedaction`. Реализация: декоратор `TelemetryToolPort implements ToolPort` (PSR-3 + опциональный OTel Tracer), значения в атрибутах — только после `AuditRedaction`.

### 5.4 Типизация и конфигурация
Сильная сторона — PHPStan `max` и `strict_types`. Резервы: `LlmPort::respond(array): array` — нетипизированный контракт на самой чувствительной границе (нужны `LlmRequest/LlmResponse`, `ToolCall`, `Usage`), `array`-аргументы с `@param array<string,mixed>` везде, где можно ввести DTO. Конфигурация — конструкторные параметры без единого объекта конфигурации и без валидации «в одном месте»; для PHP-пакета-библиотеки это нормально, но рекомендуется публиковать `*Config` readonly DTO с `fromArray()` (валидирует) — удобно для Symfony/Laravel-бриджей.

## 6. Раздел 4 — Гибкость и расширяемость

### 6.1 Как сегодня добавляется инструмент [подтверждено по `php/API.md`, `RegistryToolPort`]
1. Автор вручную собирает `ToolDescriptor` (`name`, `description`, `inputSchema`, `outputSchema`, `annotations`, `actionProfile`) — валидация строгая, выполняется в конструкторе.
2. Регистрирует `ToolDescriptor` + handler-замыкание в `RegistryToolPort` (из `reference/`, **не** из production-пакета).
3. Дайджест дескриптора (`DescriptorDigest`) используется для drift-контроля.
Нет автогенерации схемы из типов/атрибутов, нет сканирования каталога, нет container-интеграции (PSR-11), нет бриджей в Symfony/Laravel.

### 6.2 Находки

**FLX-1 (P2/M). Нет production-реестра, генерации схем и «проекций» под провайдеров.**
- Добавить в `src/`: `ToolRegistry` (immutable, строится билдером), `ToolDispatcher` (SEC-2), `ToolHandler`/`CallContext`.
- Генерация дескриптора из PHP: атрибут `#[Tool(name:, sideEffect:, ...)]` на классе-обработчике + `#[Param(description:)]` на свойствах DTO аргументов → `JsonSchemaGenerator` (reflection; образец — Symfony AI/`opis`, LLPhant, `php-mcp/server`). Схема — JSON Schema 2020-12 (MCP default dialect).
- Проекции: `toMcpTool()` (`name`, `title`, `description`, `inputSchema`, `outputSchema`, `annotations`), `toOpenAiFunction(strict: true)`, `toAnthropicTool(strict: true)`. У OpenAI и Anthropic *strict-режим* требует `additionalProperties: false` и все свойства в `required` (опциональность — через `["T","null"]`) → добавьте `assertStrictCompatible(array $schema)` и тест на всех дескрипторах в `fixtures/`.
- Провайдер-агностичность: `LlmPort` оставить минимальным, но типизировать; адаптеры OpenAI/Anthropic/Gemini/OpenAI-compatible — отдельными пакетами (`agentools/llm-openai`…) во избежание тяжёлых зависимостей в ядре.
- MCP: в репозитории есть вендоринг MCP schema `2026-07-28` и клиентский транспорт Dart (`agentools_mcp_dart`, поверх `mcp_dart`), conformance-прогон против официального набора. **Серверная сторона MCP и любой MCP-слой для PHP отсутствуют** (по прочитанному). Если цель — «инструменты, которые можно подключить как MCP-сервер», стоит либо написать тонкий мост к официальному PHP SDK MCP (актуальность и API проверить: на момент аудита я его не изучал), либо документировать, что проект — «контрактный слой» поверх существующих MCP-реализаций.

**FLX-2 (P2/S). `ToolDescriptor` слишком жёсткий.** [подтверждено]
- Описание обязано быть из 4 строк `Purpose / Call when / Required arguments / Example` — отличный стандарт для *своих* инструментов, но чужие MCP-инструменты (сторонние серверы) импортировать нельзя. Предлагаю два профиля валидации: `Authoring` (строгий) и `Import` (мягкий, с предупреждениями).
- `annotations` проверяются как `array_keys($annotations) !== ['readOnlyHint','destructiveHint','idempotentHint','openWorldHint']` — порядок ключей важен, `annotations.title` (допустим в MCP) запрещён, а любые будущие аннотации спецификации MCP — нет.
- `side_effect` — строка; `match` в `assertAnnotationsMatchEffect` имеет `default => null` и молча принимает неизвестное значение (расширяемость vs строгость — решите осознанно). Нужен enum `SideEffect` + `vendor.*` расширения через `ExtensionNegotiator`.
- Имя: `^[a-z][a-z0-9]*(_[a-z0-9]+)+$`, ≤ 64 символов — строго уже, чем MCP (SHOULD 1–128, `A-Za-z0-9_-.`) и допускает только snake_case с минимум двумя сегментами (`search` нельзя, `search_docs` можно). Это подмножество, совместимое с лимитами провайдеров (в документации OpenAI/Anthropic имена ограничены символами `a-zA-Z0-9_-` и 64 знаками — **числа я не сверял построчно в этой сессии**, проверьте перед ссылкой в спецификации). Решение разумное; задокументируйте *почему* и оставьте путь маппинга внешних имён (`.`/`-` ↔ `_`) с хранением оригинала.

**FLX-3 (P2/S). Состав `DescriptorDigest`.** [подтверждено] В дайджест входят name, description, inputSchema, outputSchema и `extension` (ActionProfile). `annotations`, `title`, остальные `_meta` — **нет**. Изменение `destructiveHint`/`idempotentHint`/`openWorldHint` (важные для безопасности подсказки клиентам) drift-детектором не ловится. Если это сознательно (TLP-18 в спецификации) — отметьте в `API.md`; иначе включите. Парой — рекомендация MCP Tools: аннотации считать недоверенными, пока сервер не доверенный; это же применимо к «pinning» дескрипторов против rug-pull.

**FLX-4 (P2/M). Версионирование контрактов инструментов.** Сильное: датированные ревизии спецификации, `spec_rev`, upcaster'ы событий. Недостаёт: версии **самого инструмента** (поле `_meta["dev.agentools/version"]`, semver) и `deprecated`/`replacedBy`; автоматической проверки обратной совместимости JSON Schema (`oasdiff`-подобно: удаление поля/сужение типа/новый required = breaking) в CI между релизами; политики «имя неизменно, новая мажорная версия — новое имя». Расширение `dev.agentools/action` предполагает владение доменом `agentools.dev` (см. NM-1).

**FLX-5 (P2/S). Dart ↔ PHP паритет.** [подтверждено частично] Один `ToolDescriptor` определён и в `schema`, и в `tool` Dart-пакета — экспорт требует `hide ToolDescriptor` в `lib/agentools.dart`; в публичный API экспортирован `src/smoke.dart` (см. NM-2). Выделите единственный источник типа.

### II.1.2 Вывод: наиболее вероятная причина — ограничение биллинга/аккаунта для GitHub-hosted раннеров (вероятность ~75–80 %)
Совокупность «job создаётся, но `runner_id = 0`, `steps = []`, провал через 2–5 с, 2 аннотации у упавших job'ов, падения с самого первого запуска» — это стандартная картина, когда GitHub не запускает job на hosted-раннере из-за платёжных ограничений организации (неоплаченный счёт/сбой платежа, исчерпанный бюджет/spending limit, у приватных репозиториев нет включённых минут на тарифе). Типичный текст аннотации в таком случае: *«The job was not started because recent account payments have failed or your spending limit needs to be increased. Please check the 'Billing & plans' section in your settings»* — **текст аннотаций я прочитать не смог** (эндпоинт `check-runs/{id}/annotations` для приватного репозитория требует авторизации, соответствующего инструмента в подключённых коннекторах нет), поэтому это *сильная, но не подтверждённая* версия. Косвенно согласуется то, что служебные Dependabot-job'ы проходят (насколько мне известно, они не тарифицируются как обычные минуты; в этой сессии это не проверялось).

## II.2. CONF-1 (новая, P0/P1): conformance «проходит» по таблице ответов, а не по поведению

**Что найдено [подтверждено чтением кода].**
- `conformance/adapters/reference/CompiledReference.php`: константа `PAYLOAD` — ~36 КБ `base64(zlib(JSON))`; `resolve()` считает `sha256` от канонизированного `{spec_rev, spec_rule_ids, given, script}` и **возвращает готовый ответ** (`observations`, `tool_calls`, `events`, `final_state`, `error`) из этой таблицы. `ReferenceEngine::run()` в первую очередь вызывает `CompiledReference::resolve()` и «проигрывает» (`replay`) найденное; настоящая логика (`action()`, `journal()` …) выполняется **только для векторов, которых нет в таблице**.
- `conformance/adapters/reference/adapter.php`, ветка `golden_pair`: `$canonical = $pair['golden']; emit([... 'canonical' => $canonical, 'canonical_golden' => $pair['golden']])` — адаптер **возвращает эталон как собственный результат** (комментарий: «Reference adapter owns the canonicalization result; the runner only compares bytes»).
- `php/conformance/SdkConformanceEngine.php`: **та же схема для PHP SDK** — `SdkProjectionCatalog::resolve(...)` (файл `php/conformance/SdkProjectionCatalog.php`, 36 221 байт ≈ размер `CompiledReference.php`, 36 220 байт) вызывается первым, и `replay()` идентичен по структуре. Реальные классы SDK (`ActionReducer`, `GatePolicy`, `CredentialGuard`, `ScenarioRunner`, …) используются лишь для векторов вне каталога. То же по именам файлов в Dart: `dart/agentools/conformance/sdk_projection_catalog.dart`, `sdk_projection_payload.dart` (34 КБ).
- `conformance/README.md` при этом утверждает: «Эталонный адаптер … не является источником семантики: нормой остаются замороженные ревизия и корпус», и `adapter.php`: «presentation metadata fixture не может стать oracle для SUT». Фактически ответы (то есть `expect`) вшиты в таблицу в сжатом виде, ключом служит хэш входа.

**Что я не проверил (поэтому формулировка осторожная).** Не декодировал таблицы (нет локальной копии), не знаю, какая доля векторов в них покрыта (возможно, все 213), не читал `bin/semantic-parity` и `bin/harness-selftest` (могут частично компенсировать) и не знаю, как каталоги генерируются (возможно, генератор запускает настоящий SDK и «замораживает» результат — тогда это snapshot-тестирование, а не fake, но тогда оно не ловит регрессии, пока каталог не пересоздан).

**Почему важно.** Зелёный `conformance` для PHP/Dart не доказывает, что SDK ведёт себя по спецификации: он проверяет, что таблица воспроизводит саму себя. Вектор `security-007` (`untrusted_content_selected_tool`) — пример: в исходниках SDK строки причины нет, значит ожидаемый ответ может приходить только из каталога.

**Как исправить.**
1. Запретить в адаптерах SUT lookup-ветку: PHP/Dart-адаптеры вызывают только реальные классы SDK; каталог остаётся лишь у *reference*-адаптера и используется как *oracle раннера*, а не как SUT.
2. Добавить в отчёт раннера поле `source: engine|catalog` на вектор и гейт `catalog_share == 0` для SDK.
3. «Мутационный» самотест: в CI намеренно ломать SDK (например, `GatePolicy` всегда `Allow`) и проверять, что конкретные векторы краснеют (`bin/harness-selftest` расширить этим).
4. Переименовать reference в «answer-key replay» в README, чтобы текст не противоречил коду.

final class CredentialGuard
{
    /** @param list<string> $trustedIssuers */
    public function __construct(private readonly array $trustedIssuers, private readonly string $audience = 'agentools')
    {
        if ($trustedIssuers === []) {
            throw new \InvalidArgumentException('trustedIssuers must not be empty (fail-closed)');
        }
    }
    /** @param array<array-key,mixed> $arguments */
    public function rejectTokensInArguments(array $arguments, int $depth = 0): ?ToolExecutionResult
    {
        if ($depth > 16) { return self::tooDeep(); }                  // fail-closed на сверхглубокую вложенность
        foreach ($arguments as $value) {
            if (is_array($value)) {
                if (($value['kind'] ?? null) === 'access_token') { return self::tokenInArguments(); }
                if (($r = $this->rejectTokensInArguments($value, $depth + 1)) !== null) { return $r; }
            }
        }
        return null;
    }
}
