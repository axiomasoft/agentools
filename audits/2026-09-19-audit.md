Итоговый вердикт: **у Agentools уже сильное протокольное ядро, необычно хорошая спецификационная дисциплина и серьёзный conformance-контур, но это пока не “идеальный публичный пакет”**. Главные проблемы находятся не в количестве функций, а в безопасной публичной границе, долговечности confirmation/idempotency, атомарности хранилищ, разделении внутренних и публикуемых артефактов, межъязыковой эволюции API и воспроизводимом выпуске.

> Ниже — статический аудит ветки `main` по состоянию на 19 сентября 2026 года. Он основан на исходниках и проектных материалах репозитория, но не включает выполненный в локальном clean checkout прогон тестов, mutation testing и нагрузочные испытания. Поэтому утверждения о текущем коде точны, а выводы о runtime-поведении требуют подтверждения предлагаемыми тестами.

# Аудит Agentools

## Исполнительное резюме

Сильнейшая сторона проекта — подход «спецификация → правила → fixtures → conformance → две реализации». Внутренний статус заявляет 213/213 проверок для PHP и Dart, общий уровень L3, отдельные негативные адаптеры, frozen-ревизию `2026-08`, event journal, idempotency, confirmation, security и reference slice. Это существенно зрелее типичного раннего open-source SDK: [status.md](https://github.com/axiomasoft/agentools/blob/main/plans/AGENTOOLS/status.md).

Однако сам план проекта подтверждает, что терминальная фаза публикационной подготовки ещё не начата: P11 имеет статус 0/4 и должна отдельно доказать intentional public API, clean-checkout reproducibility, consumer smoke и отсутствие следов внутреннего фазового процесса в пакетах. То есть текущий репозиторий сам корректно признаёт, что conformance-ready и package-ready — разные состояния: [P11.md](https://github.com/axiomasoft/agentools/blob/main/plans/AGENTOOLS/phases/P11/P11.md).

Наиболее опасная техническая зона — `ConfirmationProtocol`. Сейчас безопасность вызова частично определяется значениями, которые передаёт сам вызывающий код:

- `now`;
- `principal`;
- `currentDescriptor`;
- `CommitAuthorizer`;
- `proposerId`;
- `dualControl`;
- `DecisionAudit`.

Такой API не является safe-by-construction. Некорректный интегратор может случайно или намеренно отключить dual control, подставить старое время, использовать permissive authorizer или передать неподходящий descriptor digest: [ConfirmationProtocol.php](https://github.com/axiomasoft/agentools/blob/main/php/src/Confirmation/ConfirmationProtocol.php).

Вторая критическая зона — anti-replay. Потраченные confirmation tokens хранятся в приватном массиве процесса:

```php
/** @var array<string, true> */
private array $spentTokens = [];
```

После рестарта состояние исчезает; несколько PHP-процессов не делят его между собой; операция check-then-set не является межпроцессно атомарной; массив не очищается и растёт до уничтожения объекта. Для production confirmation protocol это должно быть заменено на durable atomic consume.

Третья зона — контракт идемпотентности. `resolve()` и `complete()` разделены, при этом `complete()` не получает lease/fencing token. Это оставляет crash window между внешним эффектом и записью результата, а также позволяет устаревшему worker завершить запись после takeover: [IdempotencyStore.php](https://github.com/axiomasoft/agentools/blob/main/php/src/Contracts/IdempotencyStore.php).

# Главные блокеры

## P0: dual-control bypass

Текущая проверка:

```php
if ($dualControl && $proposerId === $principal) {
    throw new \LogicException(
        'Dual control requires a different approving principal.'
    );
}
```

Имеет как минимум три обхода:

1. Вызывающий код передаёт `dualControl: false`.
2. Вызывающий код передаёт `dualControl: true`, но `proposerId: null`.
3. Вызывающий код передаёт произвольный отличный `proposerId`, не связанный с подписанным token или durable proposal.

Например, следующий вызов не нарушает условие:

```php
$protocol->commit(
    token: $token,
    actualArguments: $fingerprint,
    currentDescriptor: $digest,
    principal: 'approver-1',
    now: $now,
    authorizer: $authorizer,
    proposerId: null,
    dualControl: true,
);
```

`null === 'approver-1'` ложно, поэтому commit продолжается.

### Правильное направление

- Удалить `bool $dualControl` из публичного commit API.
- Удалить отдельно передаваемый `?string $proposerId`.
- Хранить proposer identity в proposal/token claims.
- Хранить required approval policy в token либо в durable policy decision.
- Проверять approval evidence, связанное с `proposalId`, `argsFingerprint`, `descriptorDigest`, `policyRevision` и `tenantId`.
- Не позволять caller выбирать, применять dual control или нет.

Минимальный промежуточный патч:

```php
if ($dualControl && (
    $proposerId === null
    || $proposerId === ''
    || $proposerId === $principal
)) {
    throw ConfirmationFailure::dualControlViolated();
}
```

Это закрывает только `null`, но **не решает caller-controlled policy**. Финальная версия должна выглядеть примерно так:

```php
final readonly class ApprovalEvidence
{
    public function __construct(
        public ProposalId $proposalId,
        public PrincipalId $proposer,
        public PrincipalId $approver,
        public PolicyRevision $policyRevision,
        public ArgumentsFingerprint $arguments,
        public DescriptorDigest $descriptor,
        public Instant $approvedAt,
    ) {}
}

final readonly class CommitCommand
{
    public function __construct(
        public ConfirmationTokenString $token,
        public array $arguments,
        public AuthenticatedPrincipal $actor,
    ) {}
}
```

Все остальные сведения сервис должен получать из доверенных зависимостей, а не из параметров команды.

## P0: недолговечный anti-replay

`ConfirmationProtocol` хранит spent tokens в локальном массиве. Это нарушает one-shot semantics при:

- рестарте процесса;
- горизонтальном масштабировании;
- PHP-FPM, где каждый worker имеет отдельную память;
- параллельных запросах;
- повторном создании экземпляра protocol;
- аварии после эффекта;
- длительной работе объекта из-за неограниченного роста массива.

Нужен отдельный порт:

```php
interface ConfirmationTokenStore
{
    /**
     * Атомарно потребляет token ID.
     *
     * Возвращает false, если token уже был потреблён.
     */
    public function consume(
        TenantId $tenantId,
        ConfirmationTokenId $tokenId,
        Instant $expiresAt,
        Instant $consumedAt,
        ConfirmationConsumptionOutcome $outcome,
    ): bool;
}
```

PostgreSQL-реализация:

```sql
CREATE TABLE agentools_consumed_confirmation_tokens (
    tenant_id       text        NOT NULL,
    token_id        text        NOT NULL,
    proposal_id     text        NOT NULL,
    principal_id    text        NOT NULL,
    consumed_at     timestamptz NOT NULL,
    expires_at      timestamptz NOT NULL,
    outcome         text        NOT NULL,
    token_digest    bytea       NOT NULL,

    PRIMARY KEY (tenant_id, token_id),

    CHECK (expires_at > consumed_at),
    CHECK (
        outcome IN (
            'authorized',
            'authorization_denied',
            'policy_denied'
        )
    )
);

CREATE INDEX agentools_consumed_tokens_expiry_idx
    ON agentools_consumed_confirmation_tokens (expires_at);
```

Атомарное потребление:

```sql
INSERT INTO agentools_consumed_confirmation_tokens (
    tenant_id,
    token_id,
    proposal_id,
    principal_id,
    consumed_at,
    expires_at,
    outcome,
    token_digest
)
VALUES (
    :tenant_id,
    :token_id,
    :proposal_id,
    :principal_id,
    :consumed_at,
    :expires_at,
    :outcome,
    :token_digest
)
ON CONFLICT (tenant_id, token_id) DO NOTHING
RETURNING token_id;
```

Если `RETURNING` не вернул строку, token уже был использован.

Запись можно удалять после `expires_at + retention_margin`, но не раньше окончания максимального окна replay. Retention policy должна быть документирована.

## P0: security context задаёт caller

Публичный метод принимает:

```php
string $principal,
\DateTimeImmutable $now,
CommitAuthorizer $authorizer,
DescriptorDigest $currentDescriptor,
```

Это удобный unit-test seam, но опасная production API-поверхность.

### Риски

- Старое `now` позволяет принять фактически истёкший token.
- Permissive `CommitAuthorizer` превращает authorization check в формальность.
- Caller может передать старый descriptor digest, совпадающий с token.
- `principal` может не соответствовать реально аутентифицированному субъекту.
- Разные call sites могут собирать security context по-разному.

### Исправление

Зависимости внедряются в constructor:

```php
final class ConfirmationService
{
    public function __construct(
        private readonly TokenCodec $tokens,
        private readonly ConfirmationTokenStore $spentTokens,
        private readonly Clock $clock,
        private readonly AuthorizationService $authorization,
        private readonly ToolDescriptorRegistry $descriptors,
        private readonly ApprovalRepository $approvals,
        private readonly AuditSink $audit,
    ) {}

    public function commit(CommitCommand $command): AuthorizedInvocation
    {
        $now = $this->clock->now();
        $token = $this->tokens->parseAndVerify($command->token);

        $descriptor = $this->descriptors->required(
            $token->tenantId,
            $token->toolName,
        );

        $approval = $this->approvals->requiredFor($token->proposalId);

        // Все проверки выполняются здесь.
    }
}
```

Публичный caller передаёт только:

- token;
- фактические аргументы;
- аутентифицированный principal object.

Clock, registry, authorization и policy repository не должны быть заменяемы на уровне отдельного вызова.

## P0: policy decision слабо связан с token

Сейчас выполняется:

```php
if ($decision !== null) {
    $decision->assertAllowsCommit($actualArguments);
}
```

По форме API `DecisionAudit` проверяет только actual arguments. На уровне protocol call не видно связи с:

- proposal ID;
- token ID;
- principal;
- tenant;
- tool name;
- descriptor digest;
- policy revision;
- approval identity;
- сроком действия решения.

Даже если часть проверок спрятана внутри объекта, метод получает недостаточно контекста для полной сверки.

Нужен один digest policy decision:

```php
final readonly class PolicyDecisionBinding
{
    public function __construct(
        public DecisionId $decisionId,
        public ProposalId $proposalId,
        public TenantId $tenantId,
        public PrincipalId $proposer,
        public ArgumentsFingerprint $arguments,
        public DescriptorDigest $descriptor,
        public PolicyRevision $policyRevision,
        public Instant $issuedAt,
        public Instant $expiresAt,
    ) {}
}
```

В token следует включить `decision_id` или `decision_digest`. Commit обязан загрузить решение по ID и сравнить все binding fields.

Текущий порт фактически отвечает на вопрос:

Для agentic tool execution этого мало. Решение обычно зависит от:

- proposal;
- risk tier;

Проектный план прямо отмечает P11 как not started. До первого публичного стабильного релиза нельзя объявлять пакет production-ready без:

- независимого consumer smoke;

- clean-checkout build;
- package archive inspection;
- подтверждённой legal identity;

Это не новая рекомендация, а подтверждение того, что уже заложено в [P11](https://github.com/axiomasoft/agentools/tree/main/plans/AGENTOOLS/phases/P11). P11 следует расширить нижеприведёнными security и durability gates, а не только package metadata.

# Idempotency

## Crash window

Текущий контракт:

```php
interface IdempotencyStore
{
    public function resolve(
        IdempotencyRequest $request,
        \DateTimeImmutable $now,
    ): DeduplicationResolution;

    public function complete(
        IdempotencyRequest $request,
        StoredToolResult $result,
        StoredResultDigest $digest,
    ): void;
}
```

Комментарий требует атомарной unique-key вставки в `resolve()`, что правильно. Но между выполнением эффекта и `complete()` остаётся окно:

1. Worker получает право на выполнение.
2. Внешний tool создаёт заказ.
3. Процесс падает.
4. Result не сохранён.
5. Следующий worker считает операцию незавершённой.
6. Эффект может быть повторён.

Ни один общий idempotency store не может сам обеспечить exactly-once для произвольной внешней системы. Пакет должен явно обещать:

- at-most-once admission внутри store;
- replay сохранённого результата;
- lease-based takeover;
- fencing stale workers;
- exactly-once только при участии idempotent downstream tool или transactional outbox/inbox.

## Lease contract

Рекомендуемый API:

```php
interface IdempotencyStore
{
    public function acquire(
        IdempotencyRequest $request,
        Instant $now,
        Duration $leaseDuration,
    ): IdempotencyAcquisition;

    public function heartbeat(
        IdempotencyLease $lease,
        Instant $now,
        Duration $extension,
    ): void;

    public function complete(
        IdempotencyLease $lease,
        StoredToolResult $result,
        StoredResultDigest $digest,
        Instant $completedAt,
    ): void;

    public function fail(
        IdempotencyLease $lease,
        FailureRecord $failure,
        Instant $failedAt,
    ): void;
}
```

Lease должен содержать fencing token:

```php
final readonly class IdempotencyLease
{
    public function __construct(
        public IdempotencyScope $scope,
        public IdempotencyKey $key,
        public ArgumentsFingerprint $requestFingerprint,
        public string $leaseToken,
        public int $attempt,
        public Instant $expiresAt,
    ) {}
}
```

`complete()` выполняет compare-and-swap:

```sql
UPDATE agentools_idempotency
SET
    state = 'completed',
    result_payload = :result_payload,
    result_digest = :result_digest,
    completed_at = :completed_at,
    lease_token = NULL,
    lease_until = NULL
WHERE tenant_id = :tenant_id
  AND scope = :scope
  AND idempotency_key = :idempotency_key
  AND state = 'in_progress'
  AND lease_token = :lease_token;
```

Если `rowCount() !== 1`, worker потерял lease и не имеет права публиковать результат.

## Схема хранения

```sql
CREATE TABLE agentools_idempotency (
    tenant_id            text        NOT NULL,
    scope                text        NOT NULL,
    idempotency_key      text        NOT NULL,
    request_fingerprint  bytea       NOT NULL,

    state                text        NOT NULL,
    attempt              bigint      NOT NULL DEFAULT 1,
    lease_token          uuid,
    lease_until          timestamptz,

    result_payload       jsonb,
    result_digest        bytea,
    failure_code         text,

    created_at           timestamptz NOT NULL,
    updated_at           timestamptz NOT NULL,
    completed_at         timestamptz,
    expires_at           timestamptz NOT NULL,

    PRIMARY KEY (tenant_id, scope, idempotency_key),

    CHECK (state IN ('in_progress', 'completed', 'failed')),
    CHECK (
        (state = 'in_progress'
            AND lease_token IS NOT NULL
            AND lease_until IS NOT NULL)
        OR
        (state <> 'in_progress')
    )
);

CREATE INDEX agentools_idempotency_expiry_idx
    ON agentools_idempotency (expires_at);

CREATE INDEX agentools_idempotency_lease_idx
    ON agentools_idempotency (lease_until)
    WHERE state = 'in_progress';
```

## Downstream contract

`ToolPort` должен сообщать idempotency capability:

```php
enum ToolIdempotencyCapability: string
{
    case NativeKey = 'native_key';
    case ReadBeforeWrite = 'read_before_write';
    case Compensatable = 'compensatable';
    case AtMostOnceOnly = 'at_most_once_only';
    case Unknown = 'unknown';
}
```

Coordinator выбирает стратегию:

| Capability | Поведение |
|---|---|
| `native_key` | Передать downstream тот же durable idempotency key |
| `read_before_write` | До retry проверить внешний идентификатор |
| `compensatable` | Разрешить retry только через saga policy |
| `at_most_once_only` | Не делать автоматический retry после ambiguous failure |
| `unknown` | Fail closed для high-risk tools |

# Event log

## API append

Текущий контракт принимает готовый `ActionEvent`:

```php
public function append(ActionEvent $event): void;
```

и документирует optimistic concurrency через `expected_prev_seq`: [EventLog.php](https://github.com/axiomasoft/agentools/blob/main/php/src/Contracts/EventLog.php).

Проблемы:

- Caller, вероятно, участвует в назначении sequence.
- Нет атомарного append нескольких событий.
- Нет append result с присвоенной позицией.
- `lastSeq()` отдельно от `readFrom()` создаёт дополнительные race windows.
- `readFrom()` не имеет limit/cursor.
- Не определено поведение, если тот же `event_id` приходит с другим payload.
- «Тот же ID — no-op» без сравнения содержимого может скрыть corruption.

## Предлагаемый контракт

```php
interface EventStore
{
    /**
     * @param non-empty-list<UncommittedEvent> $events
     */
    public function append(
        StreamId $streamId,
        StreamVersion $expectedVersion,
        array $events,
    ): AppendResult;

    public function load(
        StreamId $streamId,
        ?StreamVersion $after = null,
        int $limit = 500,
    ): EventStreamPage;
}
```

```php
final readonly class UncommittedEvent
{
    public function __construct(
        public EventId $eventId,
        public EventType $type,
        public EventSchemaVersion $schemaVersion,
        public array $payload,
        public EventMetadata $metadata,
    ) {}
}
```

```php
final readonly class AppendResult
{
    public function __construct(
        public StreamVersion $previousVersion,
        public StreamVersion $currentVersion,
        public GlobalPosition $lastGlobalPosition,
        public array $committedEvents,
    ) {}
}
```

### Обязательные инварианты

- Все события batch получают последовательные stream sequence в одной транзакции.
- Несовпадение expected version возвращает typed conflict.
- Повторное событие с тем же ID и идентичным canonical hash — idempotent success.
- То же ID с другим hash — `EventIdCollision`.
- Event payload имеет explicit schema version.
- Metadata содержит tenant, actor, trace correlation и causation ID.
- Secret-bearing fields запрещены отдельным validator.
- Snapshot содержит stream version и event hash, на котором он построен.
- Snapshot никогда не заменяет журнал как источник истины.

## PostgreSQL layout

```sql
CREATE TABLE agentools_action_events (

    schema_version     integer     NOT NULL,

    payload             jsonb       NOT NULL,
    metadata            jsonb       NOT NULL,

    previous_hash       bytea,
    event_hash          bytea       NOT NULL,
    occurred_at         timestamptz NOT NULL,

    PRIMARY KEY (tenant_id, stream_id, stream_seq),
    UNIQUE (tenant_id, event_id),
    UNIQUE (global_position)
);
```

Хеш должен вычисляться над нормализованным immutable envelope, а не над DB-generated `global_position`, иначе его нельзя подготовить до insert.

# Confirmation token

## Claims envelope

Token должен иметь явную версию формата и минимум такие claims:

```json
{
  "v": 1,
  "alg": "HS256",
  "kid": "confirmation-2026-09",
  "iss": "agentools.example",
  "aud": "agentools-confirmation",
  "jti": "01J...",
  "tenant_id": "tenant-123",
  "proposal_id": "proposal-456",
  "decision_id": "decision-789",
  "proposer_id": "user-1",
  "subject_id": "user-2",
  "tool_name": "orders.create",
  "arguments_sha256": "...",
  "descriptor_sha256": "...",
  "policy_revision": "policy-17",
  "required_approvals": 1,
  "iat": "2026-09-19T10:00:00Z",
  "nbf": "2026-09-19T10:00:00Z",
  "exp": "2026-09-19T10:05:00Z"
}
```

Это не означает, что необходимо переходить на JWT. Компактный собственный формат допустим, если:

- envelope versioned;
- payload canonicalized;
- подпись проверяется constant-time;
- `kid` поддерживает rotation;
- `iss` и `aud` проверяются;
- размер token ограничен до parsing;
- неизвестный `alg` запрещается;
- parser не допускает duplicate JSON keys;
- token ID не зависит от raw representation;
- signing key разделяется по purpose и tenant;
- ошибки наружу не раскрывают криптографический oracle.

## Rotation

`TokenSigner` стоит заменить или расширить до key ring:

```php
interface TokenKeyProvider
{
    public function currentSigningKey(
        TenantId $tenant,
        TokenPurpose $purpose,
    ): SigningKey;

    public function verificationKey(
        TenantId $tenant,
        TokenPurpose $purpose,
        KeyId $keyId,
    ): VerificationKey;
}
```

Поддерживаемый lifecycle:

- `active`: подписывает и проверяет;
- `verify_only`: только проверяет старые tokens;
- `retired`: не используется;
- physical delete — после максимального TTL, clock skew и audit retention window.

## Порядок commit

Рекомендуемый pipeline:

1. Проверить максимальный размер token.
2. Parse envelope без доверия к содержимому.
3. Определить version/algorithm/key ID.
4. Проверить signature.
5. Проверить issuer/audience/tenant.
6. Проверить `nbf`/`exp` через injected clock.
7. Вычислить actual arguments fingerprint внутри service.
8. Получить актуальный descriptor из registry.
9. Загрузить durable policy decision.
10. Проверить proposer/approver и approval threshold.
11. Проверить authorization.
12. Атомарно consume token.
13. Создать `AuthorizedInvocation`.
14. Записать audit decision.
15. Выполнить tool через coordinator.

В текущей реализации token расходуется до authorization, причём комментарий показывает, что это намеренное решение. Оно допустимо, но тогда replay store обязан сохранить outcome `authorization_denied`, а документация должна объяснить, почему восстановление permissions не оживляет ранее предъявленный token.

# Ошибки

## Текущая неоднородность

В одном commit flow используются:

- `ConfirmationFailure`;
- `DescriptorDrift`;
- `InvalidArgumentException`;
- `LogicException`.

Для пользователя пакета это делает обработку ошибок неустойчивой. `LogicException` не позволяет понять, является ли ошибка:

- ожидаемым policy rejection;
- programmer error;
- authorization denial;
- временной инфраструктурной ошибкой;
- non-retriable protocol error.

## Единая модель

```php
interface AgentoolsFailure extends \Throwable
{
    public function errorCode(): AgentoolsErrorCode;

    public function retryability(): Retryability;

    /** Безопасный для журнала контекст. */
    public function safeContext(): array;
}
```

```php
enum Retryability: string
{
    case Never = 'never';
    case Safe = 'safe';
    case AfterBackoff = 'after_backoff';
    case AfterReauthorization = 'after_reauthorization';
    case ManualDecision = 'manual_decision';
}
```

Не следует использовать `getCode()` для строкового protocol code: PHP определяет его как integer-compatible throwable code. Нужен отдельный `errorCode()`.

### Таксономия

| Категория | Примеры | Механика |
|---|---|---|
| Input rejection | invalid arguments, malformed token | Typed result/exception, `never` |
| Policy rejection | approval required, dual control violated | Typed decision, `manual_decision` |
| Authorization rejection | principal denied | Typed decision, `after_reauthorization` |
| Concurrency | version conflict, lost lease | Typed exception, `safe` или backoff |
| Infrastructure | DB unavailable, timeout | Wrapped cause, `after_backoff` |
| Programmer error | impossible state, invariant broken | Internal exception, fail fast |
| Security integrity | signature invalid, hash mismatch | Generic external error, precise internal audit |

Error codes должны:

- быть стабильными после 1.0;
- иметь registry;
- содержать first-introduced spec revision;
- иметь retryability;
- иметь public-safe message;
- отображаться одинаково в PHP и Dart;
- тестироваться shared fixtures.

## Core facade

Не следует заставлять потребителя вручную собирать низкоуровневые protocol objects для типичной операции.

Нужны два уровня:

### Safe API

```php
interface Agentools
{
    public function propose(
        ProposeToolInvocation $command,

    public function approve(
        ApproveProposal $command,
```

## Differential runner

Для каждого generated input:

1. PHP adapter получает одинаковый canonical JSON.
2. Dart adapter получает те же bytes.
3. Сравниваются semantic outputs.
4. Нестабильные поля нормализуются runner-ом, а не SDK.
5. Любое расхождение сохраняется как regression fixture.

Псевдокоманда:

```bash
agentools-conformance differential \
  --left='php php/conformance/adapter.php' \
  --right='dart run dart/agentools_conformance/bin/adapter.dart' \
  --corpus=fixtures/differential \
  --seed=20260919 \
  --cases=10000
```

## JCS

Статус проекта указывает на собственные JCS реализации в PHP и Dart. Это оправдано для минимизации dependency risk, но означает высокий риск одинакового концептуального дефекта в двух реализациях, особенно вокруг:

- `-0`;
- exponent formatting;
- large integers;
- IEEE-754 boundaries;
- Unicode escaping;
- supplementary planes;
- invalid surrogate sequences;
- duplicate keys;
- locale-dependent number formatting;
- map key ordering.

Нужны:

- полный RFC 8785 corpus;
- независимый внешний oracle;
- property tests;
- cross-language random differential tests;
- explicit I-JSON restrictions;
- запрет native float round-trip там, где нужна lossless семантика;
- строковое представление для идентификаторов и чисел за безопасным integer range.

# Conformance

## Развести два понятия

Текущие 213/213 относятся к Agentools profile. Это сильный результат, но он не должен называться просто «MCP conformance».

Официальный MCP Conformance Test Framework запускает тестовую сторону, собирает protocol interactions и проверяет их по опубликованной спецификации. Официальная tiering-модель отдельно требует 100% применимых тестов для Tier 1 и 80% для Tier 2. [github](https://github.com/modelcontextprotocol/conformance)

Рекомендуемые формулировки:

- `Agentools Profile 2026-08: 213/213`;
- `MCP transport conformance: X/Y applicable scenarios`;
- `MCP SDK tier: not applicable`, если Agentools не позиционируется как полный SDK;
- `agentools_mcp_dart transport: official MCP conformance ...`, если satellite действительно участвует в official suite.

Не использовать неоднозначный badge `MCP compliant`, пока official suite не включён.

## Слои тестов

```text
Layer 0: schema and generated artifacts
Layer 1: pure domain semantics
Layer 2: storage contract suites
Layer 3: cross-language differential
Layer 4: Agentools extension conformance
Layer 5: official MCP conformance
Layer 6: consumer smoke
Layer 7: release archive verification
```

### Storage contract suites

Один набор тестов должен запускаться для:

- in-memory testkit;
- SQLite reference;
- PDO/PostgreSQL;
- Laravel adapter;
- Dart SQLite;
- любых будущих stores.

Обязательные сценарии:

- 50 параллельных acquire одного idempotency key;
- два append с одинаковым expected version;
- duplicate event ID с одинаковым payload;
- duplicate event ID с другим payload;
- worker lease expiry;
- stale worker complete;
- process crash после tool effect;
- token consume из двух процессов;
- clock boundary ровно на `exp`;
- retention cleanup во время concurrent consume.

## Mutation testing

Существующие negative adapters — хороший фундамент, но нужна систематическая mutation matrix.

Для PHP стоит запускать Infection или эквивалент поверх критических bounded contexts:

- удалить expiry check;
- заменить `<=` на `<`;
- пропустить descriptor check;
- пропустить principal check;
- отключить replay consume;
- заменить AND на OR в dual control;
- принять unknown algorithm;
- игнорировать expected version;
- разрешить stale lease completion;
- не сверять result digest.

Release gate:

```text
Confirmation/Security mutation score: 100% для curated security mutants
Domain mutation score: >= 85%
Escaped critical mutant: release blocked
```

Обычный aggregate mutation score не должен скрывать выживший security mutant.

## Property tests

Нужные свойства:

```text
parse(encode(x)) == x
canonicalize(parse(canonicalize(x))) == canonicalize(x)
fingerprint(a) == fingerprint(b) iff canonical representations equal
consuming token twice succeeds exactly once
fold(events) deterministic
append conflicts never produce duplicate stream_seq
stale lease never completes
unknown enum round-trips without semantic promotion
must-ignore fields do not affect known semantics
```

## Hardening GitHub Actions

Каждый workflow:

```yaml
name: quality

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  php:
    runs-on: ubuntu-latest
    timeout-minutes: 20

    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
        # v4.2.2

      - run: task ci:php
```

GitHub указывает, что полный commit SHA — единственный способ сослаться на immutable release action. Для обновления SHA следует использовать Dependabot или Renovate, сохраняя рядом комментарий с human-readable version. [docs.github](https://docs.github.com/en/actions/reference/security/secure-use)

Обязательные правила:

- workflow-level `permissions: contents: read`;
- write permissions только на конкретном release job;
- запрещён untrusted checkout в `pull_request_target`;
- PR inputs передаются через `env`, а не интерполируются в shell;
- third-party actions закреплены full SHA;
- release environment требует approval;
- static long-lived publishing credentials заменяются OIDC, где это поддерживается;
- self-hosted runners не используются для untrusted public PR;
- concurrency отменяет устаревшие CI runs;
- каждому job назначен timeout.

# Проектная бухгалтерия

## Generated status

В `status.md` много строк с датой `1970-01-01`, появившихся при migration. Для внутреннего журнала это технически объяснимо, но публично выглядит как повреждённая история.

Вместо epoch sentinel:

```json
{
  "completed_at": null,
  "completed_at_known": false,
  "migration_source": "legacy-status-v1"
}
```

UI projection:

```text
Updated: unknown (legacy migration)
```

Нельзя использовать `1970-01-01` как «нет данных»: это валидная дата и она искажает сортировку, статистику и машинный анализ.

## Open questions

[open-questions.md](https://github.com/axiomasoft/agentools/blob/main/plans/AGENTOOLS/open-questions.md) показывает отсутствие записей, но status одновременно содержит known deviations и owner gates. Формально это не противоречие — projection может учитывать только decision questions, — но название вводит в заблуждение.

Переименовать:

```text
open-owner-decisions.md
```

И добавить отдельные projections:

```text
known-deviations.md
technical-debt.md
release-blockers.md
security-findings.md
```

Каждая deviation:

```yaml
id: DEV-P10-004
owner: persistence
severity: medium
introduced: "2026-09-19"
expires_by: "before-1.0"
affected_packages:
  - php/core
rationale: "..."
risk: "..."
acceptance:
  - "..."
```

## Публикационная граница

`plans/AGENTOOLS/journal.jsonl` уже имеет значительный размер, а рядом лежат `status.md`, `plan.md`, `roadmap.md`, `index.md`, migration artifacts и generated projections: [plans/AGENTOOLS](https://github.com/axiomasoft/agentools/tree/main/plans/AGENTOOLS).

Они полезны для разработки, но должны быть:

- исключены из package archives;
- исключены из documentation navigation для обычного потребителя;
- отделены от normative specification;
- либо перенесены в `internal/planning`;
- либо оставлены в репозитории, но ясно помечены как non-product artifacts.

## README

README должен отвечать в первые две минуты:

1. Что решает Agentools?
2. Чем он не является?
3. Когда использовать?
4. Какие гарантии даёт?
5. Какие гарантии не даёт?
6. Как установить?
7. Как пройти минимальный сценарий?
8. Какие production adapters обязательны?
9. Как проверить совместимость spec/package/MCP?
10. Где сообщать уязвимость?

Пример предупреждения:

> In-memory stores are test-only and do not provide replay protection or durability across processes. Production confirmation and idempotency flows require a durable storage adapter.

## Security model

Обязательно зафиксировать trust boundaries:

```text
Untrusted:
- LLM output
- tool arguments
- MCP peer data
- user-supplied extension fields
- persisted payloads read after schema upgrades

Partially trusted:
- application integration code
- tool adapters
- policy adapters

Trusted:
- key provider
- authenticated principal provider
- clock
- descriptor registry
- durable replay store
```

Нужен отдельный раздел «misuse resistance»:

- caller не выбирает policy mode;
- caller не передаёт текущее время;
- caller не подменяет authorizer;
- caller не вычисляет security digest вручную;
- in-memory adapters невозможно случайно включить в production preset.

## Guarantees

Избегать формулировки «exactly once». Лучше:

> Agentools provides durable admission control, idempotency record coordination, replay of recorded outcomes, and fencing of stale executors. Exactly-once external effects require cooperation from the downstream system or a shared transactional boundary.

# Производительность

## Benchmarks

Добавить repeatable benchmark suite:

- JCS для 1 KB, 10 KB, 100 KB payload;
- schema validation cold/warm;
- descriptor digest;
- event fold 10, 100, 1 000, 10 000 events;
- append contention;
- idempotency contention;
- token parse/verify;
- differential runner throughput;
- snapshot restore.

Результаты не должны блокировать каждый PR по абсолютному времени. PR gate сравнивает regression budget:

```text
Canonicalization p50: no more than +10%
Canonicalization p95: no more than +15%
Event fold allocations: no more than +10%
Token verification: no more than +10%
```

## Resource limits

Установить и тестировать:

- max token bytes;
- max arguments bytes;
- max nesting depth;
- max map entries;
- max event payload;
- max events per page;
- max scenario steps;
- max expression nodes;
- max string length;
- max unknown extension fields;
- max audit baggage;
- max result bytes.

`spentTokens` — текущий пример unbounded collection; подобных структур в production path быть не должно.

- [MCP PHP SDK](https://github.com/modelcontextprotocol/php-sdk) — особенно полезен как соседний PHP package.
- [MCP SDK tiering](https://modelcontextprotocol.io/community/sdk-tiers) — прозрачные критерии полноты и сопровождения. [modelcontextprotocol](https://modelcontextprotocol.io/community/sdk-tiers)
- Страница PHP SDK публично показывает конкретные conformance gaps вместо абстрактного «поддерживается», что является хорошим образцом прозрачности. [php.sdk.modelcontextprotocol](https://php.sdk.modelcontextprotocol.io/sdk-tier/)

## Durable execution

- [Temporal](https://github.com/temporalio/temporal) — durable workflow/event history model.
- [Temporal PHP SDK](https://github.com/temporalio/sdk-php) — separation workflow/activity/client concerns.
- [EventSauce](https://github.com/EventSaucePHP/EventSauce) — PHP event-sourcing boundaries.
- [EventStoreDB](https://github.com/EventStore/EventStore) — expected revision, stream semantics, projections.
- [AWS Lambda Powertools idempotency](https://docs.powertools.aws.dev/) — acquisition, persistence, retries и result replay patterns.

Не нужно копировать эти системы. Они полезны как проверка терминологии и failure modes.

# Definition of Done

Agentools можно считать идеальным кандидатом на 1.0, когда одновременно выполнены следующие условия:

- Security-critical policy невозможно отключить параметром отдельного вызова.
- Confirmation replay state атомарно разделяется всеми процессами.
- Token format поддерживает versioning и key rotation.
- Idempotency использует leases и fencing.
- Event append атомарен для batch и защищён expected version.
- PHP и Dart имеют machine-readable semantic parity.
- Public API intentional и проверяется на backward compatibility.
- In-memory adapters невозможно перепутать с production implementations.
- Official MCP и Agentools conformance названы и измеряются раздельно.
- Все примеры компилируются и выполняются в CI.
- Clean consumer projects устанавливают пакеты только из опубликованных архивов.
- Lowest/latest dependency matrices зелёные.
- Security mutants не выживают.
- Package archives не содержат planning/research мусора.
- Release создаёт SBOM, checksums и provenance.
- `SECURITY.md`, `SUPPORT.md`, threat model и guarantees опубликованы.
- Stable release воспроизводится из тега без ручного изменения файлов.

Самая правильная ближайшая цель — не «добавить ещё возможностей», а выполнить **P11+**: существующую release/hygiene фазу, дополненную четырьмя обязательными блоками — safe confirmation boundary, durable anti-replay, lease/fencing idempotency и intentional package split. После этого проект сможет выглядеть не просто как хорошо исследованный протокол, а как действительно безопасный и удобный open-source foundation для production agent workflows.
