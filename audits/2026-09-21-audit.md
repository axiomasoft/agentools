## Критические дефекты

### Supply-chain lock неверен

В `.ci/supply-chain-lock.json` SHA `0057852...` записан под идентификатором `actions/cache`, но workflow использует этот SHA как `actions/upload-artifact`. Это ломает семантику lock-файла: обновление, аудит лицензий и проверка соответствия action ↔ SHA могут дать ложный результат. [supply-chain-lock.json](https://github.com/axiomasoft/agentools/blob/main/.ci/supply-chain-lock.json) [private-rc.yml](https://github.com/axiomasoft/agentools/blob/main/.github/workflows/private-rc.yml)

Исправление:

```json
{
  "id": "actions/upload-artifact",
  "ref_human": "v4",
  "ref_immutable": "0057852bfaa89a56745cba8c7296529d2fc39830"
}
```

`ci_policy.py` должен проверять не только наличие SHA в lock, но и точное соответствие пары `owner/repository@sha`.

### Safety hooks отключены

`lifecycle.py` реализует `safe-dirs`, daemon safety, git guardrails, changelog gate, pack guard, review gate и terminal admission, однако `.cursor/hooks.json` регистрирует только memory, telemetry, command logging и run report; `beforeShellExecution` вообще пуст. Значит, наиболее важные защитные механизмы фактически не исполняются в Cursor. [hooks.json](https://github.com/axiomasoft/agentools/blob/main/.cursor/hooks.json) [lifecycle.py](https://github.com/axiomasoft/agentools/blob/main/.cursor/hooks/lifecycle.py)

Минимальная регистрация:

```json
"beforeShellExecution": [
  {"command": "python3 \"${CURSOR_PROJECT_DIR:-.}/.cursor/hooks/lifecycle.py\" --surface security.safe-dirs"},
  {"command": "python3 \"${CURSOR_PROJECT_DIR:-.}/.cursor/hooks/lifecycle.py\" --surface lifecycle.daemon-safety"},
  {"command": "python3 \"${CURSOR_PROJECT_DIR:-.}/.cursor/hooks/lifecycle.py\" --surface lifecycle.git-guardrails"},
  {"command": "python3 \"${CURSOR_PROJECT_DIR:-.}/.cursor/hooks/lifecycle.py\" --surface lifecycle.changelog-gate"}
]
```

При этом `safe-dirs` нельзя позиционировать как полноценную security boundary: сейчас анализируется только первый token команды, поэтому оболочки вроде `bash -c`, Python, `find -delete` и другие косвенные удаления находятся вне этой проверки. [lifecycle.py](https://github.com/axiomasoft/agentools/blob/main/.cursor/hooks/lifecycle.py)

### RC допускает чужую ветку

В `private-rc.yml` событие `workflow_dispatch` всегда выставляет `proceed=true`, независимо от выбранной ветки. Ручной запуск на feature branch может собрать артефакт, выглядящий как доверенный private RC, хотя trusted-ref guard его фактически не проверил. [private-rc.yml](https://github.com/axiomasoft/agentools/blob/main/.github/workflows/private-rc.yml)

Guard должен разрешать только:

- `refs/heads/main`;
- подписанный release tag;
- явно настроенное защищённое RC-окружение.

### Candidate corpus неблокирующий

`conformance/bin/p6-gate` запускает корпус `2026-09` как `successor corpus probe (non-blocking)` и игнорирует код возврата, хотя README называет `2026-09` текущей candidate-ревизией. В результате integrated receipt может быть зелёным даже при падении основного candidate corpus. [p6-gate](https://github.com/axiomasoft/agentools/blob/main/conformance/bin/p6-gate) [README.md](https://github.com/axiomasoft/agentools/blob/main/README.md)

Допустимо оставить probe неблокирующим только до официального переключения target revision. После объявления `2026-09` current candidate его полный L1–L3 corpus должен быть release-blocking.

### MCP clean-checkout неполон

Официальный MCP contour требует `npm ci`, но показанные CI и private-RC workflow не устанавливают зависимости `conformance/mcp`, а `bin/run` сразу вызывает `npm exec`. Поскольку `node_modules` игнорируется, clean checkout не должен зависеть от заранее прогретого локального окружения или неявной загрузки пакета через `npm exec`. [MCP README](https://github.com/axiomasoft/agentools/blob/main/conformance/mcp/README.md) [MCP runner](https://github.com/axiomasoft/agentools/blob/main/conformance/mcp/bin/run) [ci.yml](https://github.com/axiomasoft/agentools/blob/main/.github/workflows/ci.yml)

Необходимо:

- Явно установить и закрепить Node.
- Выполнить `npm ci --ignore-scripts` или документированно разрешить scripts.
- Запускать `./node_modules/.bin/conformance`.
- Проверять отсутствие сетевого fallback во время теста.
- Добавить npm lock в OSV/Dependabot-контур.

### Parity переименован неверно

`semantic-parity` строит normative profile только из `error_codes` и сравнивает PHP/Dart именно по ним. Это полезный gate, но он не доказывает parity state machines, token claims, confirmation policy, leases, event-store semantics, limits или wire DTO. [semantic-parity](https://github.com/axiomasoft/agentools/blob/main/conformance/bin/semantic-parity) [semantic-manifest.json](https://github.com/axiomasoft/agentools/blob/main/spec/revisions/2026-09/semantic-manifest.json)

Варианты:

1. Честно переименовать в `error-code-parity`.
2. Расширить semantic profile следующими разделами:
   - constants and limits;
   - state transitions;
   - token claim requirements;
   - confirmation policy matrix;
   - idempotency acquisition outcomes;
   - event append conflict classes;
   - field optionality/defaults;
   - retryability and error mapping.

## Conformance-проблемы

### MCP coverage слишком узок

Applicability matrix признаёт применимым фактически только `tools_call`, а большинство client scenarios объявляет non-applicable. Формулировка «official MCP scenario compatibility» осторожнее, чем certification, но без явного отношения `passed/applicable/all-client-scenarios` всё равно может восприниматься шире фактического покрытия. [applicability matrix](https://github.com/axiomasoft/agentools/blob/main/conformance/mcp/applicability-2026-07-28.json) [MCP README](https://github.com/axiomasoft/agentools/blob/main/conformance/mcp/README.md)

В матрице также есть подозрительные обоснования: например, `json-schema-ref-no-deref` объявлен non-applicable по причине отсутствия HTTP header mapping, хотя название сценария относится к сохранению `$ref`. Это требует ручной ревизии каждой non-applicable строки. [applicability matrix](https://github.com/axiomasoft/agentools/blob/main/conformance/mcp/applicability-2026-07-28.json)

### Смешаны два измерения

Поле `applicability` допускает одновременно `applicable`, `non_applicable`, `passed` и `failed`, при наличии отдельного `execution_status`. Классификация применимости и результат исполнения должны быть независимыми осями. [applicability.schema.json](https://github.com/axiomasoft/agentools/blob/main/conformance/mcp/applicability.schema.json)

Предлагаемая модель:

```json
{
  "applicability": "applicable",
  "execution_status": "passed",
  "evidence": {
    "receipt_path": "...",
    "digest": "sha256:..."
  }
}
```

### Возможен deadlock runner

`p6-gate` читает `stdout` дочернего процесса до EOF, а затем `stderr`. Если дочерний процесс заполнит `stderr` pipe, пока родитель блокируется на `stdout`, процесс может зависнуть. [p6-gate](https://github.com/axiomasoft/agentools/blob/main/conformance/bin/p6-gate)

Лучше использовать наследование stdout/stderr, временные файлы либо неблокирующий `stream_select`.

## Benchmark-достоверность

### Event fold не выполняется

`eval_event_fold()` не создаёт и не сворачивает указанное число событий: он загружает пустой stream и канонизирует маленький объект, где `events` используется как число. Следовательно, benchmark не измеряет реальную стоимость event replay/fold и не может подтверждать resource envelope этой операции. [run_workload.php](https://github.com/axiomasoft/agentools/blob/main/benchmarks/php/run_workload.php)

Нужно генерировать реальные `UncommittedEvent`, выполнять append, page load и reducer fold для размеров вроде 1, 10, 100, 1 000 и 10 000.

### Benchmark использует старую ревизию

`eval_scenario_steps()` запускает scenario с `spec_rev: 2026-08`, несмотря на объявленный current candidate `2026-09`. Поэтому часть performance evidence относится к predecessor semantics. [run_workload.php](https://github.com/axiomasoft/agentools/blob/main/benchmarks/php/run_workload.php) [README.md](https://github.com/axiomasoft/agentools/blob/main/README.md)

### Ошибки классифицируются грубо

Token benchmark относит некоторые `invalid` ошибки к `reject.limit`, а canonicalizer превращает любой `Throwable` в `reject.invalid_json`. Это может скрыть внутреннюю ошибку реализации под ожидаемым пользовательским отказом. [run_workload.php](https://github.com/axiomasoft/agentools/blob/main/benchmarks/php/run_workload.php)

Нужны отдельные классы:

- `reject.syntax`;
- `reject.claim`;
- `reject.signature`;
- `reject.limit`;
- `reject.unsupported`;
- `error.internal`.

## CI и supply chain

### Полные тесты после merge

Full bounded conformance и disposable dependency resolution выполняются только после push в `main`, а PR получает преимущественно focused lanes. Это уменьшает время PR, но позволяет смержить изменение, которое сломает интегральный корпус и обнаружится уже после merge. [ci.yml](https://github.com/axiomasoft/agentools/blob/main/.github/workflows/ci.yml)

Лучший баланс:

- На каждый PR: focused tests.
- При изменении `spec/`, `fixtures/`, `conformance/`, public API или persistence: полный bounded corpus.
- Перед merge в protected `main`: обязательный интегральный gate.
- Nightly: extended, mutation, fuzz, storage chaos и resource envelopes.

### Dependency coverage неполный

Dependabot настроен для GitHub Actions и двух Composer roots, но не для Dart packages и npm-пакета MCP conformance. [dependabot.yml](https://github.com/axiomasoft/agentools/blob/main/.github/dependabot.yml)

Добавить:

- `pub` для `dart/agentools`;
- `pub` для `dart/agentools_mcp_dart`;
- `npm` для `conformance/mcp`;
- dependency grouping;
- security-only fast lane;
- lockfile freshness gate.

### Gitleaks имеет blind spots

Gitleaks исключает целиком `fixtures/`, `conformance/reports/` и `plans/`. Это удобно для тестовых токенов и evidence, но позволяет реальному секрету незаметно попасть в очень большие области репозитория. [.gitleaks.toml](https://github.com/axiomasoft/agentools/blob/main/.gitleaks.toml)

Нужно разрешать не каталоги, а:

- конкретные fixture IDs;
- распознаваемые fake-secret prefixes;
- конкретные generated receipt paths;
- digest-verified generated files.

### Dead CI configuration

`hosted-attest` зафиксирован через `if: false`. Такой код не тестируется и со временем дрейфует, хотя визуально выглядит частью release pipeline. [private-rc.yml](https://github.com/axiomasoft/agentools/blob/main/.github/workflows/private-rc.yml)

Лучше использовать repository variable:

```yaml
if: vars.AGENTOOLS_HOSTED_ATTESTATION == 'enabled'
```

и иметь отдельную policy-проверку конфигурации.

## Prompt-аудит

### Entry point слишком краткий

`AGENTS.md` и `CLAUDE.md` генерируются из одного source of truth — это хороший паттерн, предотвращающий дрейф. Однако содержимое задаёт лишь общие принципы и не содержит точных команд, change-impact matrix, dependency boundaries и обязательных acceptance criteria. [AGENTS.md](https://github.com/axiomasoft/agentools/blob/main/AGENTS.md) [.ai source](https://github.com/axiomasoft/agentools/blob/main/.ai/guidelines/agent-entrypoint.md)

Рекомендуемая структура root-инструкции:

1. Repository mission.
2. Normative source hierarchy.
3. Non-negotiable invariants.
4. Directory dependency graph.
5. Change-impact matrix.
6. Exact focused/full commands.
7. Generated files and edit policy.
8. Security boundaries.
9. Definition of done.
10. Release prohibitions.

### Server naming расходится

Skill говорит о сервере `serena`, тогда как `.mcp.json.example` регистрирует тот же механизм под именем `codegraph`. Модель может искать неправильный tool namespace или считать сервер отсутствующим. [ecosystem-mcp skill](https://github.com/axiomasoft/agentools/blob/main/.agents/skills/ecosystem-mcp/SKILL.md) [.mcp.json.example](https://github.com/axiomasoft/agentools/blob/main/.mcp.json.example)

Следует выбрать единый canonical name, например `codegraph`, а Serena оставить implementation detail.

### Состояние описано противоречиво

`ecosystem-mcp` утверждает, что проект подключён к mAInd, а `ecosystem-setup` фиксирует состояние `standalone`. Вероятно, одно относится к connectivity, другое — к project profile, но агенту это не объяснено. [ecosystem-mcp](https://github.com/axiomasoft/agentools/blob/main/.agents/skills/ecosystem-mcp/SKILL.md) [ecosystem-setup](https://github.com/axiomasoft/agentools/blob/main/.agents/skills/ecosystem-setup/SKILL.md)

Нужны раздельные поля:

```yaml
project_profile: protocol-sdk
hub_connectivity: connected
memory_provider: maind
codegraph_provider: serena
```

### Memory scope нестабилен

Cursor hook вычисляет scope как `project:<basename checkout directory>`, а canonical scope в навыке — `project:agentools`. Клоны `agentools-audit`, worktree directories и CI checkout могут получить другой memory scope. [lifecycle.py](https://github.com/axiomasoft/agentools/blob/main/.cursor/hooks/lifecycle.py) [ecosystem-mcp](https://github.com/axiomasoft/agentools/blob/main/.agents/skills/ecosystem-mcp/SKILL.md)

Scope следует брать из versioned project metadata, а не из имени директории.

### Навык слишком eager

`ecosystem-mcp` рекомендует обращаться к общей памяти в начале задачи. Для локальной правки DTO или теста это добавляет latency, токены и внешний failure mode без пользы. [ecosystem-mcp](https://github.com/axiomasoft/agentools/blob/main/.agents/skills/ecosystem-mcp/SKILL.md)

Лучший trigger:

- Использовать memory при вопросах о прошлых решениях, межпроектных контрактах или неочевидных причинах архитектуры.
- Не использовать для изолированной механической правки, когда источник истины уже находится в репозитории.

### Внешняя зависимость hooks

`lifecycle.py` ищет policy core внутри внешнего Swissknifeman/harness checkout или через установленные executable paths. Репозиторий поэтому не является полностью self-contained: строгие gates могут fail-close, если внешний harness недоступен. [lifecycle.py](https://github.com/axiomasoft/agentools/blob/main/.cursor/hooks/lifecycle.py)

Для надёжности нужен один из вариантов:

- versioned Python package dependency с lock;
- vendored minimal policy runtime;
- bootstrap script с digest verification;
- явный capability report вместо скрытого поиска по файловой системе.

### MCP example непереносим

`.mcp.json.example` содержит `<ABS_PATH_TO_PROJECT>` и `<HOME>/projects/packages/perplexity-web-mcp/start.sh`; второй путь завязан на локальную структуру одного разработчика. [.mcp.json.example](https://github.com/axiomasoft/agentools/blob/main/.mcp.json.example)

Разделить конфигурации:

- `.mcp.json.example` — только переносимый минимум;
- `.mcp.internal.example` — mAInd/Perplexity/internal topology;
- `scripts/configure-mcp` — генерация абсолютных путей и health check.

## Схемы и спецификация

Ревизия `2026-09` содержит отдельные runtime и authoring schemas, причём многие пары почти полностью дублируются. Это повышает риск скрытого дрейфа между authoring validation, runtime validation, fixtures и SDK DTO. [runtime schemas](https://github.com/axiomasoft/agentools/tree/main/spec/revisions/2026-09/schema) [authoring schemas](https://github.com/axiomasoft/agentools/tree/main/spec/revisions/2026-09/schema/authoring)

Для идеальной архитектуры нужен pipeline:

```text
normative semantic model
    ├── runtime JSON Schemas
    ├── authoring JSON Schemas
    ├── semantic manifest
    ├── fixture skeletons
    ├── PHP enums/DTO metadata
    └── Dart enums/DTO metadata
```

Ручное дублирование допустимо только при обязательном structural-diff gate, который знает разрешённые различия, например более строгие authoring rules.

## GitHub-качество

В `.github` присутствуют только Dependabot и workflows; нет `CODEOWNERS`, issue forms, pull request template, contribution guide и governance policy. Для private repository это не security blocker, но для «идеального GitHub-репозитория» отсутствие этих surfaces ухудшает ownership, review routing и воспроизводимость решений. [.github](https://github.com/axiomasoft/agentools/tree/main/.github)

Минимальный комплект:

- `.github/CODEOWNERS`;
- `.github/pull_request_template.md`;
- `.github/ISSUE_TEMPLATE/bug.yml`;
- `.github/ISSUE_TEMPLATE/spec-change.yml`;
- `.github/ISSUE_TEMPLATE/security-hardening.yml`;
- `CONTRIBUTING.md`;
- `GOVERNANCE.md`;
- `ARCHITECTURE.md`;
- `DEVELOPMENT.md`.

`SECURITY.md` просит использовать private security channel владельца, но не указывает конкретный доступный канал, адрес или GitHub Private Vulnerability Reporting procedure. [SECURITY.md](https://github.com/axiomasoft/agentools/blob/main/SECURITY.md)
