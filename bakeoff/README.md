# Bakeoff — терпимость генераторов кода к JSON Schema 2020-12

Корпус проб для эмпирической проверки: переживает ли генератор кода (PHP/Dart) конструкции
JSON Schema 2020-12, которых не понимает, не падая и не теряя поля документа. Вопрос —
терпимость, а не разрешение (`DR-01` §J9): опубликованные схемы AgenTools открыты (E3 —
must-ignore), и генератор обязан пережить это, а не молча деградировать.

Каждая проба — каталог `probes/<id>/` с четырьмя файлами:

- `schema.json` — минимальная схема (диалект `https://json-schema.org/draft/2020-12/schema`,
  локальный `$id`, ровно одна проверяемая конструкция).
- `valid.json` — документ, проходящий схему без исключений.
- `unknown-key.json` — тот же документ + одно неизвестное свойство документа и, где
  применимо, неизвестный ключ схемы.
- `README.md` — что проверяет проба и что считается терпимым поведением.

## Метод прогона

Каждая связка «кандидат × проба» прогоняется отдельной командой (P2.2/P2.3 — таблица с
командой, версией кандидата и полным выводом в `bakeoff/results/*.log`). Вердикт ставится
ПО НАБЛЮДАЕМОМУ ВЫВОДУ команды — не по документации кандидата.

## Шкала вердиктов (закрытое перечисление)

| Вердикт | Значение |
|:--|:--|
| `ok` | конструкция понята генератором корректно |
| `ignored-gracefully` | конструкция не понята, но прогон успешен и поля документа не потеряны |
| `field-lost` | прогон успешен, но поле исчезло из сгенерированного типа / round-trip |
| `crash` | генератор упал (ненулевой код возврата / необработанное исключение) |
| `not-supported` | кандидат не имеет такого таргета языка или не устанавливается в песочнице |

Новые значения шкалы не вводятся — случай, не покрываемый пятью значениями, эскалируется, а не
получает изобретённый вердикт.

Round-trip (отдельная колонка в таблицах P2.2/P2.3) — не то же самое, что вердикт по шкале
выше: он измеряет, теряется ли неизвестное **свойство документа** при десериализации →
сериализации сгенерированным типом (вход для must-ignore, `DR-01` §E3), тогда как шкала
вердиктов оценивает терпимость к незнакомому **ключевому слову схемы**.

## Шкала round-trip (закрытое перечисление, P4.6)

| Значение | Значит |
|:--|:--|
| `SURVIVES` | неизвестное свойство документа доходит до сериализованного вывода без потерь |
| `field-lost` | прогон успешен, но неизвестное свойство молча теряется (типичный silent data loss) |
| `REJECTED` | документ целиком отклонён из-за закрытости СХЕМЫ (`additionalProperties: false`), не терпимости кандидата |
| `crash` | генератор упал до модели — round-trip не выполняется в принципе |
| `n/a` | генерация не дошла до модели по причине, не связанной с закрытостью схемы (round-trip не измерим) |

Значения — те же, что уже употреблены в матрицах P2.2/P2.3 (`bakeoff/results/php.md`,
`dart.md`), закреплены здесь отдельным разделом (Implementation Rules P4.6). Новые значения не
вводятся.

## Открытый вариант корпуса (`probes-open/`, P4.6)

`probes-open/<id>/` — та же конструкция, что в `probes/<id>/`, с ровно одним отличием: снят
`"additionalProperties": false` на внешнем уровне документа (никаких других правок). Заводится
для восьми проб, где `additionalProperties: false` искажал измерение round-trip (F3 аудита фазы
P2: закрытая схема отклоняет документ независимо от терпимости кандидата), плюс `p03` — перенесена
как есть (уже открытая, ради полноты матрицы). `p05` не переносится — её `crash` вызван
`$defs`+`$ref`+`allOf`, к `additionalProperties` не относится. Матрица —
`bakeoff/results/open-roundtrip.md`; исходный (закрытый) корпус `probes/**` не переписывается.

## Песочницы и гигиена

`bakeoff/php/` и `bakeoff/dart/` — изолированные песочницы кандидатов (свои
`composer.json`/`pubspec.yaml`); `vendor/`/`.dart_tool/`/`build/` не коммитятся, но
lock-файлы (`composer.lock`, `pubspec.lock`) коммитятся — они доказательство прогнанных
версий. Логи прогонов (`bakeoff/results/*.log`, `bakeoff/dart-transport/*.log`)
переисключены во вложенном `.gitignore` этой папки поверх корневого `*.log` репозитория —
без переисключения `git add` по ним был бы молчаливым no-op'ом.
